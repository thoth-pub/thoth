## 1. Objective

Add the protected publisher service-configuration surface required by
[ADR-0001](../../decisions/ADR-0001-publisher-package-capability-model.md)
section 4.4: one owner-and-superuser readable representation of a publisher's
desired service configuration — current package, **effective capability codes**
and enabled distribution platforms — one superuser-only staff report over that
configuration, and one superuser-only mutation that replaces it atomically under
optimistic concurrency control, with
durable audit history recording the actor, the source and the before/after
canonical state of every committed change — including a linked-platform
normalization repair, which is a committed change even when the enabled platform
set is unchanged (section 7.4).

BE-03 also establishes **one authoritative production write path** for desired
service configuration — the service-configuration write coordinator of section
7.6 — so that the canonical version token and the canonical audit history cannot
be bypassed by a production configuration writer.

BE-03 owns **desired configuration only**. It creates no distribution job, no
job target and no job attempt; it performs no dissemination; it activates no
destination; and it executes no production migration.

### 1.1 Risk rationale

BE-03 is HIGH risk because it introduces, in one task:

1. protected exposure of the commercial subscription package and its effective
   capability codes, which BE-01 deliberately left with no API surface at all;
2. an authorization decision distinguishing owner, other-publisher,
   non-superuser and superuser callers;
3. the programme's first superuser-only mutation over publisher service
   configuration;
4. persistent audit history containing actor identity;
5. a multi-table desired-state change that must be atomic;
6. optimistic concurrency with a new canonical version token;
7. linked-platform normalization that must reuse, not re-implement, BE-02
   domain invariants, **including reachable repair of an already-split
   OAPEN/DOAB pair**;
8. a public GraphQL SDL change that adds protected operations and makes the
   BE-01 `ThothPackage` **and `PublisherCapability`** enums SDL-reachable for
   the first time;
9. downstream contract authority for APP-01 and APP-02;
10. the transaction seam that BE-04 will later extend to create durable jobs
    atomically with a configuration change;
11. a claimed canonical version/audit boundary, which is only true if BE-03
    also fixes **one** authoritative production write path for desired service
    configuration (section 7.6) rather than leaving BE-02's pool-level
    assignment functions as an equivalent production entry point.

### 2.1 Verified current behaviour

Re-derived from the merged code at the authoring base:

1. **Authorization** is ZITADEL project roles on `IntrospectedUser`.
   `policy.rs` defines `Role::{Superuser, PublisherAdmin, PublisherUser,
   WorkLifecycle, CdnWrite}`. `Superuser` is an unscoped project role;
   the others are scoped to a ZITADEL organisation id.
   `PolicyContext::require_superuser`, `require_authentication`,
   `require_publisher_for` and `require_role_for_publisher` already exist.
   `require_role_for_publisher` short-circuits for superusers and otherwise
   resolves the publisher's `zitadel_id` through the `PublisherId` trait and
   tests `has_role_for_org` for **exactly the one requested role**.
   **There is no role inheritance anywhere in `policy.rs`.**
   `require_publisher_for` is `require_role_for_publisher(value,
   Role::PublisherUser)`, so for a non-superuser it requires exactly
   `PUBLISHER_USER` for that publisher's organisation. `PUBLISHER_ADMIN`,
   `WORK_LIFECYCLE` and `CDN_WRITE` are independent scoped roles that do
   **not** satisfy it. `PublisherPermissions::permissions_for_org` reports
   `publisher_admin`, `work_lifecycle` and `cdn_write` as independent booleans,
   and `Role::PublisherUser` is deliberately absent from that struct, which
   confirms the roles are additive capabilities rather than a hierarchy.
   `require_publisher_admin_for` exists and is used only by
   `imprint/policy.rs`; the merged `PublisherPolicy::can_update` gates publisher
   metadata edits on `require_publisher_for` — that is, on `PUBLISHER_USER` —
   so an account that can administer publisher metadata already holds
   `PUBLISHER_USER` in the merged model. **No repository authority makes
   `PUBLISHER_ADMIN` independently sufficient for any publisher-scoped read.**
2. **Publisher-to-account linkage** is `publisher.zitadel_id`
   (`Nullable<Text>`). `PublisherId::zitadel_id` returns
   `ThothError::Unauthorised` when it is `NULL`, so an unlinked publisher
   fails closed. An account may legitimately hold scoped roles for more than
   one organisation, so "own publisher" is a per-publisher role check, never a
   single-publisher identity. **There is no local account table and none is
   required.**
3. **Actor identity** for an authenticated API caller is
   `IntrospectedUser.user_id`, a `String`, exposed as
   `PolicyContext::user_id()`. The existing `publisher_history` table records
   exactly this as `user_id text NOT NULL`, alongside `data jsonb` and a
   timestamp, written inside the same transaction as the entity update by the
   shared `Crud::update` macro. Two further facts about that precedent are
   decisive for section 9:
   - `publisher_history.user_id` carries **no foreign key**. The `account`
     table and the historical `publisher_history_account_id_fkey` constraint
     were removed by the ZITADEL migration (`20250000_v1.0.0/up.sql`; the
     `down.sql` restores them), and no `account` table exists in the current
     `schema.rs`. The repository's established actor representation is
     therefore a **free-text actor column with no referential integrity to any
     local account**;
   - nothing in the repository requires that value to be a ZITADEL user id.
     The column's meaning is supplied by the write path, not by a constraint.
4. **Package** is `publisher.subscription_package` of PostgreSQL type
   `thoth_package`, Rust `ThothPackage` (BE-01). It has **no** GraphQL field on
   the public `Publisher` type, and `ThothPackage` is therefore **not currently
   reachable in the generated SDL**.
   **Capabilities are already code-owned and derived, and are not persisted.**
   BE-01 merged `PublisherCapability` in `thoth-api/src/model/publisher/mod.rs`
   with the six ADR-0001 values `OaiPmh`, `MetricsCollect`, `MetricsImport`,
   `MetricsDashboard`, `MetricsWidget`, `MetricsOperasExport`, each carrying a
   GraphQL description, and it already derives `juniper::GraphQLEnum` under the
   `backend` feature. `ThothPackage::capabilities(self) -> &'static
   [PublisherCapability]` is an exhaustive `match` over the four packages
   returning the module constants `OASIS_CAPABILITIES` (empty),

   `has_capability` is `capabilities().contains(&capability)`. **There is no

   capability state anywhere in `schema.rs` or in the migrations**, and BE-01's
   specification forbids adding one. Because the constants are ordered `&'static`
   slices and the mapping is a total `match`, a package's effective capability

## 6. Canonical optimistic-concurrency token

### 6.1 Decision

Add one dedicated column:

```sql
ALTER TABLE public.publisher
    ADD COLUMN service_configuration_updated_at timestamp with time zone
        DEFAULT CURRENT_TIMESTAMP NOT NULL;
```

Rust, appended to `Publisher` after `updated_at` so the `Queryable` column
order continues to match `schema.rs`:

```rust
// Snapshots and API payloads serialized before BE-03 lack this field;
// deserialization must not require it, so the documented default applies.
#[serde(default)]
pub service_configuration_updated_at: Timestamp,
```

GraphQL: exposed **only** as `PublisherServiceConfiguration.updatedAt`
(`Timestamp!`). No resolver is added to the public `Publisher` type, so adding
the struct field does not widen the public contract.

Mutation argument: `expectedUpdatedAt: Timestamp!`.

### 6.2 Update rule

Inside the mutation transaction, after the publisher row lock, the new token is

```sql
GREATEST(CURRENT_TIMESTAMP,
         <previous service_configuration_updated_at> + interval '1 microsecond')
```

This is required, not decorative. `CURRENT_TIMESTAMP` is
`transaction_timestamp()`: a transaction that started earlier but blocked on
the row lock commits later with an *earlier* timestamp. Equality against the
stored token still fails correctly in that case, so ordinary staleness
detection does not need monotonicity — but without the `GREATEST` rule a later
write could in principle store a value **equal to a token some client still
holds**, and that client's stale write would then wrongly succeed. The rule
makes the token strictly increasing per publisher and removes that ABA hazard
at no cost, because the previous value is already in hand from the locked read.

### 6.3 Rejected alternatives

- **`publisher.updated_at`.** Rejected on two independent grounds. It moves on
  *any* publisher row update because of the `set_updated_at` trigger, so an
  unrelated metadata edit — one a publisher user may perform through
  `updatePublisher` — would invalidate a superuser's in-flight configuration
  token. Conversely an assignment-only configuration change writes only
  `publisher_distribution_platform` and would **not** move it, so it fails the
  "changes on every committed service-configuration change" requirement
  outright.
- **Computed `max()` across publisher and assignment timestamps.** Rejected: it
  requires reading several independently changing timestamps after the lock
  check, gives the client a derived rather than stored token, cannot be
  compared in one atomic predicate against one stored column, and does not move
  at all for a change whose only effect is a package update on a publisher whose
  assignments are newer.
- **A separate `publisher_service_configuration` table holding one row per
  publisher.** Rejected as larger without being more robust: it needs a
  backfill for every existing publisher, a second lock target, and a
  create-on-first-write path, while providing exactly the same single-token
  semantics as one column on a row that is already the mutation's lock target.
- **A `bigint` version counter.** Functionally equivalent and marginally
  simpler to reason about, but rejected because the approved design specifies a
  timestamp-shaped `updatedAt`/`expectedUpdatedAt` contract, and section 6.2
  already gives the timestamp strict per-publisher monotonicity.

### 6.4 Accepted consequence: `publisher.updated_at` also moves

`service_configuration_updated_at` is a column **on `publisher`**, and
`diesel_manage_updated_at` installs a `set_updated_at BEFORE UPDATE` trigger on
that table (section 2.1 item 8). Any real `UPDATE` of the publisher row that
writes the new token therefore also moves the existing public
`publisher.updated_at` in the same statement. This is a deliberate, accepted and
documented consequence, not an oversight:

1. it is **unavoidable** given the section 6.1 decision to store the dedicated
   configuration token on `publisher` under the existing trigger. Avoiding it
   would require either suppressing or special-casing a trigger the whole
   repository relies on, or moving the token to a separate table — the
   alternative already evaluated and rejected in section 6.3;
2. **BE-03 accepts this behaviour deliberately.** No trigger is changed,
   dropped, made conditional or worked around, and `publisher.updated_at`
   retains its existing meaning of "this publisher row was last updated at";
3. **`Publisher.updatedAt` is *not* the service-configuration concurrency
   token.** The only token is
   `PublisherServiceConfiguration.updatedAt`, backed by
   `publisher.service_configuration_updated_at`, and it is the only value that
   may be supplied as `expectedUpdatedAt`. A client must never read
   `Publisher.updatedAt` and submit it as a configuration version, and the two
   values are not interchangeable in either direction;
4. consequently `publisher.updated_at` **may move for a package-only change, a
   platform-only change and a linked-state repair**, even though no ordinary
   publisher metadata — name, shortname, URL, `zitadel_id`, accessibility
   fields — changed. A platform-only change and a linked-state repair move it
   because they still write the token to the publisher row in the same
   transaction (section 7.3 step 10);
5. conversely a **stale request and a true semantic no-op perform no publisher
   `UPDATE` at all** (sections 7.3 steps 5 and 10, and 7.4), so they move
   neither `service_configuration_updated_at` nor `publisher.updated_at`. The
   same holds for any failed or rolled-back transaction;
6. the public timestamp therefore reveals **that the publisher record changed**,
   at the granularity it already had. It continues to expose **no** package
   value, no capability value, no platform value, no configuration version and
   no commercial configuration of any kind: `Publisher` gains no new GraphQL
   field (section 6.1), and the anonymous surface is unchanged. The disclosure
   is the fact of a change, not its content;
7. this is recorded here as a **compatibility and observable-semantic
   consequence** so that no later reader treats an unexplained
   `Publisher.updatedAt` movement as a defect, and so that no non-goal is read
   as claiming zero observable timestamp movement. Non-goal 8 prohibits exposing
   package, capability and configuration **values** publicly; it does not and
   cannot claim that the existing publisher timestamp never moves.

A second, distinct consequence concerns the pre-existing generic publisher
history. The shared `Crud::update` macro serializes the complete `Publisher`
structure into `publisher_history.data jsonb` (section 2.1 item 3). Because
section 6.1 appends `service_configuration_updated_at` to that struct, the new
field **may appear as an additional key in future `publisher_history.data`
snapshots wherever that serialization path runs** — for example an ordinary
`updatePublisher` metadata edit. That is an additive JSON key in an untyped
`jsonb` column; no existing key changes meaning, no existing row is rewritten,
and the table, its columns and its triggers are not modified.

`publisher_history` and `publisher_service_configuration_history` are **not the
same thing and must not be described as such**. `publisher_history` is the
pre-existing generic entity-history table written by the shared `Crud::update`
macro for publisher metadata edits, keyed by `user_id`, storing a whole-entity
snapshot with a legacy `timestamp without time zone`. The section 8 configuration
audit is a new, separate, append-only table written **only** by the section 7.6
coordinator, carrying `actor`, a typed `source` and the bounded three-key
canonical configuration state of section 8.2. BE-03's mutation does not write
`publisher_history`, and the configuration audit is not a view of it.

Section 18.4 requires the timestamp-movement evidence for both timestamps across
the committed-change, no-op, stale and rollback cases, and section 20 requires
the implementation report to record the `publisher_history.data` key
consequence explicitly.

## 7. Mutation

### 7.1 Signature

```graphql
replacePublisherServiceConfiguration(
  data: ReplacePublisherServiceConfigurationInput!
): PublisherServiceConfiguration!
```

```graphql
input ReplacePublisherServiceConfigurationInput {
  publisherId: Uuid!
  subscriptionPackage: ThothPackage!
  enabledDistributionPlatforms: [DistributionPlatform!]!
  expectedUpdatedAt: Timestamp!
}
```

A single input object matches the repository's existing mutation convention
(`data: NewPublisher`, `data: PatchPublisher`).

The operation is **replace**, not patch: `enabledDistributionPlatforms` is the
complete desired enabled set, and `subscriptionPackage` is the complete desired
package. An empty platform list is a valid request meaning "no destination
enabled"; it is never interpreted as "unchanged" or "all".

The input deliberately carries **no capability argument**. Effective capabilities
are derived from `subscriptionPackage` and are not independently settable
(section 10.1 item 8), so the only way to change them is to change the package.
The mutation's returned `PublisherServiceConfiguration` reflects the new
package's capabilities immediately.

### 7.2 Authorization

Superuser only, checked with the existing `PolicyContext::require_superuser`
before any read or write. Every non-superuser is denied, whatever
publisher-scoped roles it holds for the target publisher — including
`PUBLISHER_USER`, `PUBLISHER_ADMIN`, `WORK_LIFECYCLE` and `CDN_WRITE`, alone or
in combination. There is no self-service configuration path in BE-03. The write
row of the section 11.1 matrix is authoritative.

### 7.3 Required transaction sequence

The resolver performs step 1 and then delegates every read and write to the
coordinator of section 7.6, which executes exactly one database transaction on
one connection:

1. `require_superuser()`. Deny before touching the database. The resolver then
   builds the write context of section 7.6 — `source = SUPERUSER_API` and
   `actor = PolicyContext::user_id()?` — and calls the coordinator.
2. Acquire the publisher row lock — `SELECT publisher_id FROM publisher WHERE
   publisher_id = $1 FOR UPDATE` — as the first statement in the transaction.
   Absent row yields `EntityNotFound` and the transaction ends with no write.
3. Read the canonical current configuration under that lock: the publisher's
   `subscription_package` and `service_configuration_updated_at`, and the
   current enabled assignment set. This is the `before_state` of section 8.2.
4. Compare `expectedUpdatedAt` with the stored
   `service_configuration_updated_at`.
5. If they differ, fail with the stale error of section 13. **No write, no
   version bump, no audit row.** This check precedes validation and every
   lifecycle call, so a stale request fails even when it would otherwise have
   been a true no-op **and even when it would otherwise have repaired a split
   linked group**.
6. Normalize the requested platform set: deduplicate, then close it under
   `DistributionPlatform::linked_members`, so naming either OAPEN or DOAB
   enables both and naming neither disables both. The normalized set — not the
   raw request — is what is persisted and recorded in the audit `after_state`.
7. Validate the **whole** normalized set before any write. Any member that is
   not assignable — currently exactly `JISC_NBK` — fails with the existing
   `ThothError::DistributionPlatformNotAssignable` before the first lifecycle
   call, so a rejected request never depends on rollback to leave the
   configuration untouched.
8. Update `subscription_package` only if it differs. Record whether it changed.
   The coordinator writes the column directly inside its own transaction; it does
   **not** route the change through the shared `Crud::update` macro, so the
   mutation writes no `publisher_history` row and the configuration audit of
   section 8 remains the only history BE-03 writes (section 6.4).
9. Apply the desired platform state **through BE-02's connection-scoped
   lifecycle primitives**, per section 7.7, never by writing
   `publisher_distribution_platform` rows directly, as follows:
   1. partition the normalized desired set into linked groups using
      `DistributionPlatform::linked_members`, and take one canonical
      representative per group — the earliest member in
      `DistributionPlatform::ALL` order;
   2. for **every** desired group, call the connection-scoped enable primitive
      once with that group's representative. **This call is unconditional: it
      must not be gated on a membership diff.** The primitive alone decides
      whether the group is already fully normalized (both rows present, both
      enabled, `disabled_at IS NULL`, one shared `activation_id`, one identical
      `enabled_at`) and therefore a true no-op, or is one-sided,
      split-activation or split-timestamp and therefore repaired. BE-03 must not
      re-derive that predicate;
   3. partition the **currently enabled** platforms that are not in the
      normalized desired set into linked groups, and call the connection-scoped
      disable primitive once per group with its representative. Closure under
      `linked_members` guarantees a group is either wholly desired or wholly
      undesired, so no group receives both calls;
   4. record whether **any** primitive call reported a change, using the outcome
      value that section 7.7 requires those primitives to return.
   A mutation touches exactly one publisher, so the number of lifecycle calls is
   bounded by the closed 17-value inventory — 16 linked groups — and never grows
   with the number of publishers, rows or requests. The bounded-statement
   requirement of section 12.3 governs the report, not this mutation.
10. If and only if step 8 or step 9 changed something, set
    `service_configuration_updated_at` per section 6.2.
11. If and only if step 8 or step 9 changed something, insert exactly one
    `publisher_service_configuration_history` row for the whole committed
    change, with the `source` and `actor` supplied by the caller's write
    context.
12. Commit, and return the configuration as it now stands, including the new
    token.

No distribution job is created. No external side effect occurs. No message,
file, feed or upload is produced.

### 7.4 True no-op versus linked-state repair

A **true no-op** — a success that writes nothing, moves no token and writes no
audit row — exists only when **all three** of the following hold:

1. the requested `subscriptionPackage` equals the stored
   `subscription_package`; **and**
2. the normalized desired enabled membership equals the current enabled
   membership; **and**
3. every requested enabled linked group already satisfies BE-02's fully
   normalized invariant. For OAPEN/DOAB that means: both rows exist, both are
   enabled, both have `disabled_at IS NULL`, both share one `activation_id`,
   and both have an identical `enabled_at`.

Condition 3 is **not** implied by condition 2, and this is the whole point.
Consider the persisted state

```text
OAPEN  enabled, activation A, enabled_at T1
DOAB   enabled, activation B, enabled_at T2
```

Current enabled membership is `{OAPEN, DOAB}`. A request naming either OAPEN or
DOAB normalizes to the same `{OAPEN, DOAB}`. A membership-only diff is therefore
empty. If the mutation gated its lifecycle calls on that diff, BE-02's
normalization function would never run and the split pair would survive
untouched — contradicting invariant 5 and BE-02's own guarantee that a one-sided,
split-activation or split-timestamp pair is repaired rather than treated as
idempotent. Step 9.2 removes that gate: the enable primitive is invoked for every
desired group unconditionally, and it is the primitive — not BE-03 — that
distinguishes no-op from repair.

Condition 3 is therefore **decided by the primitive, not evaluated by BE-03**.
The coordinator concludes that the request was a true no-op only when the package
was unchanged *and* every lifecycle call reported `Unchanged`.

A **linked-state repair** — membership equal but the group not fully normalized —
is a committed service-configuration change. It therefore must, inside the same
transaction:

- bump `service_configuration_updated_at` per section 6.2;
- write exactly **one** audit row for the whole repair.

Its audit `before_state` and `after_state` may contain identical
`subscriptionPackage` and identical `enabledDistributionPlatforms`; they are
distinguishable because their `configurationVersion` values differ, the
`before_state` carrying the superseded token and the `after_state` the new one.
That is sufficient. **Activation identifiers and per-row timestamps must not be
added to the audit JSON merely to make a repair visible** (section 8.2); the
canonical key set stays exactly as specified.

Rationale for keeping the true no-op silent: the token is a *configuration
version*, and a version that changed without a configuration change would force
unnecessary retries on every other client and fill the audit table with rows
whose `before_state` and `after_state` are identical in every key. This matches
BE-02, whose lifecycle functions already treat a genuinely same-state transition
as a no-op that moves no timestamp — and, equally, already treat a split linked
pair as **not** same-state.

### 7.5 Independence

A request that changes only the package must leave every assignment row byte-
identical, including `activation_id`, `enabled_at` and `updated_at`. A request
that changes only platforms must leave `subscription_package` unchanged. Tests
in section 18.5 prove both directions. This is ADR-0001's independence invariant:
a package change never alters an assignment, and an assignment change never
alters the package.

One precise qualification, so this section does not contradict section 7.4: the
package is independent of assignment **state**, not of assignment **repair**. If a
requested enabled linked group is not fully normalized, the lifecycle primitive
repairs it whether or not the same request also changes the package, because the
request asserts that group as desired. The byte-identical guarantee therefore
applies to a package-only change over **already normalized** assignment state,
which is the only state in which "unchanged" is well defined. Section 18.5
requires both cases explicitly: package-only over normalized state writes no
assignment row, and package change plus split group writes the package **and**
repairs the group, still under one token bump and one audit row.

### 7.6 Canonical service-configuration write authority

#### 7.6.1 The problem this closes

Section 6 requires `service_configuration_updated_at` to change on **every**
committed service-configuration change, and section 8 requires every such change
to produce canonical audit history. Those two claims are false unless BE-03 also
fixes **one** authoritative production write path, because BE-02's pool-level
`PublisherDistributionPlatform::enable` and `::disable` can each modify a
publisher's desired platform assignments without touching the new token and
without writing an audit row. Leaving them as an equivalent production entry
point would make the canonical boundary a documentation claim rather than a
property of the system.

#### 7.6.2 The coordinator

BE-03 must introduce exactly one internal **service configuration write
coordinator**. Its Rust name, module placement and exact signature are
implementation choices; its ownership and contract are fixed here and may not be
renegotiated during implementation.

It owns every committed write of desired service configuration across all four
of:

1. the publisher's subscription package;
2. the publisher's enabled distribution-platform desired state;
3. the canonical configuration version token
   (`publisher.service_configuration_updated_at`);
4. `publisher_service_configuration_history`.

Its contract:

- it executes **one caller-owned database transaction** on one connection, and
  performs the whole of section 7.3 steps 2 to 12 inside it. It must not open a
  second transaction, and must not perform any part of the change outside the
  transaction;
- it accepts an explicit **write context** carrying the audit `source` and the
  audit `actor` (section 9). The context is a parameter, never inferred from
  ambient state and never a GraphQL input;
- it performs no authorization of its own beyond what its callers pass it.
  Authorization is the caller's responsibility and is specified in sections 7.2
  and 11.1; the coordinator must not be reachable from any unauthenticated or
  unauthorized path;
- it uses BE-02's connection-scoped lifecycle primitives for all
  platform-assignment writes (section 7.7) and never writes
  `publisher_distribution_platform` directly;
- it decides "changed versus unchanged" from the package comparison plus the
  primitives' returned outcomes (section 7.4), and it — not its callers — owns
  the token bump and the single audit insert;
- it creates no distribution job and triggers no dissemination.

BE-03's `replacePublisherServiceConfiguration` resolver **must** call this
coordinator. The resolver's own responsibilities are exactly: authorize, build
the write context, call the coordinator, map errors, and project the returned
configuration onto the GraphQL type.

#### 7.6.3 Status of BE-02's pool-level functions

BE-02's `PublisherDistributionPlatform::enable` and `::disable` are **retained
unchanged**, because BE-02's public behaviour and its merged tests must not
change (non-goal 11, section 18.6). They are reclassified, not modified:

- they remain authoritative for the **assignment lifecycle domain** they already
  own: singleton assignment lifecycle, OAPEN/DOAB normalization,
  non-assignability, activation identity and transition timestamps;
- they are **lower-level compatibility and domain functions**, not a
  service-configuration entry point. They deliberately do not touch the
  configuration token or the audit table, and they must not be changed to do so;
- **no new production service-configuration call site may use them instead of
  the coordinator.** A production caller that needs to change desired
  configuration must go through the coordinator.

This reclassification is currently costless and verifiable: as recorded in
section 2.1 item 7, both functions have **zero production call sites** today —
they are referenced only from BE-02's tests, and BE-02 exposes neither through
GraphQL. BE-03 therefore establishes the single production write path without
displacing any existing production caller.

Required implementation evidence (section 18.9):

1. an enumeration of **every** production call site of the coordinator and of
   BE-02's pool-level and connection-scoped lifecycle functions, each classified
   as production or test;
2. a recorded repository/code search demonstrating that no production
   configuration writer other than the coordinator writes
   `publisher.subscription_package`, `publisher_distribution_platform` or
   `publisher.service_configuration_updated_at`, and therefore that no
   production writer bypasses the token or audit semantics.

Honest limitation, recorded rather than hidden: the boundary is enforced by the
specification, the review and the section 18.9 search evidence, not by the type
system. The lower-level primitives remain *capable* of writing assignments
without the token. A future task that needs a second configuration writer must
extend the coordinator, not bypass it.

#### 7.6.4 BE-02's public read contract

Unchanged. BE-03 changes none of BE-02's four public GraphQL read surfaces,
their nullability, their ordering or their authorization.

### 7.7 Composing BE-02's lifecycle primitives

BE-02's `PublisherDistributionPlatform::enable` and `::disable` take `&PgPool`,
call `db.get()?`, and open their own transaction on their own pooled
connection. Calling either from inside the coordinator's transaction would
therefore run on a **different** connection and block on the publisher row lock
that the coordinator's transaction itself holds — a self-block that resolves only
by timeout.

BE-03 must resolve this with an additive, behaviour-preserving refactor:

1. extract the existing bodies into connection-scoped functions taking
   `&mut PgConnection` and assuming a caller-owned transaction, for example
   `enable_on(connection, publisher_id, platform)` and
   `disable_on(connection, publisher_id, platform)`;
2. **the connection-scoped enable primitive must itself validate
   assignability.** `enable_on(...)` — or whatever the extracted primitive is
   named — MUST execute `platform.is_assignable()` and return
   `ThothError::DistributionPlatformNotAssignable` **before making any write**,
   independently of anything its caller did. The merged pool-level `enable`
   performs that check before it acquires a connection
   (`thoth-api/src/model/publisher_distribution_platform/crud.rs`), and that
   early check is **kept** in the wrapper. The result is deliberate defence in
   depth:
   - the pool-level wrapper validates **before** acquiring a connection or
     opening a transaction, then delegates to the connection-scoped primitive.
     Its merged behaviour and its merged tests are therefore unchanged;
   - the connection-scoped primitive validates **independently** before
     persistence, so BE-02's fail-closed non-assignability semantics hold for
     **any** internal caller, present or future, that composes it into a
     caller-owned transaction;
   - the section 7.6 coordinator MUST still validate the **whole** requested
     normalized desired set before applying any change (section 7.3 step 7). The
     primitive's own check is a backstop, not a substitute: coordinator
     pre-validation is what guarantees that a rejected request never depends on
     rollback, and that a request naming a non-assignable platform fails before
     the *first* lifecycle call rather than midway through the group loop.
   Making the invariant a property of the connection-scoped primitive rather
   than of coordinator discipline alone is the point: extraction must not
   quietly downgrade a fail-closed domain check into a caller obligation;
3. make those connection-scoped functions **report whether they changed
   persisted state**. BE-02's functions currently return `ThothResult<()>`,
   which is why a caller cannot distinguish a no-op from a repair. The
   connection-scoped functions must instead return a two-state outcome — for
   example a `#[must_use]` `enum AssignmentLifecycleOutcome { Unchanged,
   Changed }` — where:
   - `Unchanged` means the function wrote nothing and moved no timestamp: for
     enable, the whole linked group was already fully normalized; for disable,
     no member of the group was enabled;
   - `Changed` means persisted assignment state was written, which includes an
     enable, a re-enable, a disable **and a linked-state repair**;
4. reduce the existing public pool-level `enable`/`disable` to acquiring a
   connection, opening a transaction, delegating, and discarding the outcome, so
   their signatures, semantics, ordering, error behaviour and existing tests are
   unchanged. In particular the pool-level `enable` keeps its non-assignable
   check **before** any connection is acquired or transaction opened, exactly as
   merged;
5. have the coordinator call the connection-scoped functions inside its own
   transaction and aggregate their outcomes per section 7.3 step 9.

Re-acquiring the publisher row lock inside those functions is a harmless no-op
because the transaction already holds it, so the lock statement is left in
place rather than made conditional.

The connection-scoped enable function keeps BE-02's normalized-state predicate as
its own internal decision. **BE-03 must not re-implement, duplicate, re-derive or
approximate** the lifecycle, the linked-group normalization, the normalized-state
predicate, the activation/timestamp semantics or the non-assignable rule. There
is exactly one linked-platform algorithm in the repository and it stays in
BE-02's module. The defence-in-depth requirement above is consistent with this:
both the pool-level wrapper and the connection-scoped primitive call the **same**
merged `DistributionPlatform::is_assignable()` and return the **same** existing
`ThothError::DistributionPlatformNotAssignable`. Calling one predicate from two
places is not a second algorithm; writing a second assignability rule, a second
error or a second inventory would be, and is prohibited.

### 7.8 Lock ordering

The only row lock in `thoth-api/src` is BE-02's publisher-row lock. BE-03 takes
the same lock, on the same single row, as the first statement of its
transaction, and every subsequent read and write — publisher columns,
assignment rows, history insert — happens after it. The order is therefore
`publisher` row, then everything else, identically to BE-02, and a mutation
touches exactly one publisher, so there is no multi-object ordering and no
inversion is possible. Any future work that would lock an assignment row before
its publisher row must be treated as a lock-order conflict and stopped.

### 7.9 BE-04 seam

BE-04 will later extend **the coordinator's same transaction**, between steps 9
and 12, to create durable job rows atomically with the desired-state change.
BE-03 must therefore keep that transaction boundary explicit and its steps
separable, and must not push any part of the desired-state change outside the
transaction. The coordinator is deliberately the single place BE-04 will extend;
that is a further reason for it to be the only production write path. BE-03 adds
no job, no hook, no callback, no event and no placeholder for that future work.

BE-04 will also need to know *which* activations are new in order to decide job
creation. Section 7.7's outcome value is deliberately the minimum BE-03
requires — whether persisted state changed — and BE-03 must not speculatively
widen it into a job-oriented change description. BE-04 extends it under its own
specification if it needs more.

## 8. Audit history

### 8.1 Table

```sql
CREATE TABLE public.publisher_service_configuration_history (
    publisher_service_configuration_history_id uuid
        DEFAULT public.uuid_generate_v4() NOT NULL,
    publisher_id uuid NOT NULL,
    actor text NOT NULL,
    source public.publisher_service_configuration_source NOT NULL,
    before_state jsonb NOT NULL,
    after_state jsonb NOT NULL,
    created_at timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT publisher_service_configuration_history_pkey
        PRIMARY KEY (publisher_service_configuration_history_id),
    CONSTRAINT publisher_service_configuration_history_publisher_id_fkey
        FOREIGN KEY (publisher_id)
        REFERENCES public.publisher(publisher_id) ON DELETE CASCADE,
    CONSTRAINT publisher_service_configuration_history_actor_check
        CHECK (btrim(actor) <> '')
);

CREATE INDEX publisher_service_configuration_history_publisher_created_idx
    ON public.publisher_service_configuration_history
    USING btree (publisher_id, created_at DESC,
                 publisher_service_configuration_history_id DESC);
```

Notes:

- **the actor column is `actor text NOT NULL`, and its meaning is defined by the
  accompanying `source` value** (section 9.1). It follows the repository's
  established actor representation — a free-text actor column with no foreign key
  to any local account, exactly as `publisher_history.user_id` is after the
  ZITADEL migration removed the `account` table and its constraint (section 2.1
  item 3). It is deliberately **not** named `user_id`: for
  `source = SUPERUSER_API` the value is exactly `IntrospectedUser.user_id` from
  `PolicyContext::user_id()`, but section 9.3 also admits a controlled
  non-ZITADEL migration control identity, and a column named `user_id` would then
  assert something untrue. **No new identifier format, credential, secret or
  local account table is introduced.**
- the `CHECK (btrim(actor) <> '')` constraint makes "explicit, stable actor
  identity" a database property rather than a convention: no write path,
  present or future, can record an anonymous or blank actor. Section 18.7
  requires catalog verification of the constraint and a test proving a blank
  actor is rejected.
- actor and source are explicit columns, not fields buried in free-form JSON,
  so they are indexable, typed and greppable.
- `created_at timestamptz` follows BE-02. The legacy
  `publisher_history.timestamp` is `timestamp without time zone`; that defect is
  not copied forward and that table is not modified.
- the table is append-only: no `updated_at` column and therefore no
  `diesel_manage_updated_at` trigger.
- the composite index supports the section 12 latest-change lookup with a total
  order, so `DISTINCT ON` is deterministic even for two rows sharing a
  `created_at`.

### 8.2 Canonical audit state

`before_state` and `after_state` are the **bounded canonical service
configuration**, never a publisher snapshot:

```json
{
  "subscriptionPackage": "OASIS",
  "enabledDistributionPlatforms": ["OAPEN", "DOAB"],
  "configurationVersion": "2026-08-12T16:04:59.123456Z"
}
```

- `enabledDistributionPlatforms` is serialized in canonical
  `DistributionPlatform::ALL` declaration order, so two equal sets always
  serialize identically and a diff of two audit rows is meaningful;
- `configurationVersion` is the `service_configuration_updated_at` value before
  and after the change, which makes each row self-describing and lets a chain
  of rows be ordered without relying on `created_at` alone;
- the JSON must contain **no** credential, token, endpoint, bucket, host,
  account secret, adapter or feed identity, protected deployment configuration,
  or unrelated publisher metadata such as name, URL, `zitadel_id` or
  accessibility fields. Section 18.4 requires a test asserting the exact key
  set;
- the key set is exactly these three keys and **must not be widened**. In
  particular `activation_id` values, per-row `enabled_at`/`disabled_at`
  timestamps and disabled-platform history must not be added — not even to make a
  linked-state repair (section 7.4) visible. A repair is already distinguishable
  through the differing `configurationVersion` values, and activation identity is
  internal lifecycle state that BE-02 deliberately does not expose.

### 8.3 Write policy

- exactly one row per committed change, covering the whole change, written
  inside the coordinator's transaction by the coordinator itself (section 7.6);
- a **true no-op** writes no row (section 7.4);
- a **linked-state repair** is a committed change and therefore **does** write
  exactly one row, whose `before_state` and `after_state` may be identical in
  package and platform membership and differ only in `configurationVersion`;
- a stale request writes no row;
- `source` and `actor` come from the caller-supplied write context, never from a
  GraphQL input and never from ambient state;
- any failure rolls the row back with the rest of the transaction.

## 9. Audit source and actor

### 9.1 Representation

A closed PostgreSQL enum plus the repository's standard derives, matching
`ThothPackage` and `DistributionPlatform`:

```sql
CREATE TYPE public.publisher_service_configuration_source AS ENUM (
    'SUPERUSER_API',
    'MIGRATION_BACKFILL'
);
```

The `source` and `actor` columns form **one contract**, not two independent
fields: `source` fixes the namespace and the required provenance of `actor`.

| `source` | Written by | Required `actor` |
|---|---|---|
| `SUPERUSER_API` | a committed `replacePublisherServiceConfiguration` call | exactly `IntrospectedUser.user_id` of the authenticated superuser, obtained from `PolicyContext::user_id()` |
| `MIGRATION_BACKFILL` | the separately approved and separately specified MIG-01 controlled historical backfill/import, per section 9.3 | a stable, explicit, non-secret control identity naming the authorized migration/operator control context, defined by MIG-01's own approved specification |

`SUPERUSER_API` is the only value BE-03 writes. BE-03 defines
`MIGRATION_BACKFILL` and writes it never; section 9.3 fixes the conditions under
which MIG-01 may write it, and section 18.4 requires a test asserting that every
row BE-03's mutation writes carries `SUPERUSER_API`.

The Rust enum derives `diesel_derive_enum::DbEnum` and `juniper::GraphQLEnum`
with `ExistingTypePath` pointing at `crate::schema::sql_types::
PublisherServiceConfigurationSource`, exactly as BE-01 and BE-02 do. There is
deliberately no `OTHER`, no `UNKNOWN` and no `Default`: an unrecognised value
must fail rather than resolve to a nearest source.

`source` identifies *how a change entered the system*. Neither `source` nor
`actor` may encode a credential, token, hostname, container, task ARN, deployment
identifier, environment name, bucket, endpoint or any other operational or secret
identity. An actor identity is a *name for an accountable control context*, never
a means of authenticating one.

### 9.2 Why the actor contract is expressible now

The alternative of shipping `SUPERUSER_API` alone and deferring
`MIGRATION_BACKFILL` to MIG-01 was evaluated and **rejected**, because the
repository already supports a coherent non-user actor contract, so there is no
incoherent reserved value to avoid:

1. the audit actor representation is a free-text column with **no** foreign key
   to any local account, and there is no local account table at all (section 2.1
   item 3). Nothing must be invented, spoofed or credentialed for a non-ZITADEL
   control context to satisfy it;
2. BE-03 **owns** the new table, so it can define the column's name and contract
   coherently in one place rather than inheriting the misleading `user_id` name
   (section 8.1);
3. `source` disambiguates the namespace, so a `MIGRATION_BACKFILL` actor can
   never be mistaken for a ZITADEL user id, and the `CHECK (btrim(actor) <> '')`
   constraint makes an anonymous actor impossible for any write path;
4. section 9.3 binds MIG-01 to the same coordinator and the same persistence
   invariants, so the value's semantics are fixed by BE-03 rather than left for a
   later task to improvise;
5. deferring the value would additionally cost a second `ALTER TYPE ... ADD
   VALUE` migration with the constraints of section 9.4, and a second additive
   SDL enum change for downstream generated clients — for no safety gain, since
   BE-03 still writes only `SUPERUSER_API` either way.

What this specification explicitly does **not** claim: it does **not** state that
a `MIGRATION_BACKFILL` actor is, or will be, an `IntrospectedUser.user_id`. MIG-01
may or may not execute under an authenticated ZITADEL user; that is MIG-01's
decision under its own specification. The contract requires only a stable,
explicit, non-secret identity for the authorized control context, which is
satisfiable in either case.

### 9.3 MIG-01 seam

MIG-01 is out of scope for BE-03 (non-goal 5) and is separately specified,
reviewed and authorized. BE-03 nevertheless fixes the persistence contract MIG-01
must satisfy, so that `MIGRATION_BACKFILL` is a usable value rather than a
reservation whose semantics cannot be met:

1. MIG-01 must write desired service configuration through the **same
   coordinator** as section 7.6, or through an explicitly controlled internal
   coordinator mode with **identical persistence invariants**. It must not
   introduce a parallel configuration writer;
2. when it commits a change it must update the canonical configuration token
   exactly as section 6.2 requires;
3. it must write the canonical audit row of section 8, with
   `source = MIGRATION_BACKFILL` and a stable, explicit, non-secret control
   actor identity per section 9.1;
4. it must create **no** `distribution_job`, job target or job attempt, and
   trigger **no** dissemination;
5. it must remain idempotent under its own later specification: a repeat run that
   changes nothing must be a true no-op under section 7.4, moving no token and
   writing no audit row;
6. it must not weaken, bypass or special-case the token, audit, transaction or
   normalization invariants specified here.

If MIG-01's later specification cannot satisfy items 1 to 6 — for example if its
execution path can supply no accountable control identity at all — that is a
MIG-01 stop condition requiring its own decision. It is not a licence to write
configuration outside the coordinator.

### 9.4 Migration and versioning consequences

Adding a future source is an additive `ALTER TYPE ... ADD VALUE` migration.
Three consequences must be recorded in the implementation report and are stated
here so a future task is not surprised:

1. an enum value can be added but **never removed or renamed** without a type
   rebuild, so each new value is a permanent contract addition;
2. `ALTER TYPE ... ADD VALUE` interacts poorly with transactional migration
   runners: the repository applies migrations through the embedded
   `diesel_migrations` runner inside a transaction, and a newly added value
   cannot be *used* in the same transaction that adds it. A future
   source-adding migration must therefore add the value in its own migration,
   separate from any migration that writes it;
3. the value is GraphQL-visible on the superuser staff report, so adding one is
   an additive SDL enum change that downstream generated clients must tolerate.

## 10. Protected configuration type

```graphql
"The desired service configuration of one publisher."
type PublisherServiceConfiguration {
  "The publisher this configuration belongs to"
  publisher: Publisher!
  "Subscription package currently assigned to the publisher"
  subscriptionPackage: ThothPackage!
  "Capabilities the current subscription package grants this publisher, in canonical capability order. Derived from the package; a capability permits a feature but does not configure or activate it"
  effectiveCapabilities: [PublisherCapability!]!
  "Distribution platforms currently enabled for the publisher, in canonical platform order"
  enabledDistributionPlatforms: [PublisherDistributionPlatformAssignment!]!
  "Version token of this configuration; supply it as expectedUpdatedAt to replace the configuration"
  updatedAt: Timestamp!
}
```

Decisions:

- `enabledDistributionPlatforms` reuses BE-02's existing
  `PublisherDistributionPlatformAssignment` type. No parallel protected
  assignment type is created, because the protected surface needs exactly the
  same fields BE-02 already exposes.
- `publisher: Publisher!` reuses the existing public type rather than
  duplicating publisher fields.
- `effectiveCapabilities` satisfies ADR-0001 section 4.4 and is specified in
  section 10.1.
- the type carries **no** actor, no source, no audit JSON and no job state.
  Configuration-change metadata appears only on the superuser report (section
  12), which removes any need for conditionally-visible fields on this type and
  keeps it identical for owner and superuser callers.
- `ThothPackage` and `PublisherCapability` become SDL-reachable here for the
  first time (section 14.2).

### 10.1 Effective capabilities

ADR-0001 section 4.4 states that protected publisher service configuration
exposes the current package, **effective capability codes** and enabled
distribution platforms, that publisher users may read their own package and
capabilities, that superusers may read any publisher's, and that anonymous users
and users scoped only to another publisher may read neither. ADR-0001 names BE-03
as an affected task; `docs/publisher-services/README.md` records that "protected
package and effective-capability reads and the dedicated superuser package
mutation remain BE-03 scope"; and [BE-01](BE-01.md) both excludes
`Publisher.capabilities` from its own scope and anticipates that BE-03 is the
task which makes the enum SDL-reachable.

**This section reconciles BE-03 with that already-approved architecture. It is
not a new architectural decision, and it is not a programme decision.** No ADR is
changed, proposed or superseded; ADR-0001 is followed as written. An earlier
draft of this specification exposed package, platforms and `updatedAt` while
omitting capabilities, which contradicted ADR-0001 and BE-01. The omission is
corrected here rather than deferred, because deferring already-approved scope
would require a new decision to justify not doing what an approved ADR already
requires.

The contract:

1. the field is
   `effectiveCapabilities: [PublisherCapability!]!` on
   `PublisherServiceConfiguration`. `PublisherCapability` is BE-01's **merged,
   code-owned** enum (section 2.1 item 4); BE-03 defines no new capability type,
   value, alias or code;
2. the value is exactly
   `ThothPackage::capabilities(<the publisher's canonical
   subscription_package>)`, projected to a `Vec<PublisherCapability>` for the
   GraphQL layer. BE-03 adds **no** second mapping, no override, no filter, no
   merge with any other source and no per-publisher adjustment;
3. **capabilities are never persisted.** There is no capability column, table,
   override row, cache or materialization, and no migration adds one (non-goal
   8, section 15). The only durable input is
   `publisher.subscription_package`, so a package/capability inconsistency is
   **not representable** and needs no reconciliation job;
4. ordering is **deterministic and canonical**: the order in which the values
   appear in `ThothPackage::capabilities()`'s returned `&'static
   [PublisherCapability]` slice, which is the declaration order of the
   `PublisherCapability` enum. Two reads of the same package always return the
   same sequence. Implementations must not sort, deduplicate, reorder or
   otherwise post-process the slice;
5. `OASIS` returns an **empty list**, which is a correct and complete answer,
   never `null` and never a fabricated placeholder;
6. the field is **protected exactly like the rest of
   `PublisherServiceConfiguration`**: it is reachable only through the
   authorization of section 11.1 — owner `PUBLISHER_USER` or superuser — and
   through the superuser-only report of section 12. There is no separate
   capability query, no separate capability authorization rule and no capability
   field anywhere else;
7. `PublisherCapability` **must not** be added to the public `Publisher` type,
   to any anonymous surface, or to any BE-02 surface. Type reachability in the
   SDL is not value exposure: every field returning the enum is protected
   (section 14.2);
8. capabilities are **not an input**. `ReplacePublisherServiceConfigurationInput`
   carries no capability argument (section 7.1); capabilities change only as a
   consequence of changing `subscriptionPackage`, and a package change therefore
   changes the returned capabilities automatically within the same response;
9. capabilities are **not** added to the audit JSON. Section 8.2's canonical key
   set stays at exactly three keys: capabilities are a pure function of
   `subscriptionPackage`, which is already recorded in both `before_state` and
   `after_state`, so recording them would store derived state redundantly and
   create a second place for the mapping to drift;
10. ADR-0001 section 4.6 is unchanged and restated here so the field is not
    misread: a capability means the package **permits** a feature. It does not
    configure, activate, credential or schedule it. `effectiveCapabilities` is
    an entitlement statement, never operational configuration, and BE-03
    activates nothing.

## 11. Owner and superuser query

```graphql
publisherServiceConfiguration(
  publisherId: Uuid!
): PublisherServiceConfiguration!
```

### 11.1 Authorization matrix

This matrix is the single authoritative statement of BE-03's read and write
authorization. It is **least-privilege** and it matches
`PolicyContext::require_publisher_for` exactly as merged: for a non-superuser,
that helper requires **exactly** `Role::PublisherUser` for the publisher's
ZITADEL organisation (section 2.1 item 1).

"Read protected configuration" means the whole of
`PublisherServiceConfiguration` — publisher, `subscriptionPackage`,
`effectiveCapabilities`, `enabledDistributionPlatforms` and `updatedAt`. There is
exactly **one** read authorization decision, taken once at resolver entry for the
whole type. `effectiveCapabilities` carries no separate rule, no separate query,
no partial visibility and no field-level exception: a caller who may read the
configuration reads the capabilities, and a caller who may not reads nothing.
This is exactly ADR-0001 section 4.4 — publisher users read their own package and
capabilities, superusers read any publisher's, anonymous and other-publisher
callers read neither.

| Caller | Read protected configuration | Replace configuration |
|---|---|---|
| `SUPERUSER` | ALLOW, any publisher | ALLOW, any publisher |
| `PUBLISHER_USER` scoped to the target publisher | ALLOW | DENY - `Unauthorised` |
| `PUBLISHER_USER` scoped only to another publisher | DENY - `Unauthorised` | DENY - `Unauthorised` |
| `PUBLISHER_ADMIN` for the target publisher, without `PUBLISHER_USER` | DENY - `Unauthorised` | DENY - `Unauthorised` |
| `WORK_LIFECYCLE` for the target publisher, without `PUBLISHER_USER` | DENY - `Unauthorised` | DENY - `Unauthorised` |
| `CDN_WRITE` for the target publisher, without `PUBLISHER_USER` | DENY - `Unauthorised` | DENY - `Unauthorised` |
| authenticated, no applicable role for the publisher's organisation | DENY - `Unauthorised` | DENY - `Unauthorised` |
| anonymous | DENY - `Unauthorised` | DENY - `Unauthorised` |

The superuser-only staff report and its count query (section 12) follow the
write column: superuser ALLOW, everyone else DENY.

Implementation: load the publisher, then
`PolicyContext::require_publisher_for(&publisher)` for the read; the mutation and
the report use `require_superuser()`. **No new ownership table, no new role, no
new helper and no new authorization framework is introduced.**

**No role inheritance may be invented.** `PUBLISHER_ADMIN`, `WORK_LIFECYCLE` and
`CDN_WRITE` are independent scoped capabilities; none of them implies
`PUBLISHER_USER`, and `require_role_for_publisher` tests exactly the one role it
is given. Two consequences are deliberate:

- an account that can administer publisher metadata, change work lifecycle
  fields or write CDN files does **not** thereby gain visibility of the
  commercial subscription package **or of its effective capability codes**.
  Commercial package and entitlement visibility must not be widened merely
  because an account holds some other scoped operational capability;
- in the merged model this denies nothing legitimate in practice, because
  `PublisherPolicy::can_update` already gates publisher metadata edits on
  `require_publisher_for` — that is, on `PUBLISHER_USER` — so a real
  publisher-administering account already holds `PUBLISHER_USER` and is allowed
  by row 2. The least-privilege reading costs no genuine access and closes the
  package-visibility widening.

If a future decision requires `PUBLISHER_ADMIN` to read the commercial service
configuration **without** `PUBLISHER_USER`, that is an explicit authorization
widening for the CTO to approve, and it must be raised as stop condition 15
rather than implemented by loosening this matrix.

"Own publisher" is a per-publisher role check, not an identity. An account
holding `PUBLISHER_USER` for several organisations legitimately owns several
publishers and may read each of them, and only those; the check is re-evaluated
per publisher. This follows the existing model rather than assuming one publisher
per account.

A publisher whose `zitadel_id` is `NULL` fails closed for every non-superuser,
because `PublisherId::zitadel_id` returns `Unauthorised`.

### 11.2 Not-found ordering

Loading the publisher precedes the role check, so an unknown `publisherId`
returns `EntityNotFound` to any authenticated caller. This mirrors the existing
`context.load_current` convention, which already requires authentication and
then loads. It is a deliberate, recorded choice: publisher existence is already
public through the existing anonymous `publisher`/`publishers` queries, so
distinguishing "absent" from "forbidden" discloses nothing new. Anonymous
callers are rejected before any load.

## 12. Superuser staff report

```graphql
publisherServiceConfigurations(
  publishers: [Uuid!] = [],
  packages: [ThothPackage!] = [],
  enabledPlatforms: [DistributionPlatform!] = [],
  limit: Int = 100,
  offset: Int = 0,
  order: PublisherOrderBy = {field: "PUBLISHER_NAME", direction: "ASC"}
): [PublisherServiceConfigurationSummary!]!

publisherServiceConfigurationCount(
  publishers: [Uuid!] = [],
  packages: [ThothPackage!] = [],
  enabledPlatforms: [DistributionPlatform!] = []
): Int!
```

**List-argument nullability follows the merged repository convention, not a new
one.** Every equivalent list filter already merged in `thoth-api/src/graphql/`
is declared in Rust as `Option<Vec<T>>` with a `#[graphql(default = vec![], …)]`
attribute, which Juniper renders as a **nullable outer list of non-null
members**. The merged SDL in `thoth-client/assets/schema.graphql` shows exactly
that shape — for example `publishers: [Uuid!] = []` on `imprints`, `publishers`
and `workCount`, and `workTypes: [WorkType!] = []` / `workStatuses:
[WorkStatus!] = []` on `works`. BE-03's three filters therefore use
`Option<Vec<Uuid>>`, `Option<Vec<ThothPackage>>` and
`Option<Vec<DistributionPlatform>>` with the same defaulting, and must render as
`[Uuid!] = []`, `[ThothPackage!] = []` and `[DistributionPlatform!] = []`.
**BE-03 must not introduce a stricter non-null-list convention** (`[Uuid!]!`,
`[ThothPackage!]!`, `[DistributionPlatform!]!`) for these arguments: it would
diverge from every merged sibling query, and an explicit `null` — which clients
and codegen may legitimately send for an omitted optional argument — would be
rejected rather than defaulted. Section 14.3 requires the regenerated SDL lines
to be shown verbatim and compared against those merged siblings.

```graphql
"A publisher's service configuration together with its latest change metadata."
type PublisherServiceConfigurationSummary {
  "The publisher's desired service configuration"
  configuration: PublisherServiceConfiguration!
  "Metadata of the most recent recorded configuration change, or null if none has been recorded"
  lastChange: PublisherServiceConfigurationChange
}

"Metadata of one recorded service-configuration change. The before and after states themselves are not exposed."
type PublisherServiceConfigurationChange {
  "When the change was committed"
  changedAt: Timestamp!
  "Identity that made the change: the account identifier for SUPERUSER_API, or the authorized control identity for a controlled backfill"
  actor: String!
  "How the change entered the system"
  source: PublisherServiceConfigurationSource!
}
```

Rules:

- **superuser only**, enforced by `require_superuser()` at resolver entry,
  before any database access;
- empty list filters mean "no filter", per repository convention;
- `enabledPlatforms` matches publishers having an **enabled** assignment for
  **every** listed platform, so multiple values narrow rather than widen. The
  semantics must be stated in the field description;
- deterministic ordering: the requested `PublisherOrderBy` plus a mandatory
  `publisher_id ASC` tie-breaker, exactly as
  `publishersByDistributionPlatform` does, so offset pagination is stable;
- `lastChange` is nullable and is `null` for a publisher with no recorded
  change — for example every publisher immediately after the migration. It is
  **not** a fabricated placeholder;
- the count query applies exactly the same filter predicates as the list query.

### 12.1 Report boundary before BE-04

The report exposes: publisher, package, enabled platform state, configuration
version, and latest configuration-change metadata.

The report does **not** expose, and BE-03 does not implement: durable job status
filtering, latest back-catalogue job or attempt state, job failure state, or
pending-onboarding state. Those are BE-04 scope and are added later, additively,
to this same report. BE-03 must not depend on job tables that do not exist and
must not invent job state.

### 12.2 What APP-01 can and cannot obtain from BE-03

The approved design lets APP-01 depend on BE-03 **and** lets superusers inspect
back-catalogue status. Once durable job state is correctly deferred to BE-04,
BE-03 alone cannot satisfy the second half of that sentence. The programme
decision candidate in
[`docs/publisher-services/decisions.md`](../../../publisher-services/decisions.md)
section 3a reconciles it explicitly, and BE-03 records the resulting scope split
here so no APP-01 work is planned against a surface BE-03 does not provide.

Available from BE-03 alone — the BE-03-dependent APP-01 scope:

1. publisher users read their **own** package, **effective capability codes** and
   enabled-platform configuration, under the section 11.1 read matrix;
2. superusers read **and edit** package and enabled-platform configuration, and
   read any publisher's effective capability codes;
3. capability-driven UI affordances: APP-01 may read `effectiveCapabilities` to
   decide which package-permitted features to show. ADR-0001 section 4.5 remains
   authoritative that hiding a control is not authorization, and section 4.6
   that a capability permits a feature without configuring or activating it, so
   APP-01 must not treat a capability as evidence that a feature is configured,
   credentialed or active;
4. linked-platform UI behaviour driven by **backend** metadata — BE-02's existing
   `distributionPlatformOptions` linked-group and assignability descriptors — not
   by duplicated frontend rules;
5. optimistic-concurrency handling: submit `expectedUpdatedAt`, and handle the
   distinct `STALE_SERVICE_CONFIGURATION` error of section 13 as
   "configuration changed; reload";
6. server-normalized state replaces local state after a successful mutation: the
   mutation returns the normalized configuration and the new token, and the client
   must adopt them rather than its own optimistic guess — which is also what makes
   linked-group normalization and linked-state repair correct in the UI.

**Not** available from BE-03 alone, and therefore requiring BE-04:

- durable back-catalogue job status;
- attempt state;
- failure state;
- pending-onboarding state.

Any APP-01 element that renders those is BE-04-dependent, not BE-03-dependent.
APP-02 remains dependent on **both** BE-03 and BE-04 and remains the full
job-aware staff report and CSV surface. BE-04 work must not be pulled into BE-03
to preserve obsolete task wording, and BE-03 must not fabricate job state to fill
the gap (non-goal 2).

### 12.3 Query efficiency

For a page of N publishers the report must issue a bounded, constant number of
statements, with no per-publisher loop:

1. one set-based statement for the filtered, ordered, paginated publisher page,
   including `subscription_package` and `service_configuration_updated_at`;
2. one set-based statement for the latest change per publisher in the page —
   `DISTINCT ON (publisher_id) ... WHERE publisher_id = ANY($1) ORDER BY
   publisher_id, created_at DESC, publisher_service_configuration_history_id
   DESC` — eagerly attached to the row values by the resolver. Because it is
   fetched eagerly and reachable only from this superuser resolver, `lastChange`
   needs no DataLoader;
3. `PublisherServiceConfiguration.enabledDistributionPlatforms` must resolve
   through **BE-02's existing request-local
   `publisher_distribution_platforms` loader**, keyed by `publisher_id`. The
   key, the batch statement, the filtering and the canonical ordering are
   already exactly what the protected field needs, so per ADR-0007 and the
   prompt's reuse rule **no second loader is created**. Adoption must remain
   loader-first: the resolver registers its key at entry with no unrelated
   awaited work before `try_load`, uses `try_load` only, and inherits the
   foundation's total fail-closed batch behaviour, in which a backend failure
   produces an error for every key in the failed chunk with no retry and no
   per-parent fallback.

Required evidence (section 18.8): measured statement counts for the report at
representative page sizes — at least 1, 25 and 200 publishers — proving the
count does not grow with N, using the existing observed-loader test harness that
exercises the production batcher.

## 13. Error semantics

| Condition | Error | GraphQL `type` |
|---|---|---|
| anonymous or wrongly scoped caller | `ThothError::Unauthorised` (existing) | `NO_ACCESS`, message `Unauthorized` |
| publisher not found | `ThothError::EntityNotFound` (existing) | `INTERNAL_ERROR` (unchanged) |
| stale configuration version | `ThothError::StalePublisherServiceConfiguration` (**new**) | `STALE_SERVICE_CONFIGURATION` (**new arm**) |
| non-assignable platform requested | `ThothError::DistributionPlatformNotAssignable` (existing) | `INTERNAL_ERROR` (unchanged) |
| backend/database failure | `ThothError::DatabaseError` (existing) | `INTERNAL_ERROR` (unchanged) |
| invalid request shape | rejected by Juniper before the resolver | n/a |

Rules:

1. exactly **one** new `ThothError` variant and exactly **one** new
   `into_field_error` arm are added. The stale case needs a distinct machine-
   readable type so APP-01 can render a clear "configuration changed; reload"
   response rather than a generic internal error;
2. every other error family keeps its current mapping. In particular
   `DistributionPlatformNotAssignable` and `EntityNotFound` continue to surface
   as `INTERNAL_ERROR`. That is not ideal, but changing it would alter BE-02's
   merged contract and normalize unrelated error families, which is out of
   scope. It is recorded as a known limitation, not silently changed;
3. duplicates in `enabledDistributionPlatforms` are deduplicated, not rejected;
   the argument is a set;
4. the stale error message must state that the configuration changed and must
   **not** include SQL, table names, column names, driver text or the current
   stored token. Disclosing the current token to a caller who has just failed a
   version check would let a client blind-write over a change it never read.
   The caller re-reads the configuration through the query;
5. no new error path may log or return credentials, tokens, endpoints, buckets
   or personal data. The pre-existing `DatabaseError` variant already renders
   the underlying driver message; BE-03 must not add to that exposure, and this
   pre-existing behaviour is recorded rather than claimed to be absent.

## 17. Rollout and rollback

### 17.1 Rollout

- initial state after merge: **repository history changes only.** No deployment
  occurs, no migration is executed anywhere, no configuration changes and no
  API behaviour is available to any client;
- feature flag/configuration: none. A protected superuser-only mutation does
  not require a flag, and no repository or programme authority establishes one.
  Production deployment and migration execution remain separate explicit gates;
- staging/preview validation: after a separately authorized deployment and
  migration, the protected query and mutation capability exists. Even then: no
  automatic distribution job exists, no dissemination occurs, no publisher
  backfill occurs, no platform is automatically enabled, and existing package
  and platform state is unchanged;
- pilot: not applicable to BE-03; the first configuration change is an
  operational act requiring its own authorization;
- activation approval: automatic job creation remains disabled until BE-04.
  MIG-01 remains the controlled historical configuration backfill;
- observation period: not applicable.

### 17.2 Rollback

Before environment adoption — no deployment, no migration executed, no audit or
configuration data exists:

- an ordinary code revert of the pull request is possible under normal review.

After environment adoption — the migration has run and audit or configuration
data may exist:

- **retain the additive foundation.** Forward repair is preferred;
- an incorrect publisher configuration is restored through a reviewed and
  audited configuration change, which itself writes an audit row, not by
  editing or deleting history;
- **do not destroy audit history as routine rollback.** Dropping a populated
  `publisher_service_configuration_history` table requires separate explicit
  authorization;
- the `down.sql` migration is reversibility **evidence**, not an automatic
  production rollback procedure.

### 18.3 Concurrency tests

The canonical scenario, executed against a real database with two connections:

```text
clients 1 and 2 both read configuration version A
client 1 replaces with expectedUpdatedAt = A  -> succeeds, version becomes B
client 2 replaces with expectedUpdatedAt = A  -> fails as stale
client 2 wrote nothing
client 2 created no audit row
final state == exactly what client 1 committed
```

Also required:

- the same scenario where the two clients' changes touch **linked OAPEN/DOAB**
  assignments, proving the loser leaves no partial or one-sided pair;
- a stale request that would have been a **true no-op** still fails;
- a stale request that would have **repaired a split OAPEN/DOAB pair** still
  fails, leaves the split pair exactly as it was, moves no token and writes no
  audit row — proving the version check precedes every lifecycle call;
- two concurrent membership-equal repair requests on the same publisher: one
  succeeds and repairs, the other fails as stale, and the final pair is
  normalized with exactly one shared activation and one audit row;
- concurrent mutations on **different** publishers do not contend;
- a mutation concurrent with a direct BE-02 `enable`/`disable` on the same
  publisher serializes on the publisher row lock and produces a consistent
  final state with no deadlock;
- token strict monotonicity per publisher across a sequence of committed
  changes, including a sequence containing a repair.

### 18.4 Transaction and audit tests

- a failure injected after the package update and before commit rolls back the
  package, the assignments, the token and the audit row together;
- exactly one audit row per committed change, never two — including a change that
  updates the package **and** several linked groups in one request;
- audit `before_state` equals the pre-change canonical state and `after_state`
  equals the post-change canonical state, both with platforms in canonical
  order;
- the audit JSON key set is exactly the three section 8.2 keys — a test that
  fails if any additional key is ever added, including any publisher metadata,
  secret-shaped field, `activation_id` or per-row timestamp;
- for a linked-state repair, `before_state` and `after_state` are equal in
  `subscriptionPackage` and `enabledDistributionPlatforms` and differ in
  `configurationVersion`, with `before_state.configurationVersion` equal to the
  superseded token and `after_state.configurationVersion` equal to the new one;
- `actor` equals the authenticated caller's ZITADEL user id from
  `PolicyContext::user_id()`;
- `source` is `SUPERUSER_API` for **every** row BE-03 writes, and no BE-03 path
  can write `MIGRATION_BACKFILL`;
- the non-blank actor check constraint rejects a blank or whitespace-only actor.

**Timestamp-movement evidence (section 6.4).** Each case must assert **both**
`publisher.service_configuration_updated_at` and `publisher.updated_at`, read
directly from the database before and after:

| Case | `service_configuration_updated_at` | `publisher.updated_at` |
|---|---|---|
| committed package-only change | moves | moves |
| committed platform-only change | moves | moves |
| committed linked-normalization repair (membership unchanged) | moves | moves |
| true semantic no-op (section 7.4) | unmoved | unmoved |
| stale request | unmoved | unmoved |
| injected failure / rolled-back transaction | unmoved | unmoved |

The platform-only and repair rows are the ones that make the section 6.4
consequence explicit rather than incidental: `publisher.updated_at` moves even
though no ordinary publisher metadata changed. A test must assert this
deliberately, so a later reader cannot mistake it for a defect and "fix" it by
suppressing the trigger or moving the token.

Also required:

- a test asserting that a committed configuration change writes **no**
  `publisher_history` row, confirming the coordinator does not route the package
  update through `Crud::update` (section 7.3 step 8);
- the implementation report must explicitly record the
  `publisher_history.data` consequence of section 6.4: because
  `service_configuration_updated_at` is appended to the `Publisher` struct that
  the shared `Crud::update` macro serializes, the new field **may appear as an
  additional key** in future `publisher_history.data` snapshots wherever that
  path runs — for example an ordinary `updatePublisher` metadata edit. The
  report must state this as an observed, accepted additive JSON-key consequence,
  and must not conflate the generic `publisher_history` table with the section 8
  configuration audit.

### 18.5 Independence, capability-derivation and linked-platform tests

**Capability derivation (section 10.1).** Required:

- for **every** `ThothPackage` value, the protected configuration's
  `effectiveCapabilities` equals `ThothPackage::capabilities()` for that package
  exactly — same values, same length, no additions, no omissions. `OASIS`
  returns an empty list, not `null`;
- capability ordering is **deterministic**: the returned sequence equals the
  order of `ThothPackage::capabilities()`'s `&'static` slice for that package,
  and repeated reads of the same publisher return an identical sequence. The
  test must assert the exact expected sequence, not set equality, so a later
  sort, dedup or reorder fails it;
- changing a publisher's package through
  `replacePublisherServiceConfiguration` changes the returned
  `effectiveCapabilities` **automatically**, in the mutation's own returned
  configuration and in a subsequent query, with no separate capability write,
  migration, backfill or reconciliation step. Assert at least one upgrade
  (`OASIS -> SPHINX`) and one downgrade (`SPHINX -> OBELISK`), matching
  ADR-0001 section 4.7;
- **no separate persisted capability state exists**: a schema/catalog assertion
  that no capability column, capability table, capability override table or
  capability index was created by BE-03's migration, and that the only durable
  input to capabilities is `publisher.subscription_package`;
- **no package/capability inconsistency is representable**: because
  capabilities are computed on read from the same locked row that supplies
  `subscriptionPackage`, a single response can never report a package and a
  capability set that disagree. Assert this on the same returned object for
  every package, and after a package change within one transaction, so the
  derivation cannot be satisfied by a stale cached list;
- a **platform-only** change leaves `effectiveCapabilities` unchanged,
  confirming ADR-0001's independence in the capability direction as well.

**Independence and linked platforms.** Required:

- a package-only change over **already normalized** assignment state leaves every
  assignment row byte-identical, including `activation_id`, `enabled_at` and
  `updated_at`;
- a package change submitted together with a **split** requested linked group
  writes the package **and** repairs the group, under exactly one token bump and
  one audit row, per section 7.5;
- a platform-only change leaves `subscription_package` unchanged;
- requesting OAPEN alone enables both OAPEN and DOAB with one shared activation
  and one shared timestamp;
- requesting DOAB alone does the same;
- omitting both disables both;
- **the split-state repair cases required by section 7.4, each executed with the
  requested enabled membership already equal to the current enabled membership,
  so a membership-only diff would be empty:**
  - both rows enabled but with **different `activation_id` values** — repaired to
    one shared activation, token bumped, exactly one audit row written;
  - both rows enabled with the same activation but **different `enabled_at`
    values** — repaired identically;
  - a **one-sided** pair (one member enabled, the other absent or disabled) where
    the request names the group — repaired identically. This case must be asserted
    both when the request names the enabled member and when it names the other
    member;
  - a **fully normalized** pair with the same request — a true no-op: nothing
    written, no activation or timestamp change, token unmoved, no audit row;
- a request that is a true no-op for the linked group but **changes the package**
  writes the package, bumps the token, writes one audit row, and leaves every
  assignment row byte-identical;
- `OCLC_KB` and `EX_LIBRIS_KB` are independently enabled and disabled with no
  coupling, and a split state in one never affects the other;
- requesting `JISC_NBK` fails with `DistributionPlatformNotAssignable`, writes
  nothing, moves no token and creates no audit row — asserted both when the
  request would otherwise have changed nothing and when it would otherwise have
  changed the package, proving validation precedes every write;
- duplicates in the requested list are deduplicated with no error;
- an empty requested list disables everything and is never treated as "all";
- a request naming several linked groups and several singletons issues one
  lifecycle call per group, writes one audit row, and bumps the token once.

### 18.6 BE-02 regression tests

- BE-02's existing lifecycle tests pass **unchanged** against the refactored
  connection-scoped functions;
- BE-02's four public read surfaces return identical results, ordering and
  errors;
- the pool-based `enable`/`disable` public API behaviour is unchanged, including
  that a non-assignable platform still fails **before** any connection is
  acquired or transaction opened;
- the connection-scoped primitives' outcome values are asserted directly for each
  transition: absent row enabled -> `Changed`; disabled row re-enabled ->
  `Changed`; already-normalized group -> `Unchanged`; split pair -> `Changed`;
  enabled group disabled -> `Changed`; group with no enabled member disabled ->
  `Unchanged`;
- **direct non-assignability regression on the connection-scoped primitive
  (section 7.7 item 2).** Call `enable_on(JISC_NBK)` — the connection-scoped
  primitive, **directly**, inside a caller-owned transaction, bypassing both the
  pool-level wrapper and the coordinator, so nothing has pre-validated the

  - it returns `ThothError::DistributionPlatformNotAssignable`;

## 19. Stop conditions

Return `BLOCKED`, identifying the exact decision or evidence required, if:

1. this specification is absent, unapproved or not repository-authoritative on
   `develop`;
2. implementation authorization is absent or not bound to a freshly verified
   exact `develop` head;
3. BE-01 or BE-02 is not actually merged and current on the verified base;
4. the current authorization architecture cannot express the section 11.1 matrix
   — least-privilege, per-publisher, no role inheritance — without a wider
   architectural change;
5. the BE-03/BE-04/APP-01 phase boundary requires an architectural decision
   beyond the programme decision recorded in
   [`docs/publisher-services/decisions.md`](../../../publisher-services/decisions.md)
   section 3a, **or that decision's authority condition is not satisfied**. The
   authority condition — stated identically in `decisions.md` section 3a and
   here — is that the **exact** BE-03-SPEC content carrying the decision has
   received explicit CTO specification approval **and** that exact approved
   content is reachable from `develop`. Implementation is `BLOCKED` if either
   half is unsatisfied. This condition is deliberately **not** "the Markdown file
   contains a literal `APPROVED` status": requiring a mutable status word would
   make the decision permanently self-blocking after approval unless a further
   repository edit changed it, which ADR-0005 prohibits as approval-state-only
   churn. GitHub remains the terminal evidence for the exact-head approval and
   merge lifecycle;
6. safe optimistic concurrency cannot be expressed with the single canonical
   token of section 6;
7. BE-02's locking and the section 7.8 lock order conflict materially — in
   particular if any code path locks an assignment row before its publisher
   row;
8. the audit actor contract of section 9.1 cannot be satisfied — for
   `SUPERUSER_API`, from existing authenticated account state;
9. the single-coordinator rule of section 7.6 cannot be established: for example
   if a production configuration write path is found that cannot be routed
   through the coordinator without changing BE-02's public behaviour, or if the
   section 18.9 bypass search cannot be made clean;
10. BE-02's linked-group normalization cannot be reached from the coordinator
    without duplicating it, or the connection-scoped primitives cannot report
    whether they changed persisted state without altering BE-02's public
    behaviour;
11. the required report necessarily depends on BE-04 job persistence rather than
    permitting a later additive BE-04 extension;
12. a cross-programme abstraction, shared-architecture change or ADR is required;
13. implementation would require protected production configuration, secrets or
    production access;
14. any requirement would need action on PR #799 or on mutation-guard mode;
15. any authority requires widening the section 11.1 read matrix — for example
    making `PUBLISHER_ADMIN` independently sufficient to read the commercial
    service configuration. That is an explicit CTO authorization decision, not an
    implementation choice;
16. the SDL diff exceeds the section 14.1 inventory, or the generated
    list-argument nullability of section 12 cannot be produced by the merged
    `Option<Vec<T>>`-plus-default convention;
17. ADR-0001 section 4.4's effective-capability exposure cannot be satisfied
    from BE-01's merged `PublisherCapability` and `ThothPackage::capabilities()`
