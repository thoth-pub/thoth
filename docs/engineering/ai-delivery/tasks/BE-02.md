## 1. Objective

configuration by implementing:

1. the closed `DistributionPlatform` domain enum;
2. the `publisher_distribution_platform` assignment relation;

## 6. `publisher_distribution_platform` data model

### 6.1 Binding table contract

Material schema:

```sql
CREATE TABLE public.publisher_distribution_platform (
    publisher_id  uuid NOT NULL,
    platform      public.distribution_platform NOT NULL,
    enabled       boolean NOT NULL,
    activation_id uuid NOT NULL,
    enabled_at    timestamp with time zone NOT NULL,
    disabled_at   timestamp with time zone,
    created_at    timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at    timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT publisher_distribution_platform_enabled_state_check CHECK (
        (enabled AND disabled_at IS NULL)
        OR
        (NOT enabled AND disabled_at IS NOT NULL)
    ),
    PRIMARY KEY (publisher_id, platform),
    FOREIGN KEY (publisher_id)
      REFERENCES public.publisher(publisher_id) ON DELETE CASCADE
);
```

Exact SQL syntax may follow repository style, but these types, nullability,
constraints and semantics are binding.

A row exists only because the platform has been enabled at least once. Therefore:

- `enabled` has no database default;
- `activation_id` is NOT NULL and has no database default;
- `enabled_at` is NOT NULL;
- `disabled_at` is the only nullable lifecycle field;
- `enabled` is true iff `disabled_at IS NULL`.

`activation_id` is application-generated so one linked OAPEN/DOAB activation can
share exactly one UUID across both rows. Lifecycle timestamps use the database
transaction timestamp (`CURRENT_TIMESTAMP`/`now()`), not `clock_timestamp()`, so
all rows in one logical transition receive identical timestamps.

Add the standard `set_updated_at` trigger using `public.diesel_set_updated_at()`.

### 6.2 Primary key and foreign key

The natural key `(publisher_id, platform)` is deliberately the primary key. This
is a reviewed departure from Thoth's usual surrogate-key pattern and is required
because one assignment row represents the current/retained lifecycle state for
one publisher/destination.

The implementation must prove pinned Diesel supports the composite key for the
specified query/update shapes. Incompatibility is a stop condition, not authority
to substitute a surrogate silently.

The FK is `ON DELETE CASCADE`. Assignment rows are configuration, not audit
history.

### 6.3 Enabled reverse-lookup index

```sql
CREATE INDEX publisher_distribution_platform_enabled_idx
    ON public.publisher_distribution_platform
    USING btree (platform, publisher_id)
    WHERE enabled;
```

The PK already supports forward lookup by `(publisher_id, platform)`. Add no
extra index without evidence of a concrete query requirement.

### 6.4 Rust persisted model

Material Rust fields:

```text
publisher_id  -> Uuid
platform      -> DistributionPlatform
enabled       -> bool
activation_id -> Uuid
enabled_at    -> Timestamp
disabled_at   -> Option<Timestamp>
created_at    -> Timestamp
updated_at    -> Timestamp
```

Add focused insert/upsert/query types and domain functions rather than generic
CRUD. Reverse publisher lookup/count may live in a focused `impl Publisher`
where it can reuse publisher ordering/filter infrastructure.

Update `schema.rs` manually and atomically. Add the table, custom SQL enum type,
`joinable!` and `allow_tables_to_appear_in_same_query!` entries required by the
actual query shape, with no unrelated formatting.

### 6.5 No data-model broadening

No descriptor table, history table, job table, cross-domain mapping, production
backfill, assignment synthesis or legacy-environment fallback belongs here.

## 7. Required domain behavior

### 7.1 Assignment lifecycle

`T` is the transaction timestamp.

| Transition | Write | `activation_id` | `enabled_at` | `disabled_at` | `updated_at` | Result |
|---|---|---|---|---|---|---|
| ABSENT -> ENABLED | INSERT | new UUID | T | NULL | T | enabled row |
| ENABLED -> ENABLED | none | unchanged | unchanged | NULL | unchanged | idempotent success |
| ENABLED -> DISABLED | UPDATE | retained | retained | T | T | retained disabled row |
| DISABLED -> DISABLED | none | unchanged | unchanged | unchanged | unchanged | idempotent success |
| DISABLED -> ENABLED | UPDATE | new UUID | T | NULL | T | new activation on retained row |
| ABSENT -> DISABLED | none | n/a | n/a | n/a | n/a | idempotent success, no row |

Binding rules:

- disabled rows are retained, never deleted;
- same-state operations perform no write and move no timestamp;
- a genuine re-enable creates a new activation ID;
- every write sets `enabled` and `disabled_at` consistently in one statement;
- no never-activated persisted row exists.

### 7.2 OAPEN/DOAB linked normalization

`OAPEN` and `DOAB` remain separate destinations but form linked group
`OAPEN_DOAB`.

A linked pair is **normalized fully enabled** only when both member rows:

- exist;
- are enabled (`disabled_at IS NULL`);
- share the same `activation_id`; and
- share the same normalized linked activation state, including the identical
  shared `enabled_at` transition timestamp.

A pair that fails even one of these conditions is **not** normalized fully
enabled. This includes, non-exhaustively:

- one member row absent;
- one member disabled;
- the two rows carrying different `activation_id` values;
- the two rows carrying different `enabled_at` timestamps, or otherwise
  representing split/inconsistent linked activation state.

Supported-domain rules:

1. enabling either enables both;
2. disabling either disables both;
3. one linked transition is one DB transaction;
4. one linked activation generates one UUID shared across both rows;
5. timestamps are identical across rows in the transition;
6. any write failure rolls back the complete linked operation;
7. linked enable is a complete no-op **only** when the pair is already
   normalized fully enabled as defined above; in that case alone it performs no
   write and moves no timestamp;
8. otherwise linked enable atomically normalizes the group -- generate one new
   `activation_id`, use one transaction timestamp, write both rows as enabled,
   set that same `activation_id` on both, set that same `enabled_at` on both,
   clear `disabled_at` on both, and commit atomically -- so a one-sided,
   split-activation or otherwise non-normalized existing enabled pair is
   repaired rather than treated as an idempotent no-op;
9. if neither existing member is enabled, linked disable is a no-op;
10. otherwise linked disable disables every existing member row without creating
    a missing row;
11. no supported domain operation can commit one-sided enabled state.

The backend owns this rule. No app-local duplicate rule is created.

The cross-row invariant is not duplicated into a database trigger or descriptor
table. Direct DBA SQL can physically create inconsistent cross-row state; that is
outside the supported domain path. A subsequent supported linked enable repairs
such state.

### 7.3 OCLC_KB / EX_LIBRIS_KB

These are independent assignments and independent activations even though both
share internal feed profile `OCLC_KBART_PUBLIC`. Enabling one never enables the
other. BE-02 stores no shared feed state and creates no job.

### 7.4 JISC_NBK

`JISC_NBK` is included in the enum/options but initially:

```text
readiness:    Inactive
availability: NonAssignable
job:          none
```

A supported enable attempt fails closed with a dedicated stable Thoth error and
writes nothing. It is not made assignable by configuration, special input or
fallback. The internal future adapter identity may exist only as descriptor
metadata.

### 7.5 Concurrency and transaction boundary

Every state transition runs inside one `connection.transaction(...)` and first
locks the publisher row using `SELECT ... FOR UPDATE`. Reads used to decide the
transition happen after the lock and inside the transaction. Assignment
activation uses `INSERT ... ON CONFLICT (publisher_id, platform) DO UPDATE` where
appropriate.

Consequences:

- two concurrent enables for one absent singleton assignment result in one
  activation; the second sees enabled and no-ops;
- two concurrent linked enables result in one shared group activation;
- enable/disable races serialize; the later transaction determines final state;
- no torn linked pair or duplicate PK row is committed;
- different publishers do not contend on the same publisher-row lock.

BE-03 later owns the protected mutation and optimistic-concurrency public API.

  or secret is exposed.

### 9.2 `Publisher.distributionPlatforms`

```graphql
type Publisher {
  # existing fields unchanged
  distributionPlatforms: [PublisherDistributionPlatformAssignment!]!
}

type PublisherDistributionPlatformAssignment {
  platform: DistributionPlatform!
  enabledAt: Timestamp!
}
```

Functional requirements:

- enabled assignments only;
- disabled historical rows excluded;
- deterministic platform order in canonical PostgreSQL enum order;
- empty list on no enabled assignments;
- no activation ID, disabled timestamp, package/capability, adapter/feed-profile
  or protected configuration exposure;
- no child pagination arguments; maximum logical result size is 17.

#### 9.2.1 ADR-0007 production DataLoader adoption - binding

The former N+1 architecture escalation is closed. BE-02 **must use the merged
ADR-0007 foundation** and becomes its first production field consumer.

The field's resolver must obey the binding loader-first invariant:

> A loader-backed resolver MUST register its target DataLoader key before
> performing unrelated awaited work. Any resolver that cannot obey this
> loader-first rule MUST provide field-specific query-count evidence
> demonstrating that its actual execution shape remains bounded and set-based
> before that field is approved for DataLoader adoption.

For this field, there is no approved reason to violate loader-first: the resolver
already has `self.publisher_id`, so it must call the target loader near resolver
entry before unrelated awaited work.

##### Ownership and construction

- add one typed field-specific loader to the existing request-local
  `RequestLoaders` bundle in `thoth-api/src/graphql/dataloader.rs`;
- construct it per request using existing `configured_loader(...)` or an
  equivalent constructor that visibly applies **max batch size 200** and **yield
  count 10**;
- use `dataloader::non_cached::Loader`; no global/static/app-data loader;
- completed values must not be cached across requests or replayed as an
  independent cache;
- do not reintroduce ADR-0006 state, prefetch or scope concepts;
- loader availability is independent of mutation guard mode.

##### Key and value contract

The field's DataLoader key is exactly `publisher_id` (`Uuid`). There is no
argument/result-shape input, so no second key dimension is needed. If the future
field contract changes to include any result-changing argument, the key contract
must be revisited rather than silently reusing this key.

The loaded value represents the full deterministic vector of **enabled**
`PublisherDistributionPlatformAssignment` rows for one publisher.

##### API and totality

- use DataLoader `try_load`, never DataLoader `.load()`;
- a batch function is total over every requested publisher ID;
- a publisher with zero enabled assignments maps to successful `Vec::new()`;
- no requested key may be omitted from the batch result;
- missing/defective result handling fails closed through `try_load` and never
  panics or fabricates success;
- a backend failure produces an error value for **every requested key** in that
  failed chunk;
- no automatic retry and no direct per-parent fallback occurs after a failed
  batch.

##### Diesel boundary and SQL shape

The batch function must:

1. clone/move only `Arc<PgPool>` plus an owned key collection into
   `tokio::task::spawn_blocking`;
2. acquire the Diesel connection **inside** the blocking closure;
3. perform synchronous Diesel work entirely inside the closure;
4. drop the connection before the closure returns;
5. await only the closure result;
6. use a set-based query over all chunk publisher IDs, materially
   `publisher_id.eq_any(keys)` plus `enabled = true`;
7. order rows deterministically by `(publisher_id, platform)` or an equivalent
   shape that yields canonical per-publisher platform order;
8. group the rows in memory into one total result per requested key;
9. issue no query loop over publisher IDs.

For up to 200 distinct loader keys in an immediately ready cohort, one target
assignment SQL statement is expected. For 201 keys, two chunks are expected;
for 500 keys, three chunks are expected, subject to the exact loader scheduling
rules already characterized by the foundation. The specification does **not**
claim a global arbitrary-scheduling guarantee: deliberately delayed cohorts may
fragment, which is why loader-first is binding.

##### Error convention

`Publisher.distributionPlatforms` is a new public field in a family whose normal
repository convention is `ThothResult -> FieldResult` through
`.map_err(Into::into)`. Unless exact-base discovery proves the field family has
an approved different convention, the loader-backed field must preserve the
**conventional Juniper error shape**: the same message/path/null behavior as its
direct synchronous baseline and no newly invented `extensions.type`.

Use the existing safe `SharedBatchError` mechanism or an equally safe
non-panicking, non-serde projection consistent with ADR-0007. Do not serialize
and deserialize a `ThothError` to make it cloneable. This task is not a
repository-wide error-normalization project.

##### Query-count acceptance

The implementation must measure actual SQL through Diesel connection
instrumentation or an equivalently trustworthy external observation point. An
implementation-side counter alone is insufficient.

For both parent shapes:

```graphql
publishers(limit: n) {
  publisherId
  distributionPlatforms { platform enabledAt }
}

publishersByDistributionPlatform(platform: OAPEN, limit: n) {
  publisherId
  distributionPlatforms { platform enabledAt }
}
```

record the assignment-query count for multiple `n`, including at least one
`n > 200` where the fixture is practical. The required reference case is:

```text
250 parent publishers
-> target DataLoader chunks [200, 50]
-> exactly 2 set-based assignment SQL statements
-> not 250 per-parent assignment queries
```

The existing parent root query SQL is measured/reported separately from the
child assignment query count. Do not claim the whole GraphQL operation is N+1
free if an unrelated legacy intermediate path is not measured.

The batch-boundary tests should also cover 1, 100, 200, 201 and 500 independent
ready keys using the production constructor, expecting `[1]`, `[100]`, `[200]`,
`[200,1]`, `[200,200,100]` for the target loader in both Tokio runtime flavors
where practical. Foundation tests may be reused for generic scheduler behavior,
but BE-02 must add field-specific SQL/membership/order evidence.

##### Repeated references and non-caching

Pending duplicate keys may coalesce. A completed non-cached value is not
promised to be reused after completion. Therefore BE-02 must not write a test or
report that incorrectly requires universal one-load reuse for arbitrarily
separated aliases. Instead prove:

- concurrent/pending same-key references may coalesce correctly;
- sequential completed loads remain fresh/non-cached per ADR-0007;
- regardless of scheduling, loader-first list execution remains bounded and
  set-based rather than `1 + N`.

## 10. Failure and fail-closed semantics

Binding principles:

```text
configuration failure fails closed
empty assignment state never broadens processing
backend failure never becomes an empty success
```

| Condition | Required behavior |
|---|---|
| DB error in root query/transition | propagate error; never return broad/unfiltered result |
| DB error in DataLoader chunk | one GraphQL-visible error per affected field occurrence according to ordinary Juniper propagation; every key in failed chunk gets an error; no retry/fallback |
| zero enabled rows for a requested publisher | successful empty vector, not missing key |
| defective batch omits requested key | `try_load` fails closed; no panic/fabricated result |
| attempt to enable JISC_NBK | dedicated stable error before any write; no row change |
| linked transaction failure | complete rollback; no one-sided state |
| invalid GraphQL enum | input-coercion error before resolver/query |
| unknown DB enum label | Diesel/Thoth error; no fallback enum |
| disabled assignment | excluded from public active reads |

For the DataLoader failure fixture, compare a direct synchronous baseline query
with loader-backed execution and assert equivalent data/null propagation,
GraphQL path, message, extensions convention and location where stable. Assert
exactly one failed batch dispatch for the representative cohort and no fallback
SQL.

### 13.3 Locking and downtime

The FK references populated `publisher`. On PostgreSQL 17, establishing a
foreign key takes `SHARE ROW EXCLUSIVE` on the referenced `publisher` table in
addition to the constrained table. Publisher reads using `ACCESS SHARE` remain
available; ordinary writes using `ROW EXCLUSIVE` are blocked while the lock is
held.

The future implementation must reassess its **actual DDL** and verify locks
empirically on a disposable DB by observing `pg_locks` from a second session
while the migration transaction is open. Record:

- PostgreSQL major version;
- observed lock modes on both tables;
- reads-unaffected/writes-blocked conclusion for `publisher`;
- whether a migration-session `lock_timeout` is appropriate and why;
- no production duration claim.

The child table is created empty, so there is no child-row FK validation scan.
The principal operational concern is lock acquisition/queueing behind conflicting
transactions, not an asserted production duration.

Production migration execution remains separately gated by CG-13/current
release controls and is not authorized here.
