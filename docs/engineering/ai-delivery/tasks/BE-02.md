## 1. Objective

Add the inactive, additive backend foundation for publisher distribution-platform
configuration by implementing the closed `DistributionPlatform` domain enum, the
`publisher_distribution_platform` assignment relation, the assignment activation
lifecycle, code-owned exhaustive platform descriptors, linked OAPEN/DOAB
normalization, and the public GraphQL platform metadata and assignment queries.

BE-02 activates nothing. It performs no dissemination, creates no distribution
job, executes no production migration, creates no publisher assignment row,
changes no publisher UI, and adds no service-configuration mutation.

### 1.1 Risk rationale

BE-02 is HIGH risk because it:

1. **carries a canonical schema migration** - it creates a new PostgreSQL enum
   type and a new persistent table in the canonical domain, and must update the
   repository-authoritative `thoth-api/src/schema.rs` atomically under ADR-0003
   Architecture A;
2. **introduces new persistent publisher service configuration** - the
   assignment relation becomes the authoritative desired-state record for
   publisher distribution, replacing publisher-ID environment variables in later
   tasks;
3. **establishes linked-state transactional invariants** - the OAPEN/DOAB linked
   pair must never reach a supported one-sided enabled state, and a linked
   transition must be atomic and share one activation identity;
4. **adds a public API contract** - four public GraphQL surfaces with stable
   enum codes, deterministic pagination and count semantics that downstream
   repositories will pin;
5. **is depended on downstream by dissemination** - `DIS-01`, `DIS-02`,
   `MIG-01`, `BE-03`, `BE-04` and `EXP-01` all consume these semantics;
6. **could broaden publisher processing if assignment semantics are wrong** - a
   query that returned disabled rows, or a helper encoding an "all publishers"
   fallback, would later cause unintended external delivery.

BE-02 is not CRITICAL: it performs no destructive production migration, no
canonical data rewrite, no external publication, no mass redistribution and no
global security-boundary change. Uncertainty does not reduce controls
(`risk-classification.md`, "Escalation rules").

### 1.2 Required HIGH-risk controls

- this approved specification, independently reviewed and explicitly
  CTO-approved, before implementation;
- separate explicit CTO implementation authorization bound to a freshly verified
  exact `develop` SHA (section 22);
- HIGH or maximum practical implementation reasoning;
- independent cross-model review by an agent/model that did not implement the
  task, bound to the exact PR head;
- empty-database and representative populated-database migration evidence on
  disposable PostgreSQL only;
- failure-path, concurrency, authorization and non-exposure tests;
- compatibility assessment;
- rollout and rollback plans;
- initially inactive behaviour;
- explicit CTO merge authorization bound to the exact independently reviewed PR
  head, with a guarded merge (`--match-head-commit`);
- separate, later, explicit authorization for any production deployment,

Approval of this specification does not authorize implementation. Merge of the

**Migrations and schema.**

- Migration directories are `thoth-api/migrations/YYYYMMDD_v<major>.<minor+1>.0/`
  containing `up.sql` and `down.sql`, created by `make migration` (the Makefile
  target derives the date and bumps the workspace minor version). The most
  recent is `thoth-api/migrations/20260805_v1.7.0/` (BE-01). **Do not invent a
  directory name; use `make migration`.**
- Migrations are applied and reverted by the embedded runner: `cargo run migrate`
  and `cargo run migrate --revert` (full-history revert).
- PostgreSQL enum convention (BE-01, current): `CREATE TYPE public.<snake_case>
  AS ENUM ('SCREAMING_SNAKE', ...);` with schema-qualified type names and
  schema-qualified casts in defaults.
- UUID convention: `uuid`, with `DEFAULT public.uuid_generate_v4()` where the
  database owns generation (`uuid-ossp` extension is installed).
- Timestamp convention is mixed historically. Older tables (`publisher`,
  `issue`, `affiliation`) use `timestamp without time zone DEFAULT
  CURRENT_TIMESTAMP NOT NULL`; newer tables (`award`, `book_review`,
  `additional_resource`) use `timestamp with time zone DEFAULT CURRENT_TIMESTAMP
  NOT NULL`. `thoth-api/src/schema.rs` maps both to `Timestamptz` (an
  intentional physical-to-Rust alias preserved under ADR-0003).
- `updated_at` maintenance convention: a per-table
  `CREATE TRIGGER set_updated_at BEFORE UPDATE ON <table> FOR EACH ROW EXECUTE
  FUNCTION public.diesel_set_updated_at();`. That function sets
  `NEW.updated_at := current_timestamp` only when the row actually changed and
  `updated_at` was not explicitly set.
- Foreign-key convention: `ON DELETE CASCADE` (62 of 64 foreign keys; the
  remaining two are `ON DELETE SET NULL` for optional references).
- Partial-index convention is established and idiomatic, for example
  `CREATE UNIQUE INDEX location_uniq_platform_idx ON public.location USING btree
  (publication_id, location_platform) WHERE (NOT (location_platform =
  'Other'::public.location_platform));` and `CREATE UNIQUE INDEX
  publisher_zitadel_id_key ON public.publisher USING btree (zitadel_id) WHERE
  (zitadel_id IS NOT NULL);`.
- Check-constraint convention: named `CONSTRAINT <table>_<subject>_check CHECK
  (...)`, declared inline in `CREATE TABLE` or added by `ALTER TABLE`.
- Primary-key convention: every existing table has a single surrogate `uuid`
  primary key. Join tables (`issue`, `work_relation`) also carry a surrogate key
  plus a `UNIQUE` constraint on the natural pair. **No existing table uses a
  composite primary key**, so BE-02's approved `publisher_id + platform`
  composite primary key is a deliberate, specification-level departure (see
  section 6.2).
- Migration CI: `.github/workflows/run_migrations.yml` applies, reverts and
  reapplies the full chain on a disposable database.

**Rust model conventions.**

- Persisted enums use
  `#[cfg_attr(feature = "backend", derive(diesel_derive_enum::DbEnum,
  juniper::GraphQLEnum), graphql(description = "..."), ExistingTypePath =
  "crate::schema::sql_types::<Type>")]`, with per-variant
  `#[cfg_attr(feature = "backend", db_rename = "SCREAMING_SNAKE",
  graphql(description = "..."))]`.
- Non-persisted domain enums use `#[cfg_attr(feature = "backend",
  derive(juniper::GraphQLEnum), graphql(description = "..."))]` with no
  `DbEnum`.
- Both carry `#[derive(Debug, Clone, Copy, ..., Serialize, Deserialize,
  PartialEq, Eq, EnumString, Display)]`, `#[serde(rename_all =
  "SCREAMING_SNAKE_CASE")]` and `#[strum(serialize_all =
  "SCREAMING_SNAKE_CASE")]`.
- `ThothPackage` (BE-01) is the exact precedent, in
  `thoth-api/src/model/publisher/mod.rs`.
- Code-owned mappings are `const` slices plus an exhaustive `match self` with no
  wildcard arm (`ThothPackage::capabilities`).
- Model modules live under `thoth-api/src/model/<entity>/` as `mod.rs`,
  `crud.rs`, `policy.rs`, `tests.rs`, declared in `thoth-api/src/model/mod.rs`.
- The `Crud` trait provides the generic CRUD/list/count contract used by GraphQL
  CRUD entities; `crud_methods!` supplies `from_id`/`create`/`update`/`delete`.
  `update` wraps its write and history insert in `connection.transaction(...)`.
- Transactions use `diesel::Connection::transaction`. `thoth-api/AGENTS.md`
  section 5 requires database-enforced correctness for concurrent operations and
  lists row locks, unique constraints and check constraints as the approved
  tools.
- Time is `crate::model::Timestamp` (a newtype over `DateTime<Utc>`).
- Errors are `thoth_errors::ThothError` variants; the established convention is
  a dedicated stable variant per domain rule (e.g. `CanonicalLocationError`,
  `IssueImprintsError`, `ChapterIsbnError`).
- Ordering uses `apply_directional_order!`, which supports a primary expression
  **plus an optional always-ascending secondary tie-breaker**.

**GraphQL conventions.**

- One `QueryRoot` in `thoth-api/src/graphql/query.rs` with flat top-level
  fields; entity objects are implemented explicitly in
  `thoth-api/src/graphql/model.rs` via `#[juniper::graphql_object(Context =
  Context)]`. Simple code-owned value objects may use
  `#[derive(juniper::GraphQLObject)]` (precedent: `FileUploadResponse`,
  `UploadRequestHeader` in `thoth-api/src/model/file/mod.rs`).
- **Pagination is offset/limit, not cursor-based.** The established shape is
  `limit: Option<i32>` (`default = 100`), `offset: Option<i32>`
  (`default = 0`), an `order: Option<XOrderBy>` input, returning `Vec<T>`, with
  a separate sibling `xCount(...) -> i32`. There is no connection/edge/pageInfo
  type anywhere in the schema. **BE-02 must not introduce one.**
- Counts return `i32` via the documented `i64 -> String -> i32` conversion in
  `Crud::count` implementations.
- Nullability follows Rust: `Option<T>` is nullable, everything else
  non-nullable. Every field and argument carries a `#[graphql(description =
  "...")]`.
- Errors are `FieldResult<T>` with `.map_err(Into::into)` from `ThothResult`.
- Empty results are returned as empty `Vec`, never as an error.
- **`QueryRoot` read fields perform no authorization**: the entire GraphQL read
  API (including `publishers`, `publisher`, `publisherCount`) is anonymously
  accessible today. `crate::policy` is used by mutations and by protected
  surfaces, not by these public reads.
- `thoth-client/assets/schema.graphql` is generated at build time by
  `thoth-client/build.rs` and is **not** checked into the repository (only
  `thoth-client/assets/queries.graphql` is tracked). No committed generated-SDL
  update is therefore required by BE-02.

**Existing publisher surface.**

- `Publisher`, `NewPublisher`, `PatchPublisher`, `PublisherHistory`,
  `PublisherOrderBy`, `PublisherField`, `ThothPackage` and `PublisherCapability`
  are in `thoth-api/src/model/publisher/mod.rs`.
- `Publisher::all` / `Publisher::count` are in
  `thoth-api/src/model/publisher/crud.rs`. **`Publisher::all` applies no
  tie-breaker**, so its pagination is not deterministic under duplicate sort
  keys. BE-02 must not inherit that defect (section 7.3).
- The public GraphQL `Publisher` object is at `thoth-api/src/graphql/model.rs`
  and currently exposes no package or capability data. `Publisher.imprints` and
  `Publisher.contacts` are the precedent for a publisher-scoped child field.
- Database-backed tests live in `thoth-api/src/model/<entity>/tests.rs` and
  `thoth-api/src/graphql/tests.rs`, using the shared harness in
  `thoth-api/src/model/tests.rs` (`mod db`, `TEST_DATABASE_URL`, exclusive file
  lock, `execute_graphql`).

## 5. The `DistributionPlatform` enum - binding

### 5.0 Final inventory

`DistributionPlatform` contains exactly these 17 stable values, in this
canonical order (ADR-0004 section 4.1):

```text
INTERNET_ARCHIVE
OAPEN
DOAB
SCIENCE_OPEN
CAMBRIDGE_UNIVERSITY_LIBRARY
CROSSREF
FIGSHARE
ZENODO
PROJECT_MUSE
JSTOR
EBSCO_HOST
PROQUEST_EBOOK_CENTRAL
GOOGLE_PLAY
BKCI
OCLC_KB
EX_LIBRIS_KB
JISC_NBK
```

No other value may be added by BE-02. The following are explicitly prohibited:

- an `OTHER` value;
- any fallback, catch-all, wildcard or default enum value;
- any `UNKNOWN` or `PROVISIONAL` value;
- a universal platform enum shared across domains;
- collapsing `DistributionPlatform` into `MetricPlatform`.

`DistributionPlatform` and `MetricPlatform` remain separate domains with no
name-based conversion, no shared GraphQL enum and no inferred mapping
(ADR-0002 sections 4.1, 4.2, 4.5).

Aliases and historical names resolve to stable codes and do **not** become
additional enum values. In particular: `Google Books` -> `GOOGLE_PLAY`;
`ProQuest` / `Ebrary` -> `PROQUEST_EBOOK_CENTRAL`; `ProQuest ExLibris` ->
`EX_LIBRIS_KB`; `JISC KB` / `Jisc KB` -> `JISC_NBK`. The complete alias table is
ADR-0004 section 4.2.

The 10 ADR-0004 exclusions remain excluded and must not be reconsidered by
BE-02: `EBSCO_KB`, `PROQUEST_SERIALS_SOLUTIONS_KB`, `OVERDRIVE`, `BDS_LIVE`,
`RNIB_BOOKSHARE`, `SCIELO_BOOKS`, `ZOTERO`, `THOTH`, `PUBLISHER_WEBSITE`,
`OTHER`.

If live ADR-0004 contradicts any value above, the implementing agent must stop
and report the conflict rather than choosing silently.

### 5.1 PostgreSQL enum

```text
Type name:  public.distribution_platform
Kind:       PostgreSQL ENUM
Values:     the 17 codes of section 5.0, uppercase SCREAMING_SNAKE_CASE,
            single-quoted, in the canonical order above
```

The type name `distribution_platform` is the identity named by the approved
design and by ADR-0002 section 4.1, and it matches the current repository
convention for PostgreSQL enum type names (`thoth_package`, `location_platform`,
`work_type`, `contact_type`). No materially different database identity is
required, so no approved stable identity is changed.

**Declaration order is binding.** PostgreSQL orders enum values by declaration
order, and BE-02 relies on that ordering for the deterministic ordering
guarantees in sections 9.1 and 9.2. The declaration order is the ADR-0004
section 4.1 inventory order.

**Creation order in `up.sql`:** create the type first, then the table that
references it, then constraints, then the index, then the trigger. This matches
the BE-01 migration shape.

**Down migration:** drop in reverse dependency order -

```sql
DROP TABLE IF EXISTS public.publisher_distribution_platform;
DROP TYPE IF EXISTS public.distribution_platform;
```

The trigger and index are dropped implicitly with the table. `IF EXISTS` follows
the BE-01 `down.sql` convention.

**Compatibility with existing databases:** the migration is purely additive. It
creates one new type and one new table, alters no existing table, adds no column
to an existing table, and creates no row. Existing databases are unaffected
except for the new, unused objects.

### 5.2 Rust enum

`DistributionPlatform` is a closed, exhaustive Rust domain enum with exactly 17
variants in the canonical order.

- **Diesel/PostgreSQL conversion:** `diesel_derive_enum::DbEnum` with
  `ExistingTypePath = "crate::schema::sql_types::DistributionPlatform"` and a
  per-variant `db_rename` giving the exact uppercase database label, exactly as
  BE-01 does for `ThothPackage`. The `sql_types::DistributionPlatform` struct is
  added to `thoth-api/src/schema.rs` with
  `#[diesel(postgres_type(name = "distribution_platform"))]`.
- **serde representation:** `#[serde(rename_all = "SCREAMING_SNAKE_CASE")]`, so
  serde emits and accepts exactly the stable codes.
- **Stable string representation:** `strum::Display` / `strum::EnumString` with
  `#[strum(serialize_all = "SCREAMING_SNAKE_CASE")]`, so `Display` and
  `FromStr` also use exactly the stable codes.
- **GraphQL representation:** `juniper::GraphQLEnum` (section 5.3).
- **Derives:** `Debug, Clone, Copy, Serialize, Deserialize, PartialEq, Eq,
  EnumString, Display` (plus `Hash` if the implementation needs it).
- **No `Default`.** Unlike `ThothPackage`, `DistributionPlatform` has no
  defensible default: a default would function as a fallback value. The
  implementation must not derive or implement `Default` for it.
- **Invalid-value failure semantics:** an unrecognised database label, serde
  value, `FromStr` input or GraphQL input value must fail. `DbEnum` conversion
  returns a Diesel deserialization error which surfaces as
  `ThothError::DatabaseError`; `FromStr` returns `Err`; an invalid GraphQL enum
  literal or variable fails Juniper's input coercion before the resolver runs.
  No path may substitute a default, a nearest match or a fallback.
- **No wildcard behaviour:** every `match` on `DistributionPlatform` in BE-02
  code must be exhaustive with no `_` arm.

Placement: the enum, the descriptor types and the assignment model belong in one
new module, `thoth-api/src/model/publisher_distribution_platform/`, declared in
`thoth-api/src/model/mod.rs`. The implementing agent may instead follow a
different placement that the live tree demonstrates is more idiomatic, and must
justify it in the implementation report; it must not scatter the enum,
descriptors and model across unrelated modules.

`Crud` must **not** be implemented for the assignment entity. `Crud` is the
generic contract for GraphQL CRUD entities with create/update/delete mutations,
which BE-02 explicitly does not add (BE-03 owns the mutation surface). BE-02
provides bespoke, narrowly scoped domain and query functions instead.

### 5.3 GraphQL enum

## 6. `publisher_distribution_platform` data model

### 6.1 Table

```sql
CREATE TABLE public.publisher_distribution_platform (
    publisher_id  uuid NOT NULL,
    platform      public.distribution_platform NOT NULL,
    enabled       boolean DEFAULT false NOT NULL,
    activation_id uuid,
    enabled_at    timestamp with time zone,
    disabled_at   timestamp with time zone,
    created_at    timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at    timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT publisher_distribution_platform_enabled_state_check CHECK (
        (enabled AND activation_id IS NOT NULL AND enabled_at IS NOT NULL)
        OR
        (NOT enabled AND disabled_at IS NOT NULL)
    )
);
```

The exact SQL text is the implementing agent's, but the types, nullability,
defaults, constraint semantics and names above are binding.

**Settled decisions and their basis:**

| Question | Decision | Basis |
|---|---|---|
| `publisher_id` type | `uuid NOT NULL`, no default | matches `publisher.publisher_id`; the value always comes from an existing publisher |
| `platform` type | `public.distribution_platform NOT NULL` | the PostgreSQL enum of section 5.1 |
| `enabled` | `boolean DEFAULT false NOT NULL` | repository boolean convention (`canonical boolean DEFAULT false NOT NULL`); a row must never be `NULL`-enabled, and the safe default is disabled (fail closed) |
| `activation_id` | `uuid` **nullable, no database default** | see below |
| `enabled_at`, `disabled_at` | `timestamp with time zone`, nullable | lifecycle timestamps are genuinely absent before the corresponding transition occurs |
| `created_at`, `updated_at` | `timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL` | the newer repository table convention (`award`, `book_review`, `additional_resource`); using `with time zone` makes the physical type agree with the `Timestamptz` mapping already used throughout `thoth-api/src/schema.rs`, rather than relying on the legacy `without time zone` alias carried by older tables. This is implementation-level typing consistent with current repository practice and changes no approved architecture |
| Primary key | `PRIMARY KEY (publisher_id, platform)` | the approved design's explicit requirement; it makes "one assignment row per publisher per platform" a database guarantee rather than an application check, which `thoth-api/AGENTS.md` section 5 requires. No surrogate key is added: a surrogate would permit duplicate `(publisher_id, platform)` pairs unless separately constrained, and BE-02 adds no CRUD mutation that needs one |
| Foreign key | `FOREIGN KEY (publisher_id) REFERENCES public.publisher(publisher_id) ON DELETE CASCADE` | the dominant repository convention (62 of 64 FKs); deleting a publisher must not leave orphan assignments, and assignments are configuration, not audit history |
| `activation_id` generation owner | **the application (Rust), not the database** | a linked OAPEN/DOAB activation must write **one** activation identity to **two** rows in one transaction. A column `DEFAULT uuid_generate_v4()` would generate two different values, silently breaking the linked-identity invariant. The domain layer therefore generates one `Uuid::new_v4()` per logical activation and writes it to every row in that activation |
| `enabled_at` / `disabled_at` / `updated_at` generation owner | **the database transaction timestamp** (`CURRENT_TIMESTAMP` / `now()`), evaluated inside the single transition transaction | `CURRENT_TIMESTAMP` is transaction-start time and is therefore *identical* for every row written by one logical transition, which is exactly the determinism the linked pair requires. `clock_timestamp()` must not be used |
| `updated_at` maintenance | add `CREATE TRIGGER set_updated_at BEFORE UPDATE ON public.publisher_distribution_platform FOR EACH ROW EXECUTE FUNCTION public.diesel_set_updated_at();` | the established per-table repository convention; the function already exists and sets `current_timestamp` only when the row actually changed |

**Lifecycle invariant enforced by the database.** The row-level check constraint
above enforces that an enabled row always carries an `activation_id` and an
`enabled_at`, and that a disabled row always carries a `disabled_at`. This is a
single-row invariant, expressible as an ordinary `CHECK`, and consistent with
the repository's heavy use of named check constraints. It is required.

**Lifecycle invariants deliberately *not* enforced by the database:**

- the cross-row OAPEN/DOAB linkage (see section 7.2.1);
- `JISC_NBK` non-assignability (see section 7.4).

### 6.2 Composite primary key - explicit note for review

No existing Thoth table uses a composite primary key. This is therefore a
deliberate, specification-level decision, not an accidental deviation. It is
adopted because:

- the approved design states the primary key is `publisher_id` plus `platform`;
- the natural key *is* the identity of the row - there is exactly one assignment
  state per publisher per platform, and re-enabling reuses the same row rather
  than creating a new one;
- it gives the `ON CONFLICT (publisher_id, platform) DO UPDATE` upsert used by
  the lifecycle (section 7.1) a natural arbiter;
- Diesel supports composite primary keys, expressed in `schema.rs` as
  `publisher_distribution_platform (publisher_id, platform)`.

The implementing agent must confirm that Diesel's composite-key support behaves
correctly with the `Queryable` model and the query layer at the exact base, and
must record that verification. If a composite primary key proves incompatible
with the pinned Diesel version's usable API for these queries, that is a
`BLOCKED` stop condition (section 19), not a licence to substitute a surrogate
key silently.

### 6.3 Index

```sql
CREATE INDEX publisher_distribution_platform_enabled_idx
    ON public.publisher_distribution_platform
    USING btree (platform, publisher_id)
    WHERE enabled;
```

This is the enabled-row reverse-lookup index required by the approved design. It
supports `publishersByDistributionPlatform` and
`publisherCountByDistributionPlatform` (both of which filter `platform = $1 AND
enabled`), and its `(platform, publisher_id)` column order matches the lookup
shape and the tie-breaker column. The `WHERE enabled` partial predicate follows
the established repository partial-index convention and keeps the index
proportional to the enabled population.

The composite primary key already provides the `(publisher_id, platform)` index
used by `Publisher.distributionPlatforms`, so no additional index is needed for
the forward lookup. **No further index may be added unless the implementation
demonstrates a concrete need**, recorded with the query shape that requires it.

## 7. Required behaviour

### 7.1 Activation lifecycle

The supported domain write path exposes exactly two logical operations for a
single (publisher, platform) target - **enable** and **disable** - plus their
linked-group forms (section 7.2). Both run inside one transaction (section 7.5).

`T` below denotes the transaction timestamp (`CURRENT_TIMESTAMP`), identical for
every row written by one logical transition.

| Transition | Row write | `activation_id` | `enabled_at` | `disabled_at` | `updated_at` | `enabled` | Idempotent |
|---|---|---|---|---|---|---|---|
| **ABSENT -> ENABLED** | `INSERT` | newly generated `Uuid::new_v4()` | `T` | `NULL` | `T` (`created_at` also `T`) | `true` | n/a (first write); a repeat request becomes ENABLED -> ENABLED |
| **ENABLED -> ENABLED** | **no write at all** | unchanged | unchanged | unchanged | **unchanged** | `true` | **yes** - successful no-op returning the current row; no new activation, no timestamp movement |
| **ENABLED -> DISABLED** | `UPDATE` | **retained unchanged** (it identifies the activation being ended) | **retained unchanged** (it records when that activation began) | `T` | `T` | `false` | n/a; a repeat request becomes DISABLED -> DISABLED |
| **DISABLED -> DISABLED** | **no write at all** | unchanged | unchanged | unchanged | **unchanged** | `false` | **yes** - successful no-op returning the current row |
| **DISABLED -> ENABLED** | `UPDATE` | **newly generated `Uuid::new_v4()`** (a genuine re-enable is a new activation) | `T` | set to `NULL` | `T` | `true` | n/a; a repeat request becomes ENABLED -> ENABLED |
| **ABSENT -> DISABLED** (disable requested for an assignment that does not exist) | **no write at all; no row created** | n/a | n/a | n/a | n/a | n/a | **yes** - successful no-op |

Binding semantics:

- **disabled rows are retained, never deleted**; there is no supported delete
  path for an assignment row in BE-02;
- **an actual disabled-to-enabled transition generates a new `activation_id`**;
- **repeated enabling of an already enabled assignment must not create a new
  activation**, and must not move `updated_at`;
- **linked platforms enabled in one logical operation share one activation
  identity** (section 7.2);
- both no-op transitions return success, not an error, and return the current
  persisted row.

### 7.2 Linked-platform normalization

`OAPEN` and `DOAB` are separate `DistributionPlatform` values that are, for the
initial implementation, a **linked selection** in the group `OAPEN_DOAB`. **The
backend owns the rule.** `thoth-app` will later consume backend linkage metadata
(section 9.1) and must maintain no duplicate rule; no app change belongs in
BE-02.

The linked-group contract:

1. enabling `OAPEN` through the supported domain operation results in both
   `OAPEN` and `DOAB` enabled;
2. enabling `DOAB` through the supported domain operation does the same;
3. disabling either through the supported domain operation results in both
   disabled;
4. a linked enable is performed in **one** transaction;
5. every row written by one linked enable carries the **same** newly generated
   `activation_id`;
6. every row written by one linked transition carries **identical** timestamps,
   guaranteed by using the transaction timestamp `T`;
7. failure updating either row rolls back the **complete** linked operation -
   partial application is impossible;
8. repeated requests do not create unnecessary new activations;
9. **no supported domain write path may create a one-sided enabled OAPEN/DOAB
   state.**

**Group-level evaluation (binding).** A linked operation is evaluated against
the state of the whole group, not each member independently:

- **Linked enable.** If *every* member of the group is already `enabled`, the
  operation is a complete no-op: no write, no new `activation_id`, no timestamp
  movement. Otherwise the operation is a **group activation**: one new
  `activation_id` is generated and *every* member row is written with that
  `activation_id`, `enabled = true`, `enabled_at = T`, `disabled_at = NULL`,
  `updated_at = T` - including any member that was already enabled, whose
  previous `activation_id` is replaced. This is what makes requirement 5
  unconditional, and it repairs any pre-existing one-sided or
  split-activation state (for example one introduced by `MIG-01` or by direct
  SQL) rather than propagating it.
- **Linked disable.** If *no* member of the group is currently `enabled`, the
  operation is a complete no-op. Otherwise every member row that exists is
  written with `enabled = false`, `disabled_at = T`, `updated_at = T`, retaining
  its `activation_id` and `enabled_at`. Members with no row are left absent; no
  row is created by a disable.

Non-linked platforms form a singleton group, so the same rules reduce exactly to
the section 7.1 table.

#### 7.2.1 What "cannot be created" means at the enforcement boundary

The one-sided-enabled prohibition is enforced **through supported backend/domain
behaviour**, in a single transaction, exactly as the approved architecture
requires. Concretely:

- every supported write path for assignment state goes through the group-aware
  transition functions above;
- BE-02 exposes **no** mutation, resolver, CRUD implementation or public API
  that can write an assignment row outside those functions;
- the operation is transactional, so a failure on either row rolls back both;
- the per-publisher lock (section 7.5) serialises concurrent transitions, so
  interleaving cannot produce a one-sided result.

A one-sided enabled state therefore cannot arise from any supported domain
behaviour. It remains physically representable by direct SQL executed outside
the application (for example by a database administrator), which is not a
supported path and is out of BE-02's scope; the group-level enable rule above
additionally *repairs* such a state on the next supported linked enable.

**No database-level cross-row constraint is added.** A cross-row invariant is
not expressible as a PostgreSQL `CHECK`; enforcing it in the database would
require a trigger or an exclusion-constraint mechanism. That would be a new
enforcement subsystem not present in the current architecture, would duplicate
code-owned linkage metadata in the schema (ADR-0004 section 5 makes descriptors
code-owned), and would require a migration whenever a linked group changed. The
approved architecture asks for a normal transactional domain rule, and BE-02
implements exactly that.

#### 7.2.2 Destination is not adapter

`OAPEN` and `DOAB` currently map to **one** operational delivery adapter,
`OAPEN_DOAB_SWORD`. BE-02 must preserve `destination != adapter/feed profile`.
BE-02 creates no delivery job and performs no upload; the shared adapter
identity is internal descriptor metadata only (section 8).

### 7.3 `OCLC_KB` and `EX_LIBRIS_KB`

These are **independent publisher assignments**. They are **not** a linked
selection group. Both currently consume the shared feed profile
`OCLC_KBART_PUBLIC`.

BE-02 must preserve:

- each may be independently enabled and disabled;
- they do **not** share activation identities merely because they share a feed
  profile - each is its own singleton group and gets its own `activation_id`;
- enabling one must not implicitly enable the other;
- enabling both does not create two publisher-level KBART feed states - BE-02
  records **destination assignment state only** and holds no feed state at all,
  so no duplicate feed state is representable;
- neither creates an uploader job (BE-02 creates no jobs at all);
- the descriptor layer represents the shared mechanism identity
  (`OCLC_KBART_PUBLIC`) without collapsing the two destination values.

### 7.4 `JISC_NBK`

`JISC_NBK` is part of the 17-value enum but is initially **inactive**,
**non-assignable** and **job-free**. BE-02 represents and enforces that as
follows:

- it appears as a stable platform option because it is part of the enum:
  `distributionPlatformOptions` returns it like any other value;
- its public option metadata makes the state explicit: `assignable` is `false`
  (section 9.1);
- **the supported domain enable operation rejects it before any write**: the
  transition function checks the descriptor's assignment availability first and
  returns the dedicated error of section 10 without opening or writing in a
  transaction. A linked enable whose group contains a non-assignable member is
  rejected in the same way, as a whole;
- it creates no distribution job and no delivery (BE-02 creates neither for any
  platform);
- **no BE-02 path silently makes it assignable** - assignability is read from
  the single code-owned descriptor and is not parameterisable, configurable at
  runtime, or overridable by input.

`JISC_NBK_MARC_S3` must **not** be implemented. It is future, separately
approved work. The adapter/feed-profile identity may be recorded in the internal
descriptor as an inactive mechanism identity (ADR-0004 section 4.3), which is
metadata only.

Enforcement is **not** placed in a database constraint. Assignability is
code-owned descriptor metadata; a database check would duplicate it and would
require a migration to activate `JISC_NBK` later.

### 7.5 Transaction boundaries and concurrency

- Every state transition (single or linked) executes inside **one**
  `connection.transaction(...)`.
- The transaction first takes a **row lock on the publisher**:
  `SELECT ... FROM publisher WHERE publisher_id = $1 FOR UPDATE`. This
  serialises all concurrent transitions for a given publisher, covers linked
  groups without a second lock ordering problem, and is the lock BE-03 will also
  need for its configuration mutation. It uses only existing repository
  primitives (`thoth-api/AGENTS.md` section 5 explicitly lists row locks) and
  introduces no new locking subsystem.
- Assignment writes use `INSERT ... ON CONFLICT (publisher_id, platform) DO
  UPDATE ...` so that the absent/present cases are handled by one statement and
  a concurrent first-arrival cannot produce a duplicate-key failure.
- Reads used to decide the transition are performed **inside** the transaction,
  after the lock is taken, so the decision is made against a stable snapshot.

**Concurrent contradictory or duplicate transitions.** Two writers targeting the
same publisher serialise on the publisher row lock. The second writer's decision
is made against the first writer's committed state, so:

- two concurrent *enable* requests for the same absent assignment produce
  exactly one activation: the first inserts and generates an `activation_id`;
  the second observes `ENABLED` and is a no-op;
- concurrent *enable* and *disable* requests both succeed, and the final state
  is that of the later-committing transaction (last writer wins) - no lost
  update, no torn linked pair, no orphan activation;
- two concurrent *linked* enables produce exactly one group activation for the
  same reason.

Transitions targeting **different** publishers do not contend.

BE-03 later owns the protected service-configuration mutation and the
optimistic-concurrency (`expectedUpdatedAt`) public API. BE-02 provides the
sound domain persistence and normalization foundation without absorbing that
public mutation surface.

## 8. Code-owned descriptors

Descriptors are **code-owned metadata, not database rows**. No descriptor table
may be created, and no second destination registry may be introduced.

**Every one of the 17 `DistributionPlatform` variants must have exactly one
descriptor**, and exhaustiveness must be guaranteed **at compile time with no
runtime fallback**.

**Required implementation shape** (the exact signatures may follow repository
conventions, but the properties are binding):

```rust
pub struct DistributionPlatformDescriptor {
    pub platform: DistributionPlatform,
    pub display_label: &'static str,
    pub linked_group: Option<DistributionPlatformGroup>,
    pub back_catalogue_behaviour: BackCatalogueBehaviour,
    pub assignment_availability: AssignmentAvailability,
    pub mechanism_readiness: MechanismReadiness,
    pub adapter_profile: DistributionAdapterProfile,
}

impl DistributionPlatform {
    pub const ALL: [DistributionPlatform; 17] = [ /* canonical order */ ];
    pub const fn descriptor(self) -> &'static DistributionPlatformDescriptor {
        match self { /* one arm per variant; no wildcard */ }
    }
}
```

Required properties:

- `descriptor` is implemented as an **exhaustive `match self` with one arm per
  variant and no `_` arm**, so adding an eighteenth variant fails to compile.
  An equivalent static construction that provides the same compile-time
  exhaustiveness guarantee is acceptable; a `HashMap`, a lazily initialised
  registry, a lookup returning `Option`, or any construction with a fallback arm
  is not;
- descriptors are `&'static` data with no allocation;
- there is exactly one canonical descriptor definition; no consumer may
  duplicate any descriptor field;
- `DistributionPlatform::ALL` is the canonical ADR-0004 section 4.1 order and is
  the single source of iteration order for `distributionPlatformOptions`.

## 9. Public GraphQL contract

All four surfaces are **public**, consistent with the current architecture in

### 9.1 `distributionPlatformOptions`

```graphql

```

Backend-owned descriptor metadata, derived entirely from the code-owned
descriptors. It takes **no arguments**, performs **no database access**, and

```graphql
type DistributionPlatformOption {

  displayLabel: String!
  linkedGroup: DistributionPlatformGroup
  backCatalogueBehaviour: BackCatalogueBehaviour!
```

Implemented with `#[derive(juniper::GraphQLObject)]` (precedent:

Field semantics:

- `platform` - the stable platform identity;
- `displayLabel` - the stable display label from the descriptor table;
- `linkedGroup` - **nullable**; non-null exactly for `OAPEN` and `DOAB`, both

**Not exposed** (binding):

- mechanism readiness - internal operational state; `assignable` already carries

- any credential, endpoint, host, bucket, account or secret operational

- update or withdrawal expectations - not needed by any BE-02 consumer.

Ordering is the canonical `DistributionPlatform::ALL` order (ADR-0004 section
4.1) and is deterministic and stable.

### 9.2 `Publisher.distributionPlatforms`

```graphql
type Publisher {
  # ... existing fields unchanged ...
  distributionPlatforms: [PublisherDistributionPlatformAssignment!]!
}

type PublisherDistributionPlatformAssignment {
  platform: DistributionPlatform!
  enabledAt: Timestamp!
}
```

Added to the existing explicit `#[juniper::graphql_object] impl Publisher` in
`thoth-api/src/graphql/model.rs`, following the `Publisher.imprints` /
`Publisher.contacts` precedent.

Binding requirements:

- returns **enabled assignments only** (`WHERE publisher_id = $1 AND enabled`);
- **disabled historical rows must never be exposed** as active publisher
  platforms;
- deterministic ordering: `ORDER BY platform ASC`, which is PostgreSQL enum
  declaration order and therefore the canonical inventory order. No tie is
  possible because `(publisher_id, platform)` is the primary key;
- returns an empty list, successfully, when the publisher has no enabled
  assignment;
- `enabledAt` is non-null: the section 6.1 check constraint guarantees an
  enabled row has an `enabled_at`;
- `activationId`, `disabledAt`, `enabled`, `createdAt` and `updatedAt` are
  **not** exposed. `activationId` is an internal correlation identity for BE-04
  job deduplication; `disabledAt` would expose historical state this field
  explicitly must not show;
- **no package data may become public through this field** - the assignment type
  contains no package or capability field, and the `Publisher` object still
  exposes no `subscriptionPackage` or `capabilities`;
- the field takes no `limit`/`offset` arguments: the result is bounded above by
  17 rows by construction.

### 9.3 `publishersByDistributionPlatform`

```graphql
publishersByDistributionPlatform(
  platform: DistributionPlatform!
  limit: Int = 100
  offset: Int = 0
  order: PublisherOrderBy = { field: PUBLISHER_NAME, direction: ASC }
): [Publisher!]!
```

Binding requirements:

- accepts the stable GraphQL platform enum (not a string). An invalid enum value
  fails Juniper input coercion before the resolver runs;
- returns publishers with an **enabled** assignment for that platform only:
  `INNER JOIN publisher_distribution_platform ON publisher_id WHERE platform =
  $1 AND enabled`;
- uses the repository's existing offset/limit pagination style, argument names,
  defaults and descriptions;
- **paginates deterministically.** Ordering is the requested `PublisherOrderBy`
  field and direction, **always** followed by `publisher_id ASC` as tie-breaker,
  using the existing `apply_directional_order!` secondary-expression form. The
  tie-breaker is mandatory and is not optional or configurable. (Note that the
  existing `Publisher::all` has no tie-breaker; BE-02 must not copy that
  defect);
- returns an **empty successful page** when no publisher has an enabled
  assignment for the requested platform - never an error, never a null;
- **must not broaden scope on failure**: a database error propagates as an
  error; it never degrades to "all publishers" or to an unfiltered list;
- **must not infer assignments** from locations, `LocationPlatform` values,
  packages, dissemination configuration, workflow configuration or legacy
  environment variables. The only source is
  `publisher_distribution_platform.enabled`;
- returns at most one row per publisher (guaranteed by the primary key).

### 9.4 `publisherCountByDistributionPlatform`

```graphql
publisherCountByDistributionPlatform(platform: DistributionPlatform!): Int!
```

Binding requirements:

- counts **exactly the same enabled-assignment population** as section 9.3,
  using the same filter predicate;
- returns `0` when there are no enabled assignments;
- **never uses a fallback source** and never falls back to a total publisher
  count;
- returns `i32` using the established `Crud::count` conversion idiom;
- semantics for `JISC_NBK` are the ordinary semantics with **no special
  casing**: because no supported path can enable `JISC_NBK`, the count is `0`
  and the reverse lookup is empty. The query must not hard-code `0`, must not
  error, and must not filter on assignability - it reports the actual persisted
  enabled population, which is what makes it agree with section 9.3 by
  construction.

Count and reverse-lookup agreement must be proven by test (section 18).

## 10. Failure semantics and fail-closed behaviour

Two binding principles carry through BE-02 and into every later consumer:

```text
configuration failure fails closed
an empty assignment set does not broaden processing
```

Even though dissemination cutover is later work, **no BE-02 query or domain
helper may encode fallback semantics that downstream code could interpret as
"all publishers"**. There is no "if no assignments, return everything" path, no
`unwrap_or(all)`, no default-open branch and no legacy-environment fallback
inside Thoth.

| Condition | Required behaviour |
|---|---|
| Database error in any query or transition | propagate as `ThothError::DatabaseError` -> GraphQL error. Never return a partial, unfiltered or broadened result |
| Invalid state transition | not representable: the six transitions of section 7.1 are total over `{ABSENT, ENABLED, DISABLED} x {enable, disable}`. Any state that violates the row check constraint is rejected by the database |
| Attempt to enable `JISC_NBK` (directly or as part of a group) | rejected **before any write**, with a dedicated stable error variant added to `thoth-errors`, materially `ThothError::DistributionPlatformNotAssignable(String)` carrying the stable platform code. No transaction is opened; no row is created or modified |
| Linked OAPEN/DOAB transaction failure on either row | the complete transaction rolls back; neither row is written; the error propagates. No one-sided state results |
| Empty reverse lookup | successful empty list |
| No assignments for a publisher | successful empty list from `Publisher.distributionPlatforms` |
| Invalid GraphQL enum input | Juniper input-coercion failure before the resolver runs; no query executes; no default platform is substituted |
| Stale or disabled rows | excluded from every public read by the `enabled` predicate; retained in storage; never treated as active |
| Unknown database enum label reaching Rust | Diesel deserialization error -> `ThothError::DatabaseError`. No fallback variant exists to absorb it |

### 13.1 Empty-database evidence

On a **disposable** PostgreSQL database only:

1. apply the complete migration chain with `cargo run migrate`;
2. verify the resulting BE-02 schema: the `distribution_platform` type exists

### 13.3 Locking and downtime

The implementation must assess the **actual** DDL operations and the PostgreSQL
locks they take:

- `CREATE TYPE` - no lock on existing tables;
- `CREATE TABLE` / `ALTER TABLE ... ADD CONSTRAINT` on the **new, empty** table -

- `CREATE INDEX` on the new empty table - locks only the new table;
- `CREATE TRIGGER` on the new table - locks only the new table;
- no existing table is altered, so no lock is taken on `publisher` or any other

The expected conclusion is that the migration takes no lock on any populated
table. That conclusion must be **stated as a reviewed assessment of the actual
DDL**, and the report **must not claim a production execution duration**: no
production evidence exists and **no production database access is authorized**.

### 18.3 Assignment lifecycle (database-backed)

- ABSENT -> ENABLED inserts one row with a new `activation_id`, `enabled = true`,
  `enabled_at` set, `disabled_at` null;
- ENABLED -> ENABLED is idempotent: no new `activation_id`, unchanged
  `enabled_at`, **unchanged `updated_at`**, still exactly one row;
- ENABLED -> DISABLED sets `enabled = false` and `disabled_at`, retains
  `activation_id` and `enabled_at`, and **retains the row**;
- DISABLED -> DISABLED is idempotent with no timestamp movement;
- DISABLED -> ENABLED sets a **different** `activation_id` from the previous
  activation, sets a new `enabled_at`, and clears `disabled_at`;
- ABSENT -> DISABLED creates no row and succeeds;
- timestamps follow the section 7.1 state machine exactly;
- the row check constraint rejects a directly attempted invalid combination
  (enabled with null `activation_id`; enabled with null `enabled_at`; disabled
  with null `disabled_at`).

### 18.4 Linked OAPEN/DOAB (database-backed)

- enabling `OAPEN` enables both `OAPEN` and `DOAB`;
- enabling `DOAB` enables both;
- disabling either disables both;
- one linked enable writes the **same** `activation_id` to both rows and
  **identical** `enabled_at` values;
- a linked enable of an already fully enabled group creates no new activation
  and moves no timestamp;
- a linked enable of a partially enabled group produces one new shared
  activation across both rows (state repair);
- the linked write is atomic: an injected failure on the second row rolls back
  the first, leaving the pre-transaction state intact;
- after any sequence of supported linked operations, no one-sided enabled state
  exists;
- repeated and concurrent linked transitions follow the specified idempotency
  and locking behaviour: two concurrent linked enables of the same absent group
  produce exactly one shared activation across both rows.

## 19. Stop conditions

The implementing agent must stop and report `BLOCKED` if:

- ADR-0004 is not repository-authoritative at the implementation base, or the
  live inventory differs from the 17-value inventory of section 5.0;
- ADR-0005 is not authoritative on the then-current `develop`;
- ADR-0003 Architecture A would need to change, or implementation would require
  `diesel_cli`, a root `diesel.toml`, `diesel print-schema` as canonical writer,
  or a schema synchronizer;
- a low-level choice would actually change approved architecture rather than
  follow repository convention;
- BE-02 cannot prevent supported one-sided OAPEN/DOAB state without adding an
  architectural mechanism not already approved (for example a trigger subsystem
  or an exclusion-constraint framework);
- a composite primary key proves incompatible with the pinned Diesel version's
  usable query API for the specified queries;
- the public/private API boundary conflicts with current approved architecture;
- BE-02 would need to absorb BE-03, BE-04, MIG-01, DIS-01, EXP-01, OAI-01 or
  production work;
- production credentials, production data access or a shared service would be
  required;
- the migration proves unexpectedly destructive or long-locking on a populated
  table;
- representative populated migration evidence cannot be produced;
- a required test path cannot run against a disposable database;
- the current repository state materially contradicts this specification's
  premise, or the exact implementation base moves after branching;
- a cross-programme decision involving Metrics or another programme is required;
- an inventory or architecture change appears necessary - escalate to the CTO
  rather than changing it in BE-02;
- implementation cannot be completed without an unrelated change;
- removal of the assignment foundation would be proposed as rollback - use
  `BLOCKED - ROLLBACK REQUIRES ADR CHANGE`.

When blocked, identify the **exact CTO decision required**. Do not resolve
architectural conflicts by inference.

## 23. Lifecycle boundary

These are different events, and none of them grants any later one:

```text
specification authored
specification independently reviewed
specification approved by CTO
implementation explicitly authorized
implementation completed
implementation independently reviewed
CTO merge authorization
merge
production activation
```

Authoring this specification grants none of the later events.

Under ADR-0005, live review, authorization and merge evidence is the **GitHub
pull-request record**. No repository commit is created to copy review
identifiers, approval identifiers, merge-authorization identifiers, merge SHAs,
timestamps or completion state into Markdown. No approval-state-only commit is
created. No post-merge pull request is opened merely to record that a pull
request merged. A material post-merge correction still requires its own bounded
task and pull request.
