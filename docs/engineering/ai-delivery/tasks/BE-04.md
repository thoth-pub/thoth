## 1. Objective

Add durable **publisher back-catalogue distribution jobs** to `thoth-api`: the
`distribution_job`, `distribution_job_target` and `distribution_job_attempt`
relations, a deterministic deduplication identity derived from BE-02's activation
semantics, atomic job creation inside BE-03's existing single service-
configuration write transaction, a complete claim/lease/retry/cancel state
machine enforced by PostgreSQL, a narrow least-privilege machine authorization
for dissemination workers, the three worker operations the approved design names,
and an **additive** job-aware extension of BE-03's superuser staff report.

BE-04 owns **durable job state only**. It performs no dissemination, produces no
file, feed or deposit, and contacts no external platform. `thoth-dissemination`
remains the execution engine and consumes these jobs under its own separately
specified DIS-02 task.

Automatic job creation is **OFF by default** and merging BE-04 activates
nothing.

### 1.1 Risk rationale

BE-04 is HIGH risk because it introduces, in one task:

1. job claiming, retries, leases and concurrency (`risk-classification.md` HIGH);
2. idempotency and deduplication (HIGH);
3. a machine/service role and machine-to-machine authorization (HIGH);
4. a database migration whose tables are new but whose creation path extends a
   transaction that already writes populated tables (HIGH);
5. an extension of the one authoritative production configuration write path
   BE-03 fixed, so a defect here can corrupt desired-state writes that BE-03
   made atomic;
6. a public GraphQL contract change adding write operations reachable by a
   non-superuser identity for the first time in this programme;
7. durable state whose deletion would destroy operational audit evidence;
8. an activation switch whose future `OFF -> ON` transition can enqueue an entire
   publisher back catalogue.

### 1.2 Required HIGH-risk controls

1. an approved bounded specification (this document) that is
   repository-authoritative on `develop` before implementation;
2. separate explicit CTO implementation authorization bound to a freshly
   verified exact `develop` head;
3. one bounded branch and one bounded pull request;
4. fresh independent exact-head review by an agent/model that did not implement,
   author or materially assist with BE-04;
5. explicit CTO merge authorization bound to that exact implementation head;
6. real PostgreSQL concurrency tests, not mocked sequential substitutes, wherever
   correctness depends on database locking;
7. deployment, environment migration execution, production migration execution,
   worker credential provisioning, worker deployment and automatic-job-creation
   activation all remain separately gated after merge.

### 2.2 Verified current behaviour

Re-derived from the merged code at the authoring base. Each item is the evidence
a later design decision rests on.

1. **The single canonical service-configuration write coordinator exists and is
   exactly one function.**
   `thoth_api::model::publisher_service_configuration::crud::replace_publisher_service_configuration(db: &PgPool, write_context: &ServiceConfigurationWriteContext<'_>, data: &ReplacePublisherServiceConfigurationInput) -> ThothResult<PublisherServiceConfiguration>`
   acquires one pooled connection and calls
   `connection.transaction(|connection| replace_in_transaction(...))`. The
   private `replace_in_transaction` is the whole transaction body, and it is
   deliberately not a second entry point. Its only production caller is
   `graphql::mutation::replace_service_configuration`, which authorizes first and
   supplies the audit provenance as a parameter. The coordinator itself makes
   **no** authorization decision.
2. **The coordinator's merged transaction boundary and step order** are, in
   `replace_in_transaction`:
   1. `lock_publisher(connection, publisher_id)` — `SELECT publisher_id FROM
      publisher WHERE publisher_id = $1 FOR UPDATE`, the first statement; an
      absent row returns `ThothError::EntityNotFound` with no write;
   2. read the publisher row and `enabled_platforms(...)` under that lock;
      `previous_token = current.service_configuration_updated_at`;
   3. staleness check against `data.expected_updated_at`, returning
      `ThothError::StalePublisherServiceConfiguration` before any validation or
      lifecycle call;
   4. `normalize_requested_platforms(...)` — deduplicate and close under
      `DistributionPlatform::linked_members`, in canonical
      `DistributionPlatform::ALL` order;
   5. validate `is_assignable()` for the **whole** normalized set, returning
      `ThothError::DistributionPlatformNotAssignable` before the first lifecycle
      call;
   6. `package_changed = current.subscription_package != data.subscription_package`
      — comparison only, no write;
   7. `PublisherDistributionPlatform::enable_on(...)` once per desired linked
      group representative, **unconditionally**, accumulating
      `lifecycle_changed |= outcome.changed()`; then `disable_on(...)` once per
      undesired currently-enabled group representative, accumulating the same;
   8. if neither the package nor any lifecycle call changed anything, return
      early — no publisher `UPDATE`, no token movement, no audit row, and
      therefore neither publisher trigger fires;
   9. **exactly one** `diesel::update(publisher::table ...)` carrying
      `service_configuration_updated_at` always and `subscription_package` only
      when `package_changed`, with
      `GREATEST(CURRENT_TIMESTAMP, service_configuration_updated_at + interval '1 microsecond')`
      making the token strictly increasing per publisher, and
      `.returning(publisher::all_columns)`;
   10. re-read `enabled_platforms(...)`, build the bounded three-key
       `CanonicalServiceConfigurationState` before/after values, and insert
       **exactly one** `publisher_service_configuration_history` row carrying
       the caller-supplied `source` and `actor`;
   11. commit and return `PublisherServiceConfiguration::new(updated)`.
   BE-03 section 7.9 states explicitly that BE-04 extends **this** transaction
   between steps 9 and 12 of its own numbering, and that BE-03 deliberately added
   no hook, callback, event or placeholder for it.
3. **Publisher lock ordering.** `lock_publisher` is the only `FOR UPDATE` in
   `thoth-api/src`. The coordinator and both BE-02 connection-scoped primitives
   take it on the same single row; re-taking it inside the coordinator's
   transaction is a harmless no-op. The application-level order is therefore
   `publisher` row first, everything else after. The one other explicit lock in
   the crate is `pg_advisory_xact_lock(hashtext($1))` in
   `model/work_relation/crud.rs`, which is unrelated to publisher configuration.
4. **Assignment lock/update ordering.** `enable_on` and `disable_on` each call
   `lock_publisher` first, then read `member_rows(...)`, then write. `enable_on`
   writes one `INSERT ... ON CONFLICT (publisher_id, platform) DO UPDATE` per
   linked member with one shared `activation_id = Uuid::new_v4()` and one shared
   `transition_at = CURRENT_TIMESTAMP` (transaction-scoped). `disable_on` writes
   one set-based `UPDATE ... WHERE platform = ANY(enabled_members)` setting
   `enabled = false` and `disabled_at`.
5. **Package handling.** The package write is deferred to the coordinator's
   single publisher `UPDATE`, written directly rather than through the shared
   `Crud::update` macro, so the mutation writes **no** `publisher_history` row.
6. **Linked-platform normalization.** `DistributionPlatformGroup::OapenDoab` is
   the only linked group. `linked_members()` returns the group's members in
   canonical order, or `vec![self]` for an unlinked destination.
   `is_normalized_fully_enabled` is a complete no-op only when every member row
   exists, is enabled, has `disabled_at IS NULL`, and shares one `activation_id`
   **and** one `enabled_at`; any other state is repaired to one new shared
   activation.
7. **`service_configuration_updated_at` handling** is item 2.9 above. It is a
   `publisher` column, `timestamptz DEFAULT CURRENT_TIMESTAMP NOT NULL`.
8. **Audit write** is item 2.10 above. `publisher_service_configuration_history`
   is append-only, has no `updated_at` and no `diesel_manage_updated_at` trigger,
   carries `CHECK (actor ~ '[^[:space:]]')`, an `ON DELETE CASCADE` foreign key
   to `publisher`, and a `(publisher_id, created_at DESC, id DESC)` composite
   index. The `before_state`/`after_state` JSON key set is exactly
   `subscriptionPackage`, `enabledDistributionPlatforms`, `configurationVersion`
   and BE-03 section 8.2 forbids widening it.
9. **Source handling.** `PublisherServiceConfigurationSource` is a closed
   PostgreSQL enum with exactly `SUPERUSER_API` and `MIGRATION_BACKFILL`, no
   `OTHER`, no `UNKNOWN`, no `Default`. `SUPERUSER_API` is the only value any
   merged execution path writes; `MIGRATION_BACKFILL` exists so the separately
   approved MIG-01 backfill has a coherent value, and no merged path emits it.
   `source` and `actor` form one contract, supplied by the caller as
   `ServiceConfigurationWriteContext`, never inferred from ambient state and
   never a GraphQL input.
10. **Existing no-op semantics.** A true no-op requires the package unchanged
    **and** every lifecycle call reporting `AssignmentLifecycleOutcome::Unchanged`.
    Membership equality alone does not imply a no-op, because a split linked pair
    has equal membership and is repaired.
11. **Existing publisher UPDATE triggers — there are two.**
    `set_updated_at BEFORE UPDATE ON public.publisher FOR EACH ROW EXECUTE
    FUNCTION public.diesel_set_updated_at()`, and
    `set_work_updated_at_with_relations AFTER UPDATE ON public.publisher FOR EACH
    ROW EXECUTE FUNCTION public.publisher_work_updated_at_with_relations()`.
12. **`set_work_updated_at_with_relations` cascade.** When `NEW IS DISTINCT FROM
    OLD`, `publisher_work_updated_at_with_relations()` executes exactly one
    set-based statement:

    ```sql
    UPDATE work
    SET updated_at_with_relations = current_timestamp
    FROM imprint
    WHERE work.imprint_id = imprint.imprint_id
      AND imprint.publisher_id = NEW.publisher_id;
    ```

    `work.updated_at_with_relations` is a public downstream freshness signal
    consumed by `thoth-export-server`'s Redis-cached record path, so refreshing it
    invalidates that publisher's cached export output.
13. **Real transaction write footprint.** A committed configuration change
    therefore writes one publisher row, plus bounded configuration and audit rows,
    plus **N related work rows**, where N is the number of works belonging to
    that publisher through its imprints. The publisher `FOR UPDATE` lock is held
    while the trigger's set-based `UPDATE` runs, so the transaction's row-lock
    footprint and duration grow with catalogue size. It is **wrong** to describe
    the transaction as touching one publisher row.
14. **BE-02 activation model.** `publisher_distribution_platform` has composite
    primary key `(publisher_id, platform)`, columns `enabled boolean NOT NULL`,
    `activation_id uuid NOT NULL`, `enabled_at timestamptz NOT NULL`,
    `disabled_at timestamptz`, `created_at`, `updated_at`; an `ON DELETE CASCADE`
    foreign key to `publisher`; a named
    `publisher_distribution_platform_enabled_state_check` enforcing
    `enabled == (disabled_at IS NULL)`; a partial
    `(platform, publisher_id) WHERE enabled` index; and a `set_updated_at`
    trigger. **A fresh `activation_id` is minted on every insert, re-enable and
    repair, shared across all members of a linked group.** Disabled rows are
    retained, never deleted. `activation_id` is deliberately not exposed through
    any BE-02 public contract.
15. **`AssignmentLifecycleOutcome`** is a `pub(crate)`, `#[must_use]` two-variant
    enum `Unchanged | Changed` with `changed() -> bool`. BE-03 section 7.9
    records that it is deliberately the minimum BE-03 needs and that **BE-04
    extends it under its own specification if it needs more**.
16. **Platform descriptors and back-catalogue behaviour classification** are
    code-owned `&'static DistributionPlatformDescriptor` values reached through a
    compile-time-exhaustive `descriptor()` match. The exhaustive classification
    at this base is:

    | `BackCatalogueBehaviour` | Destinations |
    |---|---|
    | `AutomaticPush` | `INTERNET_ARCHIVE`, `OAPEN`, `DOAB`, `CAMBRIDGE_UNIVERSITY_LIBRARY`, `CROSSREF`, `FIGSHARE`, `ZENODO`, `PROJECT_MUSE`, `JSTOR`, `EBSCO_HOST`, `PROQUEST_EBOOK_CENTRAL`, `GOOGLE_PLAY`, `BKCI`, `JISC_NBK` |
    | `PullFeed` | `OCLC_KB`, `EX_LIBRIS_KB` |
    | `Manual` | `SCIENCE_OPEN` |

    `JISC_NBK` is the only `NonAssignable`/`Inactive` destination, so it can never
    be enabled and can therefore never produce a job target. `OCLC_KB` and
    `EX_LIBRIS_KB` share `Profile::OclcKbartPublic` but are independently
    assignable with no linked group. This classification is read from descriptors,
    never inferred from names.
17. **There is no existing durable job machinery of any kind in this
    repository.** A search of `thoth-api/`, `thoth-api-server/`, `thoth-client/`,
    `thoth-errors/`, `thoth-export-server/` and `src/` for job tables, queues,
    claims, leases, claim tokens, `SKIP LOCKED`, idempotency or deduplication
    keys, retry state machines, cancellation primitives and machine worker APIs
    finds **none**. The only concurrency primitives present are the publisher row
    lock (item 3) and the `work_relation` transaction advisory lock. BE-04 is the
    first durable job machinery in this repository.
18. **There is no existing machine/service-worker authorization convention.**
    `policy.rs` defines `pub(crate) enum Role { Superuser, PublisherAdmin,
    PublisherUser, WorkLifecycle, CdnWrite }` over ZITADEL project roles on
    `IntrospectedUser`. `Superuser` is checked **unscoped** by `is_superuser()`
    (key presence in `project_roles`); every other role is checked **scoped to a
    ZITADEL organisation id** by `has_role_for_org`. `require_role_for_publisher`
    short-circuits for superusers and otherwise tests exactly the one requested
    role; **there is no role inheritance anywhere in `policy.rs`**.
    `publisher_org_ids()` collects org ids from every scoped role **except**
    `SUPERUSER`. `PublisherPermissions` reports `publisher_admin`,
    `work_lifecycle` and `cdn_write` as independent booleans. The unscoped-role
    check pattern therefore already exists, applied to exactly one role.
19. **Role provisioning.** `src/bin/commands/zitadel.rs` `setup` provisions
    exactly `SUPERUSER`, `PUBLISHER_ADMIN` and `PUBLISHER_USER`. `WORK_LIFECYCLE`
    and `CDN_WRITE` exist in `policy.rs` but are **already absent** from that
    list. That pre-existing gap is recorded here as an observed fact and is
    **not** BE-04's to repair.
20. **The repository's OFF-by-default runtime switch convention** is the merged
    mutation-guard mode: a `clap::Arg` in `src/bin/arguments/mod.rs` with
    `.long(...)`, `.value_name("THOTH_GRAPHQL_MUTATION_GUARD_MODE")`,
    `.env(...)`, `.default_value("OFF")`, `.value_parser([...])` and
    `.num_args(1)`; a typed Rust enum with `FromStr`; a `start_server(...)`
    parameter; `.app_data(Data::new(mutation_guard_mode))`; and per-request
    extraction in the `/graphql` handler. The value is read once at process
    start and there is no reload path. `MutationGuardMode` is deliberately
    **not** on `Context`, because the guard runs before execution.
21. **BE-03's merged GraphQL surface.** Queries
    `publisherServiceConfiguration(publisherId: Uuid!): PublisherServiceConfiguration!`
    (superuser, or exactly `PUBLISHER_USER` for that publisher, via
    `load_current` then `require_publisher_for`),
    `publisherServiceConfigurations(publishers: [Uuid!] = [], packages:
    [ThothPackage!] = [], enabledPlatforms: [DistributionPlatform!] = [], limit:
    Int = 100, offset: Int = 0, order: PublisherOrderBy = ...):
    [PublisherServiceConfigurationSummary!]!` and
    `publisherServiceConfigurationCount(...): Int!` (both `require_superuser()`);
    mutation `replacePublisherServiceConfiguration(data:
    ReplacePublisherServiceConfigurationInput!): PublisherServiceConfiguration!`
    (`require_superuser()`). Object types `PublisherServiceConfiguration`
    (`publisher`, `subscriptionPackage`, `effectiveCapabilities`,
    `enabledDistributionPlatforms`, `updatedAt`),
    `PublisherServiceConfigurationSummary` (`configuration`, nullable
    `lastChange`) and `PublisherServiceConfigurationChange` (`changedAt`,
    `actor`, `source`). The report exposes **no** job status, and BE-03 section
    12.1 requires BE-04 to add job-aware state **additively to this same report**.
22. **Report query shape.** `PublisherServiceConfiguration::all_summaries` issues
    one set-based filtered/ordered/paginated publisher statement plus one
    `DISTINCT ON (publisher_id)` latest-change statement, with a mandatory
    `publisher_id ASC` tie-breaker applied through the `apply_directional_order!`
    macro; `enabledDistributionPlatforms` resolves through BE-02's existing
    request-local `publisher_distribution_platforms` DataLoader.
    `filtered_publishers` is shared by the list and count queries so they cannot
    diverge, and `enabledPlatforms` narrows with **AND** semantics.
23. **Generated internal client.** `thoth-client/assets/schema.graphql` is
    written by `thoth-client/build.rs` and is ignored through
    `thoth-client/.gitignore`; the tracked client contract file is
    `assets/queries.graphql`. BE-03 added protected operations the internal
    export client does not consume, and its expected outcome was no query change.
24. **Database conventions.** Migrations live in
    `thoth-api/migrations/YYYYMMDD_v<version>/{up.sql,down.sql}`, created by
    `make migration`, which derives `<version>` as `MAJOR.(MINOR+1).0` from the
    root `Cargo.toml` version (currently `1.6.2`) and `YYYYMMDD` from the current
    date. The embedded `diesel_migrations` runner applies directories in
    lexicographic name order; the highest existing directory at this base is
    `20260813_v1.6.3`. Surrogate primary keys are `uuid` with
    `DEFAULT public.uuid_generate_v4()` (the `uuid-ossp` extension is installed by
    `20250000_v1.0.0/up.sql`); pure junction tables use a composite primary key
    (`publisher_distribution_platform`). Timestamps are `timestamp with time zone
    DEFAULT CURRENT_TIMESTAMP NOT NULL`, mapped to `Timestamptz` in `schema.rs`
    and to `crate::model::Timestamp` (a `DateTime<Utc>` newtype) in models.
    Mutable tables install `SELECT diesel_manage_updated_at('public.<table>')`;
    append-only tables do not. Enums are `CREATE TYPE ... AS ENUM` with
    SCREAMING_SNAKE_CASE labels, a `sql_types` struct in `schema.rs` carrying
    `#[diesel(postgres_type(name = "..."))]`, and a Rust enum deriving
    `diesel_derive_enum::DbEnum` and `juniper::GraphQLEnum` with
    `ExistingTypePath`, `serde(rename_all = "SCREAMING_SNAKE_CASE")` and
    `strum(serialize_all = "SCREAMING_SNAKE_CASE")`. Constraints are explicitly
    named. `schema.rs` additionally carries `joinable!` and
    `allow_tables_to_appear_in_same_query!` entries in alphabetical order.
    `thoth-errors` uses `thiserror` variants with `#[error("...")]`, and
    `into_field_error` gives a distinct GraphQL `type` extension only where a
    client needs classification; everything else falls through to
    `INTERNAL_ERROR`.
25. **Existing concurrency tests.** BE-02 and BE-03 database tests run against a
    disposable PostgreSQL reached through `TEST_DATABASE_URL`
    (`thoth-api/src/model/tests.rs`), and BE-03's concurrency evidence uses real
    connections and real transactions rather than mocks.

## 3. Explicit scope

The task must:

1. add the four closed PostgreSQL enums, three relations, constraints and indexes
   of section 7, with `make migration` and a manual atomic `schema.rs` update
   under ADR-0003 Architecture A;
2. add the Rust domain model, deterministic deduplication identity and job
   creation rules of sections 8 and 9;
3. extend BE-02's connection-scoped `enable_on` outcome so the coordinator can
   distinguish a **new activation** from a **repair**, per section 9.1, without
   changing BE-02's public behaviour;
4. extend BE-03's existing coordinator transaction exactly as section 10
   specifies, adding no second production transaction and no after-the-fact hook;
5. add the automatic-job-creation switch of section 9.3, defaulting to `OFF`,
   following the merged mutation-guard configuration convention;
6. implement the job state machine, claim/lease concurrency, retry and
   cancellation of sections 11 to 14, enforced by PostgreSQL;
7. add the `DISSEMINATION_WORKER` role and the least-privilege authorization
   matrix of section 15;
8. add the additive worker GraphQL API and the superuser cancellation mutation of
   section 16;
9. extend BE-03's staff report additively with the job-aware contract of section
   17, including its new DataLoaders under ADR-0007;
10. add exactly the two new `ThothError` variants and two new `into_field_error`
    arms of section 16.3;
11. regenerate the authoritative SDL, inspect the exact diff and record client
    compatibility per section 20;
12. add the tests and evidence required by sections 25 and 26;
13. update `docs/publisher-services/task-status.md` and `CHANGELOG.md`.

## 4. Non-goals

The task must not:

### Deferred distribution state

1. implement work-level distribution choices, `ALL_PUBLISHER_PLATFORMS`,
   `SELECTED_PLATFORMS` or `NONE`;
2. implement work-upsert jobs, withdrawal jobs or a metadata-change outbox;
3. implement delivery fingerprints, remote identifiers or any per-work/
   per-platform observed delivery state;
4. implement scheduled reconciliation;
5. implement uploader execution, adapter invocation, catalogue processing, file
   selection or Rust ports of uploaders;
6. contact any external distribution platform, or produce any file, feed,
   deposit, message or upload.

### Shared architecture

7. create a generic job framework, a universal lease abstraction, a universal

## 5. Invariants

The implementation must preserve:

1. **PostgreSQL is the sole durable owner** of every job, target, attempt, lease,
   claim token, deduplication key and retry state (root `AGENTS.md` section 10).
   No file, workflow, object store, browser state or external service is a
   durable owner of any of them, and no worker process is a lock manager.
2. **Every committed production change to desired service configuration still
   passes through BE-03's single coordinator**, and BE-04 adds no second
   configuration transaction.
3. **A job is never created outside that coordinator's transaction**, so a job
   cannot exist without the desired-state change that justified it, and the
   desired-state change cannot commit without the job.
4. **A job never exists without a token bump and exactly one audit row.** Job
   creation requires a new activation, which requires
   `AssignmentLifecycleOutcome::Activated`, which implies `changed()`, which
   forces the coordinator's single publisher `UPDATE` and its single audit row.
5. **One linked activation creates exactly one logical job with one target per
   `AutomaticPush` member**, never two jobs and never duplicate adapter execution
   (programme operational invariant 4).
6. **Pull-feed and manual destinations create no uploader job**, ever
   (operational invariant 5).
7. **Backfill of existing assignments creates no back-catalogue job**
   (operational invariant 3), and `MIGRATION_BACKFILL` can never create one.
8. **Automatic job creation is initially inactive** (operational invariant 7),
   and neither merge nor deployment enqueues any back catalogue.
9. **Claims are exclusive and leased, and a stale claim token cannot complete
   current work** (operational invariant 6).
10. **Authorization fails closed, and no role implies another.** `SUPERUSER` does
    not confer worker powers and `DISSEMINATION_WORKER` confers no publisher
    scope (section 15).
11. **Job, target and attempt history is never deleted or rewritten as routine
    operation.** A target row is immutable; an attempt row is inserted once and
    closed once.
12. **BE-02's assignment lifecycle semantics** are unchanged: retained disabled
    rows, a new activation identity on re-enable, one transaction timestamp per
    transition, same-state no-ops that move no timestamp, repair of one-sided,
    split-activation and split-timestamp pairs.
13. **The closed 17-value inventory** with no `OTHER`, fallback or `Default`
    (ADR-0004), and `JISC_NBK` included, inactive and non-assignable.
14. **`DistributionPlatform` and `MetricPlatform` remain separate** with no
    conversion (ADR-0002).
15. **`thoth-api/src/schema.rs` is edited manually and atomically with the
    migration** (ADR-0003).
16. **Every existing public GraphQL surface remains backwards compatible**, and
    BE-03's configuration-only contract for publisher users is unchanged.
17. **Application lock order remains `publisher` row first**, and the worker path
    never takes the publisher lock (section 10.2).

## 6. Architecture boundary

### 6.1 Three-layer state model

The approved three-layer distinction is preserved exactly:

```text
DESIRED STATE
    Publisher package + enabled distribution platforms.
    Owned by BE-01/BE-02/BE-03. Unchanged by BE-04.

DURABLE JOB STATE
    Work that must be performed, retried or audited.
    Owned by BE-04. This task.

OBSERVED DELIVERY STATE
    Per-work/per-platform delivery outcome, fingerprints, remote identifiers.
    Deferred future work. NOT BE-04.
```

BE-04 owns durable **publisher back-catalogue** jobs only. Everything listed in
non-goals 1 to 6 remains deferred and must reuse these foundations rather than
introduce a parallel model.

### 6.2 Programme-local boundary

BE-04 defines **programme-local durable distribution-job machinery owned by
`thoth-api`**. [`thoth-api/AGENTS.md`](../../../../thoth-api/AGENTS.md) section 1
already assigns "durable jobs, leases and audit records implemented in Thoth" to
this crate, and section 5 already names the exact primitives BE-04 uses — unique
constraints, foreign keys, check constraints, row locks, leases with expiry,
claim tokens, `FOR UPDATE SKIP LOCKED` and deterministic idempotency keys. BE-04
is therefore a **conventional application** of already-approved repository
architecture, not new shared architecture.

The boundary is explicit and binding:

- every type, table, column, enum, constant, module and role code BE-04 adds is
  named for **distribution jobs** and is unusable as a generic facility;
- there is no `Job`, `Queue`, `Lease`, `Worker` or `ServiceRole` generic type, no
  trait abstracting job kinds across programmes, no shared scheduler and no
  shared claim protocol;
- the `distribution_job_kind` enum exists so this programme's own later job kinds
  (work upsert, withdrawal) reuse one table under their own approved tasks. It is
  not an extension point for another programme;
- the automatic-creation switch is one named argument for one behaviour, not a
  feature-flag subsystem;
- `DISSEMINATION_WORKER` is one role with three permitted operations, expressed
  through the **existing** unscoped-project-role check pattern that
  `is_superuser()` already establishes (section 2.2 item 18). It introduces no
  general service-role framework, no machine-identity storage and no credential
  handling.

If implementation finds that any of the above cannot hold — that a correct BE-04
genuinely requires a generic framework, a universal lease abstraction, a shared
worker/service-role convention, a metrics-job abstraction, a universal queue or a
new cross-programme identity model — the implementing agent must return
`BLOCKED` under stop condition 12 with the exact decision and affected
programmes, and must not create the cross-programme ADR inside the BE-04 pull
request.

### 6.3 Cross-programme adjacency finding

This is recorded as an **observed finding for the CTO**, not as a decision taken
by this specification, and not as a resolution of anything.

`docs/metrics/task-status.md` records Thoth Metrics work package **WP5 - Service
auth and entitlements**, repositories `thoth` + clients, risk `CRITICAL`, status
`BLOCKED`, whose first listed blocking dependency is a **"role decision"**. WP5
therefore concerns the same crate, the same `policy.rs`, the same `Role` enum and
the same ZITADEL project as BE-04's worker role.

The assessment, stated plainly:

1. BE-04 does **not** require WP5's decision. `DISSEMINATION_WORKER` reuses the
   unscoped-role check pattern that `SUPERUSER` already establishes; it adds one
   role, one predicate and one `require_*` helper, permits exactly three
   operations and confers no publisher scope and no entitlement. Nothing in BE-04
   answers "how do metrics clients authenticate and how are entitlements
   enforced", and nothing in BE-04 forecloses any answer WP5 may choose —
   including a publisher-scoped service role, per-client credentials or an
   entitlement model.
2. BE-04 is likewise **not blocked by** WP5. WP5 is BLOCKED on its own
   dependencies (WP4, bounded slice specifications) independently of this task.
3. The adjacency that remains, and that the CTO should see, is **precedence**:
   `DISSEMINATION_WORKER` would be the repository's first non-`SUPERUSER`
   unscoped project role, and WP5 will reasonably look at it. Precedence is not
   the same as a shared convention, and this specification deliberately does not
   convert one into the other — see the explicit boundary in section 6.2 and the
   prohibition in non-goal 8.
4. If the CTO judges instead that the machine-identity question must be settled
   once, for both programmes, before either uses it, then BE-04's authorization
   design is superseded and **BE-04 implementation is `BLOCKED`** under stop
   condition 13 until that separate CTO-controlled decision exists. That
   judgement is reserved to the CTO and is not available to the implementing
   agent.

No ADR is created by this task, and
[`docs/publisher-services/decisions.md`](../../../publisher-services/decisions.md)
is deliberately **not** edited: this finding is an adjacency to surface, not an
unresolved programme-local decision, and every design decision BE-04 needs is
derivable from merged repository evidence.

## 7. Database model

### 7.1 Enums

Four closed PostgreSQL enums, following section 2.2 item 24 exactly. None has an
`OTHER`, `UNKNOWN`, catch-all or `Default` variant: an unrecognised database,
serde, string or GraphQL value must fail rather than resolve to a nearest value.

```sql
CREATE TYPE public.distribution_job_kind AS ENUM (
    'PUBLISHER_BACK_CATALOGUE'
);

CREATE TYPE public.distribution_job_status AS ENUM (
    'PENDING',
    'RUNNING',
    'SUCCEEDED',
    'FAILED',
    'CANCELLED'
);

CREATE TYPE public.distribution_job_attempt_result AS ENUM (
    'SUCCEEDED',
    'FAILED',
    'CANCELLED',
    'ABANDONED'
);

CREATE TYPE public.distribution_job_cancellation_reason AS ENUM (
    'ADMINISTRATIVE',
    'ASSIGNMENT_DISABLED'
);
```

`distribution_job_kind` carries exactly one value now. It exists so that this
programme's deferred job kinds reuse one relation and one deduplication index
under their own approved tasks (section 6.2), and so that the deduplication key
formula is kind-scoped from the first row.

`distribution_job_attempt_result` is deliberately **not** `distribution_job_status`
restricted to terminal values. A job's status and an attempt's result are
different facts: a `FAILED` attempt routinely leaves the job `PENDING` for retry,
and `ABANDONED` — a lease that expired with no worker response — has no job-status
counterpart at all. Overloading one enum would make both meanings unreadable.

`distribution_job_cancellation_reason` exists so an operator can distinguish a
deliberate administrative cancellation from a cancellation caused by the
publisher's own platform being disabled (section 14.3). Without it the staff
report cannot answer "why is this cancelled", which is exactly the question a
cancelled onboarding job raises.

### 7.2 `distribution_job`

```sql
CREATE TABLE public.distribution_job (
    distribution_job_id uuid DEFAULT public.uuid_generate_v4() NOT NULL,
    kind public.distribution_job_kind NOT NULL,
    publisher_id uuid NOT NULL,
    work_id uuid,
    activation_id uuid NOT NULL,
    status public.distribution_job_status DEFAULT 'PENDING' NOT NULL,
    deduplication_key text NOT NULL,
    attempt_count integer DEFAULT 0 NOT NULL,
    available_at timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,
    claim_token uuid,
    claimed_by text,
    claimed_at timestamp with time zone,
    lease_expires_at timestamp with time zone,
    completed_at timestamp with time zone,
    cancellation_reason public.distribution_job_cancellation_reason,
    last_error_code text,
    last_error_detail text,
    created_at timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,

    CONSTRAINT distribution_job_pkey
        PRIMARY KEY (distribution_job_id),

    CONSTRAINT distribution_job_publisher_id_fkey
        FOREIGN KEY (publisher_id)
        REFERENCES public.publisher(publisher_id) ON DELETE CASCADE,

    CONSTRAINT distribution_job_work_id_fkey
        FOREIGN KEY (work_id)
        REFERENCES public.work(work_id) ON DELETE CASCADE,

    CONSTRAINT distribution_job_deduplication_key_key
        UNIQUE (deduplication_key),

    CONSTRAINT distribution_job_deduplication_key_formula_check CHECK (
        kind <> 'PUBLISHER_BACK_CATALOGUE'
        OR deduplication_key =
            'PUBLISHER_BACK_CATALOGUE:' || publisher_id::text
                                        || ':' || activation_id::text
    ),

    CONSTRAINT distribution_job_deduplication_key_length_check
        CHECK (char_length(deduplication_key) BETWEEN 1 AND 256),

    CONSTRAINT distribution_job_back_catalogue_work_check
        CHECK (kind <> 'PUBLISHER_BACK_CATALOGUE' OR work_id IS NULL),

    CONSTRAINT distribution_job_attempt_count_check
        CHECK (attempt_count >= 0),

    CONSTRAINT distribution_job_claim_state_check CHECK (
        (status = 'RUNNING'
            AND claim_token IS NOT NULL
            AND claimed_by IS NOT NULL
            AND claimed_at IS NOT NULL
            AND lease_expires_at IS NOT NULL)
        OR
        (status <> 'RUNNING'
            AND claim_token IS NULL
            AND claimed_by IS NULL
            AND claimed_at IS NULL
            AND lease_expires_at IS NULL)
    ),

    CONSTRAINT distribution_job_claimed_by_check
        CHECK (claimed_by IS NULL OR claimed_by ~ '[^[:space:]]'),

    CONSTRAINT distribution_job_completed_at_check CHECK (
        (status IN ('SUCCEEDED', 'FAILED', 'CANCELLED')
            AND completed_at IS NOT NULL)
        OR
        (status IN ('PENDING', 'RUNNING') AND completed_at IS NULL)
    ),

    CONSTRAINT distribution_job_cancellation_reason_check CHECK (
        (status = 'CANCELLED' AND cancellation_reason IS NOT NULL)
        OR
        (status <> 'CANCELLED' AND cancellation_reason IS NULL)
    ),

    CONSTRAINT distribution_job_last_error_check
        CHECK (last_error_detail IS NULL OR last_error_code IS NOT NULL),

    CONSTRAINT distribution_job_last_error_code_format_check CHECK (
        last_error_code IS NULL
        OR (last_error_code ~ '^[A-Z][A-Z0-9_]*$'
            AND char_length(last_error_code) <= 64)
    ),

    CONSTRAINT distribution_job_last_error_detail_length_check CHECK (
        last_error_detail IS NULL OR char_length(last_error_detail) <= 2048
    )
);

SELECT diesel_manage_updated_at('public.distribution_job');
```

Column notes, each stating a decision rather than restating the DDL:

- **`work_id` is the nullable future work identifier the approved design
  requires, and BE-04 never populates it.** The
  `distribution_job_back_catalogue_work_check` constraint makes that a database
  property for the only current kind, so no code path can populate it by
  accident. Because no BE-04 row ever sets it, the `ON DELETE CASCADE` behaviour
  is unobservable in BE-04; a future work-level job task must revisit that choice
  explicitly rather than inherit it silently.
- **`activation_id` is a first-class column, not only a component of the key.**
  The claim eligibility predicate of section 12.4 needs it to decide whether a
  job's targets are still enabled *under the activation that created the job*,
  which is what prevents a disable/re-enable cycle from producing two live jobs
  for one destination. It is `NOT NULL` because the only current kind always has
  one; a future kind without an activation must change it under its own task.
- **`deduplication_key` is a single kind-agnostic unique text column**, and
  `distribution_job_deduplication_key_formula_check` proves it equals the exact
  section 8.2 formula for the only current kind. That check uses only immutable
  expressions — an enum inequality against a literal, `uuid::text` casts and
  `||` — so it is a genuine database guarantee, not a convention. The key and the
  typed columns therefore cannot diverge.
- **`claim_token`, `claimed_by`, `claimed_at` and `lease_expires_at` are non-null
  if and only if `status = 'RUNNING'`.** This one constraint is what makes every
  stale-token statement in section 12.6 structurally safe: a job that is not
  running has no current token to match.
- **`claimed_by` follows BE-03's audit-actor convention exactly** — a free-text
  actor column with no foreign key to any local account (none exists), with a
  non-whitespace check constraint so no write path can record a blank machine
  identity. It stores `PolicyContext::user_id()` of the authenticated worker and
  is never a GraphQL input (section 16.1).
- **`cancellation_reason` is non-null if and only if `status = 'CANCELLED'`.**
- **`last_error_code` is a stable machine-readable classification**, constrained
  to `^[A-Z][A-Z0-9_]*$` and 64 characters, so free-form prose cannot be stored
  in the field clients switch on. `last_error_detail` is the bounded human
  diagnostic (section 18). Both mirror the most recent attempt's values so an
  operator sees the current failure without a join.
- **`ON DELETE CASCADE` from `publisher`** matches BE-02 and BE-03. Deleting a
  publisher therefore destroys its job and attempt history along with its
  assignments and configuration audit. That is a reviewed consequence of an
  already superuser-only destructive act, recorded here rather than discovered
  later.

### 7.3 `distribution_job_target`

```sql
CREATE TABLE public.distribution_job_target (
    distribution_job_id uuid NOT NULL,
    platform public.distribution_platform NOT NULL,
    created_at timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,

    CONSTRAINT distribution_job_target_pkey
        PRIMARY KEY (distribution_job_id, platform),

    CONSTRAINT distribution_job_target_distribution_job_id_fkey
        FOREIGN KEY (distribution_job_id)
        REFERENCES public.distribution_job(distribution_job_id) ON DELETE CASCADE
);
```

- **Uniqueness is the primary key.** `(distribution_job_id, platform)` is
  composite exactly as `publisher_distribution_platform` is, so one logical job
  can never carry the same destination twice and no surrogate identifier is
  invented for a pure junction row.
- **Deterministic ordering is `ORDER BY platform`.** The column is a PostgreSQL
  enum, so its sort order is the declaration order, which is the canonical
  `DistributionPlatform::ALL` order the public contract already guarantees —
  identical to BE-02's `enabled_assignment_rows`.
- **Target rows are immutable.** Nothing updates or deletes a target row for any
  lifecycle reason: not failure, not retry, not cancellation, not disabling the
  assignment. They disappear only with the job row, by cascade.
- **No logical job may exist with zero targets.** PostgreSQL cannot express "at
  least one child row" without a deferred constraint trigger, and BE-04 does not
  add one: a trigger enforcing a cardinality that exactly one code site can
  produce would add shared DDL surface for no reachable defect. Instead the
  invariant is enforced by construction — the single creation function of section
  10.1 step 9b computes a **non-empty** target set before inserting the job and
  inserts job and targets in the same transaction — and section 25.4 requires a
  test asserting `SELECT count(*) FROM distribution_job j WHERE NOT EXISTS
  (SELECT 1 FROM distribution_job_target t WHERE t.distribution_job_id =
  j.distribution_job_id)` is `0` after every creation scenario. This is stated as
  a deliberate, reasoned choice rather than presented as database enforcement.

### 7.4 `distribution_job_attempt`

```sql
CREATE TABLE public.distribution_job_attempt (
    distribution_job_attempt_id uuid DEFAULT public.uuid_generate_v4() NOT NULL,
    distribution_job_id uuid NOT NULL,
    attempt_number integer NOT NULL,
    claim_token uuid NOT NULL,
    claimed_by text NOT NULL,
    started_at timestamp with time zone DEFAULT CURRENT_TIMESTAMP NOT NULL,
    finished_at timestamp with time zone,
    result public.distribution_job_attempt_result,
    error_code text,
    error_detail text,

    CONSTRAINT distribution_job_attempt_pkey
        PRIMARY KEY (distribution_job_attempt_id),

    CONSTRAINT distribution_job_attempt_distribution_job_id_fkey
        FOREIGN KEY (distribution_job_id)
        REFERENCES public.distribution_job(distribution_job_id) ON DELETE CASCADE,

    CONSTRAINT distribution_job_attempt_number_key
        UNIQUE (distribution_job_id, attempt_number),

    CONSTRAINT distribution_job_attempt_claim_token_key
        UNIQUE (claim_token),

    CONSTRAINT distribution_job_attempt_number_check
        CHECK (attempt_number >= 1),

    CONSTRAINT distribution_job_attempt_claimed_by_check
        CHECK (claimed_by ~ '[^[:space:]]'),

    CONSTRAINT distribution_job_attempt_closure_check CHECK (
        (finished_at IS NULL AND result IS NULL)
        OR
        (finished_at IS NOT NULL AND result IS NOT NULL)
    ),

    CONSTRAINT distribution_job_attempt_interval_check
        CHECK (finished_at IS NULL OR finished_at >= started_at),

    CONSTRAINT distribution_job_attempt_error_result_check CHECK (
        (error_code IS NULL AND error_detail IS NULL)
        OR result = 'FAILED'
    ),

    CONSTRAINT distribution_job_attempt_error_pairing_check
        CHECK (error_detail IS NULL OR error_code IS NOT NULL),

    CONSTRAINT distribution_job_attempt_error_code_format_check CHECK (
        error_code IS NULL
        OR (error_code ~ '^[A-Z][A-Z0-9_]*$' AND char_length(error_code) <= 64)
    ),

    CONSTRAINT distribution_job_attempt_error_detail_length_check CHECK (
        error_detail IS NULL OR char_length(error_detail) <= 2048
    )
);
```

- **Relationship to the job.** One job has zero or more attempts; one attempt
  belongs to exactly one job. `attempt_number` is the attempt's ordinal within
  its job, starting at `1`, and equals the job's `attempt_count` immediately
  after the claim that created it. `UNIQUE (distribution_job_id, attempt_number)`
  makes the ordinal structural rather than conventional.
- **`UNIQUE (claim_token)` is load-bearing.** A claim token identifies exactly
  one attempt row for all time, so every worker statement that predicates on the
  token addresses exactly one attempt and can never close a newer one.
- **Worker/claim identity is required for audit**, so `claim_token` and
  `claimed_by` are `NOT NULL` and are recorded at insert. A cancelled or
  abandoned attempt still names who held it.
- **Immutable fields**, never rewritten after insert:
  `distribution_job_attempt_id`, `distribution_job_id`, `attempt_number`,
  `claim_token`, `claimed_by`, `started_at`.
- **Write-once-at-closure fields**: `finished_at`, `result`, `error_code`,
  `error_detail`. Every closing statement predicates on
  `claim_token = $token AND finished_at IS NULL`, so a second close affects zero
  rows.
- **No `updated_at` column and no `diesel_manage_updated_at` trigger**, following
  BE-03's append-only audit precedent. The row is inserted open and closed once;
  there is no third write, and nothing deletes a row except the job cascade.
- **The attempt's `result` names the event that closed it**, which is the rule
  that keeps the four values unambiguous: `SUCCEEDED` and `FAILED` for a worker
  report, `CANCELLED` when a cancellation closed it, `ABANDONED` when lease
  expiry recovered it.

### 7.5 Indexes

```sql
CREATE INDEX distribution_job_claimable_idx
    ON public.distribution_job
    USING btree (available_at, distribution_job_id)
    WHERE status = 'PENDING';

CREATE INDEX distribution_job_lease_idx
    ON public.distribution_job
    USING btree (lease_expires_at, distribution_job_id)
    WHERE status = 'RUNNING';

CREATE INDEX distribution_job_publisher_latest_idx
    ON public.distribution_job
    USING btree (publisher_id, kind, created_at DESC, distribution_job_id DESC);
```

- `distribution_job_claimable_idx` supports the section 12.3 claim selection's
  exact predicate and total order, and being partial it stays small as terminal
  jobs accumulate.
- `distribution_job_lease_idx` supports the section 12.2 lease-recovery scan on
  the same basis.
- `distribution_job_publisher_latest_idx` supports the section 17.4
  `DISTINCT ON (publisher_id)` latest-job lookup with a **total** order, so the
  selected row is deterministic even for two jobs sharing a `created_at`. It is
  the direct analogue of BE-03's
  `publisher_service_configuration_history_publisher_created_idx`.
- `distribution_job_deduplication_key_key` (the unique constraint) provides the
  index the `ON CONFLICT` creation path needs; no separate index is created.
- `distribution_job_target_pkey` and
  `distribution_job_attempt_number_key`/`distribution_job_attempt_claim_token_key`
  provide the loader and worker lookups; no separate index is created for them.
  The attempt loader's `distribution_job_id = ANY($1)` uses the leading column of
  `distribution_job_attempt_number_key`.

### 7.6 `schema.rs` and Rust model contract

`thoth-api/src/schema.rs` is edited **manually and atomically in the same pull
request** as the migration, under ADR-0003 Architecture A. `diesel print-schema`
must not be used as the canonical writer, no `diesel.toml` is introduced and no
schema-synchronization subsystem is added. The exact additions are:

- four `sql_types` structs — `DistributionJobKind`, `DistributionJobStatus`,
  `DistributionJobAttemptResult`, `DistributionJobCancellationReason` — each with
  `#[diesel(postgres_type(name = "..."))]`, placed after the existing
  `PublisherServiceConfigurationSource`;
- three `table!` blocks in alphabetical position, with column order matching the
  DDL above so `Queryable` derives line up with the model structs;
- `joinable!(distribution_job -> publisher (publisher_id));`,
  `joinable!(distribution_job -> work (work_id));`,
  `joinable!(distribution_job_target -> distribution_job (distribution_job_id));`,
  `joinable!(distribution_job_attempt -> distribution_job (distribution_job_id));`
  in alphabetical position;
- `distribution_job`, `distribution_job_attempt`, `distribution_job_target` added
  to `allow_tables_to_appear_in_same_query!` in alphabetical position.

No unrelated schema reformatting, reordering or renaming is permitted.

The Rust domain lives in a new module
`thoth-api/src/model/distribution_job/{mod.rs, crud.rs, tests.rs}`, following the
shape of `publisher_distribution_platform/` and
`publisher_service_configuration/`. `Crud` is deliberately **not** implemented for
any of the three entities: there is no generic create/update/delete surface for
durable jobs, and the only supported writes are the named domain functions this
specification fixes. GraphQL evidence lives in a new
`thoth-api/src/graphql/distribution_job_tests.rs`, following
`distribution_platform_tests.rs` and `service_configuration_tests.rs`.

The code-owned bounds are named constants in that module, not magic numbers and
not runtime configuration:


construction and section 25.10 tests both.

## 8. Deterministic deduplication model

### 8.1 Activation identity is the deduplication input

The key is derived from **BE-02's actual activation semantics**, not from the
platform list and not from a hash of the request.

Section 2.2 item 14 establishes that `enable_on` mints one fresh
`activation_id` and writes it to **every member of the linked group** in one
transaction. `activation_id` is therefore already exactly the thing BE-04 needs:
*one identity per logical activation of one destination or linked group for one
publisher*. It is minted on first enable, on genuine re-enable and on repair, and
it is never reused.

Deriving the key from `activation_id` rather than from `(publisher, platform)`
is what makes every requirement in section 8.4 and 8.5 fall out of one rule
instead of needing special cases.

### 8.2 Key formula

For `kind = PUBLISHER_BACK_CATALOGUE` the deduplication key is exactly:

```text
PUBLISHER_BACK_CATALOGUE:<publisher_id>:<activation_id>
```

In Rust, at the single creation site:

```rust
format!("{kind}:{publisher_id}:{activation_id}")
```

where:

- `{kind}` is the `strum` `Display` of `DistributionJobKind`, which is the
  SCREAMING_SNAKE_CASE database label — `PUBLISHER_BACK_CATALOGUE`;
- `{publisher_id}` and `{activation_id}` are `uuid::Uuid`'s `Display`, which is
  the lowercase hyphenated form and is byte-identical to PostgreSQL's
  `uuid::text` output;
- the separator is a single ASCII colon, which cannot occur inside either
  component, so the encoding is unambiguous and parseable.

The rendered length is fixed at 98 characters, well inside the 256-character
check.

Every future kind added by a later approved task defines its own formula,
prefixed by its own kind label, and adds its own arm to the
`distribution_job_deduplication_key_formula_check` constraint. The kind prefix is
what guarantees two kinds can never collide in the one unique index.

### 8.3 Database uniqueness rule

Idempotency is enforced by **the database, not by an application check-then-
insert**:

```sql
INSERT INTO distribution_job
    (kind, publisher_id, activation_id, deduplication_key, status,
     attempt_count, available_at)
VALUES ($1, $2, $3, $4, 'PENDING', 0, CURRENT_TIMESTAMP)
ON CONFLICT ON CONSTRAINT distribution_job_deduplication_key_key DO NOTHING
RETURNING distribution_job_id;
```

- if a row is returned, this observation created the job and the caller inserts
  its target rows;
- if **no** row is returned, a job already exists for that logical activation:
  the caller writes **no** target rows, raises **no** error, and continues. A
  repeated observation is a silent, correct no-op.

Two independent guarantees therefore hold, and both are required rather than one
being a fallback for the other:

1. **serialization** — the coordinator holds the publisher row lock for its
   whole transaction, so two concurrent configuration writes for the same
   publisher cannot interleave at all;
2. **uniqueness** — `distribution_job_deduplication_key_key` makes duplicate
   creation impossible even for a caller that does not hold that lock, which is
   the guarantee that survives any future creation path.

`distribution_job_deduplication_key_formula_check` additionally makes the stored
key provably equal to the section 8.2 formula, so a code defect that computed the
wrong key would fail the insert rather than silently create a second job.

### 8.4 Linked OAPEN/DOAB result, mechanically

Enabling OAPEN, or DOAB, or both, in one configuration replacement produces
exactly this and nothing else:

| Quantity | Value | Because |
|---|---:|---|
| `enable_on` calls | 1 | the coordinator takes one canonical representative per linked group |
| `activation_id` values minted | 1 | `enable_on` writes one shared id to every member |
| deduplication keys | 1 | the key is `kind:publisher:activation`, and there is one activation |
| `distribution_job` rows | 1 | the unique key admits one |
| `distribution_job_target` rows | 2 | one per `AutomaticPush` member of the activated group: `OAPEN`, `DOAB` |
| adapter executions DIS-02 must perform | 1 | both targets share `Profile::OapenDoabSword`; the job is one unit of work |

The two targets are ordered `OAPEN` then `DOAB` by the enum's declaration order.
Section 25.5 requires this exact one-job/two-target result to be asserted by row
count and by content, for all three request shapes (name OAPEN, name DOAB, name
both).

### 8.5 Re-enable produces a new legitimate job

A genuine disable followed by a re-enable calls `enable_on` on a group with no
enabled member, which mints a **new** `activation_id`. The key therefore differs
from the previous onboarding's key, the unique constraint does not fire, and a
new `PENDING` job is created — which is correct: the publisher genuinely asked to
be onboarded again, to a destination that had been withdrawn.

The three cases are distinguished by exactly one rule and no special-casing:

| Case | `activation_id` | Key | Result |
|---|---|---|---|
| repeated observation of one activation | same | same | `ON CONFLICT DO NOTHING`; no second job |
| genuine disable then re-enable | new | new | new legitimate onboarding job |
| linked-state repair | new | new | **no job** — excluded earlier, by section 9.1, before a key is ever computed |

The third row is the one that would otherwise be wrong, and section 9.1 is where
it is handled: a repair is excluded at classification time, so its new
`activation_id` never reaches the key formula.

## 9. Job creation rules

### 9.1 Activation classification

Job creation must distinguish a **new activation** from a **repair**. The merged
`AssignmentLifecycleOutcome` cannot express that difference — BE-03 section 7.9
records that it is deliberately the minimum BE-03 needed and that BE-04 extends
it under its own specification. BE-04 extends it:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[must_use]
pub(crate) enum AssignmentLifecycleOutcome {
    /// Nothing was written and no timestamp moved.
    Unchanged,
    /// A group with no enabled member became enabled under a new activation.
    Activated { activation_id: Uuid },
    /// An already partly-enabled group was normalized to a new shared activation.
    Repaired { activation_id: Uuid },
    /// A group with at least one enabled member was disabled.
    Disabled,
}

impl AssignmentLifecycleOutcome {
    pub(crate) fn changed(self) -> bool {
        !matches!(self, AssignmentLifecycleOutcome::Unchanged)
    }
}
```

The classifying predicate is available **inside `enable_on` from the
`member_rows` it already reads**, before it writes anything:

- `Unchanged` — `is_normalized_fully_enabled(&existing, &members)` is true. The
  merged predicate is used unchanged and is not re-derived.
- `Activated` — the group is not fully normalized **and no member row is
  currently enabled**. This covers an absent group, a wholly disabled group, and
  a group whose rows exist but are all disabled.
- `Repaired` — the group is not fully normalized **and at least one member row is
  currently enabled**. This covers the one-sided, split-activation and
  split-timestamp cases.

`disable_on` returns `Disabled` where it currently returns `Changed`, and
`Unchanged` unchanged.

**Why "any member already enabled" is the correct repair test**, and not an
approximation: members of a linked group share one adapter profile by
construction — that is what makes them linked. `OAPEN` and `DOAB` both resolve to
`Profile::OapenDoabSword`, one deposit. So if any member was already enabled, the
shared adapter was already active for that publisher and the back catalogue has
already been onboarded through it. Creating an onboarding job for a repair would
re-push an entire back catalogue to satisfy a cosmetic normalization. The rule is
derived from the descriptor model, not from the group's name.

**BE-02's public behaviour is unchanged.** The pool-level
`PublisherDistributionPlatform::enable`/`::disable` keep their `ThothResult<()>`
signatures, their early non-assignable check and their existing tests; they
already discard the outcome. The enum is `pub(crate)`, so the widening is
internal. BE-03's accumulation becomes `lifecycle_changed |= outcome.changed()`
with an unchanged meaning, and section 25.11 requires a regression test proving
BE-02's merged lifecycle semantics — retained disabled rows, new activation on
re-enable, one transaction timestamp, same-state no-op, split repair — are
byte-identical.

### 9.2 Complete creation matrix

For one committed configuration replacement, evaluated per linked group:

| Situation | Job created? | Rule |
|---|---|---|
| `Activated` group with ≥ 1 `AutomaticPush` member, `SUPERUSER_API`, switch `ON` | **YES** — one job, one target per `AutomaticPush` member | the only creating case |
| `Activated` group whose members are all `PullFeed` | NO | `PullFeed` never creates an uploader/back-catalogue job |
| `Activated` group whose members are all `Manual` | NO | `Manual` never creates an uploader/back-catalogue job |
| `Repaired` group | NO | section 9.1: the adapter was already active |
| `Unchanged` group | NO | nothing was written |
| `Disabled` group | NO | disabling never creates a job |
| package-only change | NO | no group is `Activated` |
| true no-op replacement | NO | the coordinator returns before any write |
| stale replacement | NO | the coordinator returns before any write |
| repeated identical replacement | NO | the second call yields `Unchanged`; and the unique key would refuse a duplicate anyway |
| `source = MIGRATION_BACKFILL` | NO, unconditionally | operational invariant 3; MIG-01 imports existing assignments and must create zero onboarding jobs |
| switch `OFF` | NO, unconditionally | operational invariant 7 |
| non-assignable destination (`JISC_NBK`) | NO | it can never be enabled, so it can never be `Activated` and can never be a target |

The two unconditional rules are one expression at one site, so neither can be
bypassed by any caller, present or future:

```rust
let create_jobs = write_context.job_creation == DistributionJobCreation::On
    && write_context.source == PublisherServiceConfigurationSource::SuperuserApi;
```

The target set for a qualifying activated group is:

```rust
group_members
    .iter()
    .copied()
    .filter(|p| p.descriptor().back_catalogue_behaviour == BackCatalogueBehaviour::AutomaticPush)
    .collect::<Vec<_>>()
```

in canonical order. If that set is **empty**, no job is created — which is what
makes the `PullFeed` and `Manual` rows above exhaustive and future-proof for a
mixed group, rather than depending on today's inventory happening to have none.
The behaviour is read from code-owned descriptors and never inferred from a
destination's name.

### 9.3 Automatic-creation switch

The switch follows the merged mutation-guard convention (section 2.2 item 20)
exactly, because that is the repository's one established OFF-by-default runtime
control and inventing a second mechanism would be worse than reusing it.

```rust
/// Whether a qualifying activation may create a durable distribution job.
///
/// Publisher-Services-specific. This is not a feature-flag subsystem.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub enum DistributionJobCreation {
    #[default]
    Off,
    On,
}
```

- `FromStr` accepts exactly `OFF` and `ON` and **fails** on anything else. An
  unparseable value is never silently resolved to a nearest value; the process
  fails to start.
- `Default` is `Off`, so every construction path that omits it is inactive.
- Argument in `src/bin/arguments/mod.rs`:

  ```rust
  Arg::new("distribution-job-creation")
      .long("distribution-job-creation")
      .value_name("THOTH_DISTRIBUTION_JOB_CREATION")
      .env("THOTH_DISTRIBUTION_JOB_CREATION")
      .default_value("OFF")
      .value_parser(["OFF", "ON"])
      .help("Automatic durable distribution-job creation: OFF or ON")
      .num_args(1)
  ```

- registered on **every** command that can serve GraphQL — `start graphql-api`
  **and** `init`, which is the image's default command. Registering it on only
  one is the exact defect `THOTH-GQL-OPS-02` had to fix for the guard mode, and
  section 25.9 requires the both-profiles argument tests that pin it.
- plumbed as `MutationGuardMode` is: a `start_server(...)` parameter,
  `.app_data(Data::new(distribution_job_creation))`, extraction in the
  `/graphql` handler.
- **unlike `MutationGuardMode`, it must reach the resolver**, so `Context` gains
  one field and `Context::new` one parameter. The resolver then places it in the
  write context; the coordinator makes no ambient lookup:

  ```rust
  pub struct ServiceConfigurationWriteContext<'a> {
      pub source: PublisherServiceConfigurationSource,
      pub actor: &'a str,
      pub job_creation: DistributionJobCreation,   // BE-04
  }
  ```

  This preserves BE-03's discipline exactly: the coordinator takes policy as an
  explicit parameter and never infers it from ambient state. It is also what lets
  every creation test drive the switch directly, with no environment mutation.

The value is read once at process start, as the guard mode is; there is no reload
path and BE-04 adds none. Turning the switch `ON` in any deployed environment is
a **production activation act** requiring separate explicit CTO authorization
(section 22). Merging BE-04 does not authorize it.

### 9.4 No retroactive sweep

Enabling the switch executes **no code over existing rows**. There is
deliberately no sweep, no backfill, no startup scan, no reconciliation pass, no
migration-time creation and no lazy creation on read. The switch is consulted at
exactly one place — inside the coordinator's transaction, while handling one
configuration replacement — so a publisher whose platforms were enabled before
the switch was turned on acquires a job only if and when a **new** activation
occurs afterwards.

Section 25.6 requires a test that turns the switch on with pre-existing enabled
assignments present and asserts zero jobs exist until a fresh activation happens.

## 10. BE-03 transaction extension

### 10.1 Exact sequence

BE-04 extends **the coordinator's existing single transaction on its existing
single connection**. It adds no second transaction, no nested transaction, no
savepoint, no deferred hook, no callback, no event and no after-the-fact
best-effort path. The full committed sequence, with BE-04's additions marked:

| # | Step | Owner |
|---:|---|---|
| 1 | `require_superuser()`; build `ServiceConfigurationWriteContext { source, actor, job_creation }` | resolver (BE-03, extended field) |
| 2 | **lock** — `SELECT publisher_id ... FOR UPDATE`, first statement; absent row ⇒ `EntityNotFound`, no write | BE-03 |
| 3 | read publisher row and current enabled platforms under the lock; capture `previous_token` | BE-03 |
| 4 | **concurrency check** — compare `expected_updated_at` with `previous_token` | BE-03 |
| 5 | stale ⇒ `StalePublisherServiceConfiguration`; no write, no token movement, no audit row, **no job** | BE-03 |
| 6 | **normalization** — deduplicate the requested set and close it under `linked_members` | BE-03 |
| 7 | validate `is_assignable()` over the whole normalized set before any write | BE-03 |
| 8 | compute `package_changed`; **do not** write the package here | BE-03 |
| 9 | **assignment diff/lifecycle writes** — `enable_on` per desired group representative unconditionally, then `disable_on` per undesired enabled group representative; accumulate `lifecycle_changed`, and **retain each outcome with its group representative** | BE-03, outcome widened by BE-04 (section 9.1) |
| 9a | **qualifying-job determination** — for each `Activated { activation_id }` outcome, if `create_jobs`, compute the `AutomaticPush` target set; a non-empty set qualifies. Pure computation, no I/O | **BE-04** |
| 9b | **deduplicated job and target writes** — for each qualifying activation, in canonical group-representative order: `INSERT ... ON CONFLICT ON CONSTRAINT distribution_job_deduplication_key_key DO NOTHING RETURNING distribution_job_id`; if a row was returned, insert its target rows in one multi-row `INSERT` in canonical platform order; if not, write nothing and continue | **BE-04** |
| 9c | **assignment-withdrawal cancellation** — for each `Disabled` outcome, cancel that group's `PENDING` jobs, per section 14.3. `RUNNING` jobs are not touched | **BE-04** |
| 10 | early return **if and only if** neither the package nor any lifecycle call changed anything — zero publisher `UPDATE`s, no token movement, no audit row, no job, neither publisher trigger fires | BE-03 |
| 11 | **exactly one** publisher `UPDATE`, carrying the package only when changed and always the strictly-increasing token, returning the row | BE-03 |
| 12 | **exactly one** audit row for the whole committed change, with the caller-supplied `source` and `actor`, and the **unwidened** three-key canonical before/after state | BE-03 |
| 13 | **commit** and return the configuration as it now stands | BE-03 |

**Why 9a–9c precede the publisher `UPDATE`.** Step 11 fires the `AFTER UPDATE`
`set_work_updated_at_with_relations` trigger, whose single set-based statement
takes row locks on all N of the publisher's work rows and holds them until
commit. Placing the job writes *after* it would extend the time those N locks are
held by the whole of the job insertion. Placing them before costs nothing and
shortens the widest part of the lock footprint. The ordering is a deliberate,
reasoned choice, not an arbitrary insertion point, and section 25.7 requires the
statement order to be asserted.

**The audit JSON is not widened.** BE-03 section 8.2 fixes the canonical key set
at exactly `subscriptionPackage`, `enabledDistributionPlatforms` and
`configurationVersion` and forbids widening it. Job creation is recorded in
`distribution_job`, which is the durable, queryable, typed record of it; adding a
job key to the audit JSON would duplicate that state in an un-indexed form and
break an approved invariant. Section 25.7 requires the key-set assertion to still
pass after a job-creating change.

### 10.2 Lock ordering and write footprint

**Application lock order is unchanged: `publisher` row first, everything else
after.** Every BE-04 write inside the coordinator happens after `lock_publisher`,
so the order is `publisher` → `distribution_job` → `distribution_job_target`.
BE-04 introduces no explicit row lock on the configuration path; its inserts take
only the ordinary unique-index insertion locks, released at commit.

**The worker path takes a disjoint set of locks.** A worker claims, completes,
fails or is recovered by locking `distribution_job` rows only. It never takes the
publisher row lock, never reads `publisher` for update, and never writes
`publisher_distribution_platform`. The two paths therefore cannot form a lock
cycle:

```text
configuration path:  publisher  ->  distribution_job (+ target)
worker path:                        distribution_job (+ attempt)
cancellation path:                  distribution_job (+ attempt)
```

Any future code path that would lock a `distribution_job` row before its
publisher row, or lock a publisher row from the worker path, is a lock-order
inversion and must be stopped rather than merged (stop condition 8).

**The real transaction write footprint is unchanged in shape and grows only by a
bounded amount.** Section 2.2 item 13 already establishes that a committed
configuration change writes:

```text
one publisher row
+ bounded configuration/audit rows
+ N related work rows
```

BE-04 adds, at most:

```text
+ G job rows
+ T target rows
+ C cancelled-job rows and their closed attempt rows
```

where `G` is the number of qualifying activated groups in this one replacement
(at most 16, the number of linked groups in the closed 17-value inventory), `T`
is the number of their `AutomaticPush` members (at most 17), and `C` is the
number of `PENDING` jobs the same replacement withdrew. All three are bounded by
the closed inventory and by that publisher's own pending work; **none grows with
the number of publishers, works or requests**. It remains **wrong** to describe
this transaction as touching only one publisher row, and BE-04 inherits, without
solving, all four consequences BE-03 section 7.8 records:

1. the row-lock footprint grows with catalogue size, because of the trigger;
2. transaction duration may grow with catalogue size, for the same reason;
3. the publisher `FOR UPDATE` lock is held while the trigger's set-based `UPDATE`
   runs, so concurrent configuration writers for one publisher serialize behind
   all of it;
4. no production duration figure and no safe catalogue-size threshold is stated
   here, because neither is derivable from the repository. Section 25.7 requires
   a measurement in a disposable environment, explicitly not as a production
   prediction.

BE-04 must not attempt to solve any of the four by altering the shared publisher
triggers, moving `subscription_package`, or moving the configuration token. If
the measured behaviour is judged materially unacceptable, that is stop condition
9 — `BLOCKED`, with measurements attached and a separate architecture escalation.

### 10.3 Invariants that follow from the placement

These are consequences of section 10.1, not additional requirements, and each is
independently testable:

1. **A job cannot exist without its desired-state change.** Both are in one
   transaction; a rollback loses both.
2. **A desired-state change cannot commit without the job it qualified for.**
   Same reason, in the other direction.
3. **A job cannot exist without a token bump and exactly one audit row.**
   Creation requires `Activated`, which implies `changed()`, which forces step 11
   and step 12.
4. **A stale or rejected request creates no job**, because steps 5 and 7 return
   before step 9.
5. **A true no-op creates no job**, because it produces no `Activated` outcome.
6. **Job creation never causes a second publisher `UPDATE`** and therefore never
   causes a second work-freshness cascade: BE-04 adds no publisher write.

## 11. Job state machine

### 11.1 States

| Status | Meaning | Claim fields | `completed_at` |
|---|---|---|---|
| `PENDING` | durable work exists and is not claimed; claimable once `available_at` has passed and eligibility holds | all NULL | NULL |
| `RUNNING` | claimed by one worker under a live or expired lease | all NOT NULL | NULL |
| `SUCCEEDED` | terminal; the worker reported success | all NULL | NOT NULL |
| `FAILED` | terminal; the worker reported a non-retryable failure, or the retry budget is exhausted | all NULL | NOT NULL |
| `CANCELLED` | terminal; withdrawn administratively or by assignment disable | all NULL | NOT NULL |

`distribution_job_claim_state_check` and `distribution_job_completed_at_check`
make both right-hand columns database facts rather than conventions.

### 11.2 Transition table

This graph is **complete**. Any transition not listed is illegal and is rejected
by section 11.6.

| # | From | To | Trigger | Effects |
|---:|---|---|---|---|
| T0 | — | `PENDING` | qualifying activation, inside the coordinator transaction (section 10.1 step 9b) | job + ≥1 target rows; `attempt_count = 0`; `available_at = CURRENT_TIMESTAMP`; all claim fields NULL |
| T1 | `PENDING` | `RUNNING` | `claimDistributionJobs` selects the job (section 12.3) | mint `claim_token`; `claimed_by = PolicyContext::user_id()`; `claimed_at = CURRENT_TIMESTAMP`; `lease_expires_at = claimed_at + lease`; `attempt_count += 1`; **insert one attempt row** with `attempt_number = attempt_count`, the same token and identity |
| T2 | `RUNNING` | `SUCCEEDED` | `completeDistributionJob` with the **current** token | `completed_at = CURRENT_TIMESTAMP`; clear all claim fields; clear `last_error_*`; close the open attempt with `result = 'SUCCEEDED'` |
| T3 | `RUNNING` | `PENDING` | `failDistributionJob` with the current token, `retryable = true`, and `attempt_count < DISTRIBUTION_JOB_MAX_ATTEMPTS` | clear all claim fields; `completed_at` stays NULL; `available_at = CURRENT_TIMESTAMP + backoff(attempt_count)`; set `last_error_code`/`last_error_detail`; close the open attempt with `result = 'FAILED'` and the same sanitized error |
| T4 | `RUNNING` | `FAILED` | `failDistributionJob` with the current token, and (`retryable = false` **or** `attempt_count >= DISTRIBUTION_JOB_MAX_ATTEMPTS`) | `completed_at = CURRENT_TIMESTAMP`; clear all claim fields; set `last_error_*`; close the open attempt with `result = 'FAILED'` |
| T5 | `RUNNING` | `PENDING` | lease expiry recovery during any claim call (section 12.2) | clear all claim fields; `available_at = CURRENT_TIMESTAMP`; **`attempt_count` is not decremented**; close the open attempt with `result = 'ABANDONED'`; `last_error_*` untouched |
| T6 | `PENDING` | `CANCELLED` | `cancelDistributionJob` (superuser) | `completed_at = CURRENT_TIMESTAMP`; `cancellation_reason = 'ADMINISTRATIVE'`; no open attempt exists to close |
| T7 | `RUNNING` | `CANCELLED` | `cancelDistributionJob` (superuser), live **or** expired lease | `completed_at = CURRENT_TIMESTAMP`; `cancellation_reason = 'ADMINISTRATIVE'`; **clear all claim fields, invalidating the holder's token**; close the open attempt with `result = 'CANCELLED'` |
| T8 | `PENDING` | `CANCELLED` | assignment withdrawal inside the coordinator transaction (section 14.3) | `completed_at = CURRENT_TIMESTAMP`; `cancellation_reason = 'ASSIGNMENT_DISABLED'` |

T5 deliberately does **not** decrement `attempt_count`: an abandoned attempt
consumed a real try and must count against the budget, otherwise a worker that
crashes reliably would retry for ever.

T3 and T5 both land in `PENDING`, and their difference is exactly the attempt
result recorded (`FAILED` versus `ABANDONED`) and whether `last_error_*` moved.
That is the whole reason `distribution_job_attempt_result` carries four values.

### 11.3 Attempt lifecycle

- **Creation is atomic with the claim.** T1 inserts the attempt row in the same
  statement sequence, in the same transaction, as the `UPDATE` that set
  `RUNNING`. There is no window in which a job is `RUNNING` with no open attempt.
- **`attempt_number` is the post-increment `attempt_count`**, taken from the
  claim `UPDATE`'s `RETURNING`, so the ordinal is derived from the same
  statement that produced it and `UNIQUE (distribution_job_id, attempt_number)`
  makes a duplicate impossible.
- **Closure is write-once.** Every closing statement predicates on
  `claim_token = $token AND finished_at IS NULL`. A repeat affects zero rows.
- **Exactly one attempt is open at a time**, because a job has a token only while
  `RUNNING`, `UNIQUE (claim_token)` binds a token to one attempt, and every path
  that leaves `RUNNING` closes the open attempt in the same statement sequence.
- **History is never deleted or rewritten.** Attempts accumulate across retries
  and remain readable after the job terminalizes.

### 11.4 Retry and backoff

- **Retry budget**: `DISTRIBUTION_JOB_MAX_ATTEMPTS = 5`. Bounded so that a
  permanently failing destination cannot retry for ever, and large enough that a
  transient outage spanning the full backoff window is survived. It is a
  code-owned constant, so changing it is a reviewed specification change (section
  7.6).
- **Backoff representation is an absolute `available_at` timestamp**, never a
  stored delay and never a worker-side computation. The retry schedule is
  therefore a database fact that the staff report can show and an operator can
  inspect, and no two workers can disagree about when a job becomes due.
- **Curve**, computed server-side at T3:

  ```text
  backoff(n) = min(DISTRIBUTION_JOB_RETRY_BASE_SECONDS * 2^(n - 1),
                   DISTRIBUTION_JOB_RETRY_MAX_SECONDS)
  ```

  with `n` the just-completed `attempt_count`. With base 300 s and cap 21 600 s
  the schedule is 5 min, 10 min, 20 min, 40 min for attempts 1–4; attempt 5 is
  terminal, so the cap is not reached by the current budget and exists so the
  curve stays correct if the budget is ever raised.
- Retry after T5 (abandonment) uses `available_at = CURRENT_TIMESTAMP` with no
  backoff: the job was never reported failed, only orphaned, and delaying
  recovery of a crashed worker's work serves nothing.

### 11.5 Lease expiry and abandoned-worker recovery

A lease expires when `status = 'RUNNING' AND lease_expires_at <= CURRENT_TIMESTAMP`.
Expiry is **not** self-executing: PostgreSQL runs no timer, and BE-04 adds no
scheduler, no background task and no cron. Recovery is performed by the claim
operation itself, as step A of section 12.2, which means:

- recovery happens exactly when it can be useful — when a worker is asking for
  work;
- an expired lease costs nothing while no worker is running;
- no additional process, permission or deployment surface is introduced.

Recovery is T5. The previously claiming worker is not notified and needs no
notification: its token is cleared, so every subsequent statement it issues is
rejected as stale (section 12.6).

**No heartbeat or lease-extension operation is added.** A worker sizes its lease
request to its own batch behaviour through `leaseSeconds` (section 12.5), and a
job that outlives its lease is recovered and retried — which is safe precisely
because the programme's acceptance matrix already requires DIS-02's
back-catalogue worker to be **at-least-once safe**. Adding a fourth worker
operation to avoid a hazard another task is already required to tolerate would be
API invention. If DIS-02's measured behaviour later shows a heartbeat is
genuinely required, that is a bounded addition under DIS-02's own specification,
recorded here as deferred rather than pre-built.

### 11.6 Invalid transitions

| Attempt | Result |
|---|---|
| complete/fail/cancel a job that does not exist | `ThothError::EntityNotFound` |
| complete/fail a job in `SUCCEEDED`, `FAILED` or `CANCELLED` | `ThothError::DistributionJobAlreadyTerminal(<status>)` |
| cancel a job in `SUCCEEDED`, `FAILED` or `CANCELLED` — including cancelling an already-`CANCELLED` job | `ThothError::DistributionJobAlreadyTerminal(<status>)` |
| complete/fail a job in `PENDING` (no current claim) | `ThothError::StaleDistributionJobClaim` |
| complete/fail a `RUNNING` job with a token that is not its current `claim_token` | `ThothError::StaleDistributionJobClaim` |
| claim a job that is `RUNNING` with a live lease | not an error — the job is simply not selected, and the claim returns fewer jobs |
| claim a job whose targets are no longer enabled under its activation | not an error — not selected (section 12.4) |
| any of the above with an unparseable or absent claim token | rejected by Juniper as a malformed `Uuid!` before the resolver runs |

`PENDING` and "held by another worker" deliberately produce the **same** error.
Distinguishing them would tell a caller whether another worker currently holds
the job, which it has no need to know and which is exactly the information that
makes a stale caller retry aggressively. Failing identically is the fail-closed
choice.

Repeat calls are defined rather than merely tolerated: a second
`completeDistributionJob` with the same token after a successful first returns
`DistributionJobAlreadyTerminal("SUCCEEDED")` and changes nothing, because the
job is no longer `RUNNING` and its `claim_token` is NULL. There is no path by
which two calls produce contradictory state.

## 12. Claims and leases

### 12.1 Mechanism selection

Claims must be atomic, exclusive, bounded, lease-based and **database-enforced**.
The selected mechanism is `SELECT ... FOR UPDATE SKIP LOCKED` feeding an
`UPDATE`, in one transaction on one connection.

It is selected on evidence, not because it is the common answer. The repository's
own [`thoth-api/AGENTS.md`](../../../../thoth-api/AGENTS.md) section 5 lists it
among the approved concurrency primitives, and the alternatives were each
evaluated against BE-04's actual requirement — *select a bounded batch of
eligible rows, exclusively, without blocking a concurrent worker*:

| Alternative | Disposition |
|---|---|
| plain `FOR UPDATE` (no `SKIP LOCKED`) | **Rejected.** Overlapping workers block on the same head-of-queue rows, so throughput collapses to one worker and a slow claim stalls every other worker. Exclusivity is achieved at the cost of the concurrency the feature exists to provide. |
| optimistic `UPDATE ... WHERE status='PENDING' AND claim_token IS NULL` with application retry | **Rejected.** Correct for a single row, but it cannot claim a deterministic bounded *batch* without repeated conflict-and-retry loops, and under contention the set each worker obtains becomes non-deterministic, which defeats the deterministic ordering requirement. |
| `pg_advisory_xact_lock`, as used by `model/work_relation/crud.rs` | **Rejected.** Advisory locks serialize a logical operation keyed by a hash; they do not select rows. Using one here would serialize all claiming across all publishers — the plain-`FOR UPDATE` problem with an extra indirection. |
| an external queue, workflow or object store as the claim owner | **Prohibited.** Root `AGENTS.md` section 10 forbids any non-PostgreSQL durable owner of jobs, leases and claims. |
| `FOR UPDATE SKIP LOCKED` | **Selected.** Gives exclusive, non-blocking, deterministically ordered bounded batch selection with the lease and token written in the same transaction. |

### 12.2 Step A — lease recovery

Executed first inside the claim transaction, before selection, so a worker's
request also recovers work orphaned by a crashed worker:

```sql
WITH expired AS (
    SELECT distribution_job_id, claim_token
    FROM distribution_job
    WHERE status = 'RUNNING'
      AND lease_expires_at <= CURRENT_TIMESTAMP
    ORDER BY lease_expires_at ASC, distribution_job_id ASC
    FOR UPDATE SKIP LOCKED
    LIMIT $recovery_limit
),
closed AS (
    UPDATE distribution_job_attempt a
    SET finished_at = CURRENT_TIMESTAMP,
        result = 'ABANDONED'
    FROM expired e
    WHERE a.claim_token = e.claim_token
      AND a.finished_at IS NULL
    RETURNING a.distribution_job_id
)
UPDATE distribution_job j
SET status = 'PENDING',
    claim_token = NULL,
    claimed_by = NULL,
    claimed_at = NULL,
    lease_expires_at = NULL,
    available_at = CURRENT_TIMESTAMP
FROM expired e
WHERE j.distribution_job_id = e.distribution_job_id;
```

`$recovery_limit` is `DISTRIBUTION_JOB_LEASE_RECOVERY_BATCH = 50`, so one claim
call performs a bounded amount of recovery. The attempt closure runs in the same
statement as the job reset, so an abandoned attempt can never be left open.

### 12.3 Step B — claim selection

```sql
WITH eligible AS (
    SELECT j.distribution_job_id
    FROM distribution_job j
    WHERE j.status = 'PENDING'
      AND j.available_at <= CURRENT_TIMESTAMP
      AND (cardinality($kinds) = 0 OR j.kind = ANY($kinds))
      AND <eligibility predicate of section 12.4>
    ORDER BY j.available_at ASC, j.distribution_job_id ASC
    FOR UPDATE OF j SKIP LOCKED
    LIMIT $batch
),
claimed AS (
    UPDATE distribution_job j
    SET status = 'RUNNING',
        claim_token = public.uuid_generate_v4(),
        claimed_by = $worker,
        claimed_at = CURRENT_TIMESTAMP,
        lease_expires_at = CURRENT_TIMESTAMP + ($lease_seconds * interval '1 second'),
        attempt_count = j.attempt_count + 1
    FROM eligible e
    WHERE j.distribution_job_id = e.distribution_job_id
    RETURNING j.distribution_job_id, j.claim_token, j.claimed_by,
              j.claimed_at, j.attempt_count
)
INSERT INTO distribution_job_attempt
    (distribution_job_id, attempt_number, claim_token, claimed_by, started_at)
SELECT distribution_job_id, attempt_count, claim_token, claimed_by, claimed_at
FROM claimed;
```

- **Deterministic claim ordering** is `available_at ASC, distribution_job_id ASC`
  — a total order, since `distribution_job_id` is unique — supported exactly by
  `distribution_job_claimable_idx`. Two workers running the same statement
  consider rows in the same order and differ only in which locked rows they skip.
- **`public.uuid_generate_v4()` is VOLATILE**, so it evaluates per row and each
  claimed job receives its own distinct token in the one statement.
- **Attempt creation is atomic with the claim**: the same statement sequence, the
  same transaction, deriving `attempt_number` from the claim's own `RETURNING`.
- **`claimed_by` is `$worker` = `PolicyContext::user_id()`**, taken from the
  authenticated identity and never from a GraphQL input, so it cannot be spoofed
  and it follows BE-03's actor precedent exactly (section 16.1).
- The claim response is then read back for the returned job ids, including target
  rows in canonical order.

### 12.4 Eligibility predicate

A `PENDING`, due job is claimable **only if every one of its targets is still an
enabled assignment for its publisher, under the job's own activation**:

```sql
NOT EXISTS (
    SELECT 1
    FROM distribution_job_target t
    WHERE t.distribution_job_id = j.distribution_job_id
      AND NOT EXISTS (
          SELECT 1
          FROM publisher_distribution_platform p
          WHERE p.publisher_id = j.publisher_id
            AND p.platform = t.platform
            AND p.enabled
            AND p.activation_id = j.activation_id
      )
)
```

Three properties, each deliberate:

1. **`enabled` is required**, so a destination disabled while its job was
   `RUNNING` — and later recovered to `PENDING` by lease expiry — is never picked
   up again. Section 14.3's cancellation handles the ordinary `PENDING` case
   deterministically; this predicate is the fail-closed backstop for every state
   reached by any other route.
2. **`activation_id` must match the job's**, so a disable/re-enable cycle cannot
   make an old job claimable alongside the new job its new activation created.
   Without this clause the same back catalogue could be pushed twice.
3. **Every target must qualify** (`NOT EXISTS ... NOT EXISTS`), not any target.
   Partial delivery to a subset of a linked group is not a state BE-04 will
   authorize.

The inner lookup is a primary-key probe on `publisher_distribution_platform`, so
the predicate costs one index probe per target and targets are bounded by the
17-value inventory.

A job made permanently unclaimable this way is **never silently deleted and never
silently mutated**. It remains `PENDING` and visible in the staff report, where a
superuser can cancel it explicitly (section 14).

### 12.5 Bounds

| Input | Default | Bound | Behaviour outside the bound |
|---|---:|---|---|
| `limit` (batch size) | `10` | `1 ..= 50` | clamped to the maximum; `limit <= 0` returns an empty claim |
| `leaseSeconds` | `900` | `60 ..= 3600` | clamped to the nearer bound |
| kinds filter | `[]` | closed enum | empty means "every kind" |

Both are **clamped rather than rejected**, and the field descriptions must say
so. The reasoning is stated rather than assumed: a worker that asks for slightly
too much should still make bounded progress, because erroring would put a
long-running automated process into a retry loop that delivers nothing, and the
bound is a server guarantee rather than a client contract. Fail-closed applies to
**authorization and state transitions**, where BE-04 rejects unconditionally; it
is not a reason to refuse work over a sizing argument.

### 12.6 Stale claim tokens

Every mutating worker statement predicates on **both** the token and the status:

```sql
UPDATE distribution_job
SET ...
WHERE distribution_job_id = $1
  AND status = 'RUNNING'
  AND claim_token = $2
```

and every attempt closure predicates on `claim_token = $2 AND finished_at IS NULL`.

When zero rows are affected, the resolver reads the row **inside the same
transaction** and classifies deterministically: absent ⇒ `EntityNotFound`;
terminal ⇒ `DistributionJobAlreadyTerminal(status)`; otherwise ⇒
`StaleDistributionJobClaim`.

A stale token therefore **cannot**, structurally rather than by convention:

| Prohibited effect | Why it is impossible |
|---|---|
| complete a newer attempt | the `UPDATE` requires `claim_token = $stale`, which is no longer the job's token |
| fail a newer attempt | same predicate |
| retry a newer attempt | retry is a branch of the same `fail` statement and shares its predicate |
| overwrite worker identity | `claimed_by` is only ever written by the claim statement, which mints a fresh token in the same write |
| overwrite the current lease | `lease_expires_at` is only ever written by the claim statement |
| mutate a terminal result | terminal rows have `status <> 'RUNNING'` and `claim_token IS NULL`, so no predicate can match |
| close someone else's attempt | `UNIQUE (claim_token)` binds a token to exactly one attempt row, for all time |

## 13. Retry and idempotency contract

"Retries are idempotent" is decomposed into four separately testable contracts.

### 13.1 Creation idempotency

Repeated observation of the same logical activation creates no duplicate job.
Guaranteed by the section 8.3 unique constraint plus `ON CONFLICT DO NOTHING`,
independently of the publisher row lock; the lock additionally makes the race
unreachable through the coordinator. Evidence: sections 25.5 and 25.6, including
a **real concurrent** two-connection test.

### 13.2 Claim idempotency and concurrency

At most one valid claim token exists per job at any instant, and each token maps
to exactly one attempt row for all time. Guaranteed by
`distribution_job_claim_state_check` (token non-null iff `RUNNING`),
`FOR UPDATE SKIP LOCKED` (no two transactions select the same row) and
`UNIQUE (claim_token)` on attempts. Evidence: section 25.8, with real concurrent
connections.

### 13.3 Completion and failure idempotency

| Sequence | Result |
|---|---|
| `complete(token)` then `complete(token)` | first succeeds; second returns `DistributionJobAlreadyTerminal("SUCCEEDED")`; no state change |
| `complete(token)` then `fail(token, ...)` | second returns `DistributionJobAlreadyTerminal("SUCCEEDED")`; no state change |
| `fail(token, retryable=false)` then `fail(token, ...)` | second returns `DistributionJobAlreadyTerminal("FAILED")`; no state change |
| `fail(token, retryable=true)` then `fail(token, ...)` | job is `PENDING` with `claim_token = NULL`; second returns `StaleDistributionJobClaim`; no state change |
| `complete(stale_token)` after re-claim | `StaleDistributionJobClaim`; the newer attempt is untouched |

No sequence produces contradictory state, and none creates a second attempt row
or a second terminal result.

### 13.4 Retry semantics

**Retry is encoded by `failDistributionJob(retryable: true)`. There is no
separate GraphQL retry mutation.** The justification is specific rather than
stylistic: the only actor that knows whether a failure is retryable is the worker
that observed it, at the moment it observed it, and the T3 transition is fully
expressed by the fail operation. A separate `retryDistributionJob` would either
duplicate that judgement or require a human to re-drive work the worker has
already classified — and the approved design's naming of three worker operations
is satisfied exactly. Adding a fourth to mirror a verb in the epic would be API
invention, which section 16.4 forbids.

The resulting contract is nevertheless fully testable and section 25.8 requires
it to be tested directly: `fail(retryable=true)` at attempts 1–4 returns the job
to `PENDING` with a computed `available_at`; the same call at attempt 5
terminalizes to `FAILED`; each retry adds exactly one closed attempt row; and a
repeat retry behaves per section 13.3.

**Reopening a terminal `FAILED` job is deliberately not supported.** Recovery
from an exhausted onboarding is a genuine re-activation — disable, then re-enable
— which mints a new `activation_id`, yields a new deduplication key and creates a
new job through the same audited configuration path as every other change. That
keeps every job's history immutable, keeps one creation path, and avoids an
operation that reopens a terminal state and would break section 13.3's
guarantees. It is recorded as a deferred capability with its reason, not as an
oversight.

## 14. Cancellation

### 14.1 Administrative cancellation

- **Who may cancel:** `SUPERUSER` only. Not `DISSEMINATION_WORKER`, not any
  publisher-scoped role, not anonymous (section 15.2).
- **Operation:** one additive superuser GraphQL mutation,
  `cancelDistributionJob` (section 16.1). It is justified by an existing approved
  requirement rather than invented: the
  [rollout plan](../../../publisher-services/rollout-plan.md) stage 6 rollback
  procedure requires an operator to "cancel pending pilot jobs", and no other
  operator surface exists for it.
- **Cancellable states:** `PENDING` (T6) and `RUNNING` (T7), the latter whether
  the lease is live or expired. Every terminal state is rejected with
  `DistributionJobAlreadyTerminal`, including cancelling an already-`CANCELLED`
  job — the operation fails closed rather than reporting a comfortable idempotent
  success.
- **Behaviour with a current claim (T7):** all claim fields are cleared in the
  same statement, which **invalidates the holder's token immediately**. The open
  attempt is closed with `result = 'CANCELLED'` and its `finished_at`. The
  in-flight worker's next `complete` or `fail` is rejected as
  `StaleDistributionJobClaim`; it is not notified, and needs no notification.
- **Expired lease:** identical handling. The attempt is closed as `CANCELLED`,
  not `ABANDONED`, because the attempt's result names the event that closed it
  (section 7.4) and cancellation is what closed this one.
- **Target rows remain immutable.** Cancellation deletes and rewrites nothing.
- **Cancellation is terminal and cannot be reopened or retried.** A new
  onboarding requires a genuine new activation, exactly as in section 13.4.
- **Job and attempt history is never deleted.** A cancelled job and all its
  attempts remain readable in the staff report.

**Cancellation cannot undo an already-performed external upload.** If the worker
had begun or completed deposits before its token was invalidated, those deposits
exist at the destination and BE-04 neither knows about them nor can withdraw
them. Cancellation withdraws *durable Thoth-side work*, nothing else. The field
description and the operational note in section 21 must say so plainly, and
external reconciliation after cancelling a `RUNNING` job is an operator
responsibility that the rollout plan's stage 6 already assigns
("reconcile partial external delivery").

### 14.2 Cancellation from every relevant state

| State at cancel | Allowed | Job effect | Attempt effect |
|---|---|---|---|
| `PENDING`, never claimed | YES (T6) | `CANCELLED`, `completed_at` set, reason `ADMINISTRATIVE` | none open; earlier closed attempts untouched |
| `PENDING`, after a retry | YES (T6) | as above | earlier closed attempts untouched |
| `RUNNING`, live lease | YES (T7) | `CANCELLED`, claim fields cleared | open attempt closed `CANCELLED` |
| `RUNNING`, expired lease | YES (T7) | as above | open attempt closed `CANCELLED` |
| `SUCCEEDED` | NO | unchanged | unchanged |
| `FAILED` | NO | unchanged | unchanged |
| `CANCELLED` | NO | unchanged | unchanged |

### 14.3 Assignment-disable interaction

When the coordinator's `disable_on` reports `Disabled` for a linked group, then
**in the same transaction**, at step 9c:

```sql
UPDATE distribution_job j
SET status = 'CANCELLED',
    completed_at = CURRENT_TIMESTAMP,
    cancellation_reason = 'ASSIGNMENT_DISABLED'
WHERE j.publisher_id = $publisher
  AND j.status = 'PENDING'
  AND EXISTS (
      SELECT 1 FROM distribution_job_target t
      WHERE t.distribution_job_id = j.distribution_job_id
        AND t.platform = ANY($disabled_group_members)
  );
```

The rules, and the reason for each:

1. **`PENDING` jobs for the disabled group are cancelled (T8).** The desired
   state that justified the onboarding has been withdrawn, so leaving the work
   claimable would let a worker push a back catalogue to a destination the
   publisher has just switched off. Cancelling deterministically, in the same
   transaction, is the honest record of what happened, and
   `ASSIGNMENT_DISABLED` distinguishes it from an operator's decision.
2. **`RUNNING` jobs are not touched.** External work may be in flight, and
   cancelling cannot undo an upload (section 14.1). The claiming worker
   terminalizes its own attempt normally. If instead its lease expires, T5
   returns the job to `PENDING` — where section 12.4's eligibility predicate
   makes it unclaimable, so it waits visibly for an operator rather than silently
   resuming.
3. **`SUCCEEDED`, `FAILED` and already-`CANCELLED` jobs are not touched.**
4. **Jobs of other publishers are never touched**, because the statement is
   scoped by `publisher_id` under the publisher row lock.
5. **The two mechanisms are deliberately overlapping, not redundant.** Rule 1 is
   the clean deterministic behaviour for the ordinary case; section 12.4 is the
   database-side fail-closed invariant that holds for every state reached by any
   route, including ones not yet imagined. Avoiding an application-side rule
   without a matching database-side guarantee is exactly what
   `thoth-api/AGENTS.md` section 3 requires.

Section 25.9 requires both the pending-disable and the running-disable cases to
be tested explicitly, including the post-expiry unclaimability of the running
case.

## 15. Worker authorization

### 15.1 The role

One new role, added to the existing enum in `thoth-api/src/policy.rs`:

```rust
pub(crate) enum Role {
    Superuser,
    PublisherAdmin,
    PublisherUser,
    WorkLifecycle,
    CdnWrite,
    DisseminationWorker,   // BE-04
}
```

| Property | Value |
|---|---|
| Exact role code | `DISSEMINATION_WORKER` (from the existing `#[strum(serialize_all = "SCREAMING_SNAKE_CASE")]`) |
| Scope | **Unscoped** ZITADEL project role, checked exactly as `SUPERUSER` is — by key presence in `project_roles`, not by organisation |
| Permitted operations | `claimDistributionJobs`, `completeDistributionJob`, `failDistributionJob` — and nothing else |
| Forbidden operations | every publisher-scoped read or write; `replacePublisherServiceConfiguration`; `publisherServiceConfiguration`; the staff report and its count; `cancelDistributionJob`; every existing mutation in `MutationRoot`; every file, CDN, work, publisher, imprint or metadata operation |
| Publisher permissions conferred | **none** — `PublisherPermissions` is untouched, so `publisher_admin`, `work_lifecycle` and `cdn_write` all remain `false` for a worker-only account |
| Provisioning dependency | the role must exist in the ZITADEL project and be granted to the worker's machine account before any worker operation can succeed |
| Deployment prerequisite | the worker must present a token whose introspection yields that project role; until then every worker operation denies |

Why the role is unscoped: a dissemination worker operates across publishers by
definition, so a per-organisation grant would have to be re-issued for every
publisher and would fail closed on the first unenrolled one. The unscoped-check
pattern is not new — section 2.2 item 18 establishes that `is_superuser()`
already implements it — so this is the existing mechanism applied to a second
role, not a new mechanism.

Implementation shape, kept deliberately minimal (non-goal 8):

- a private `UserAccess::has_unscoped_role(&self, role: Role) -> bool` expressing
  the key-presence check once;
- `is_superuser()` re-expressed in terms of it with **byte-identical behaviour**,
  proven by the existing `policy.rs` tests continuing to pass unchanged;
- `is_dissemination_worker()` alongside it;
- `PolicyContext::require_dissemination_worker() -> ThothResult<&IntrospectedUser>`,
  mirroring `require_superuser()`;
- **`publisher_org_ids()` must skip `DISSEMINATION_WORKER` as well as
  `SUPERUSER`.** It currently skips only the superuser key while collecting org
  ids from every other role, so without this change a worker account would appear
  to hold publisher organisations in the frontend switcher list. This is a real
  behavioural detail, not a cosmetic one, and section 25.9 requires a test.

`has_unscoped_role` stays private to the module. It must not be exposed as a
general service-role API, and no `ServiceRole` type, role registry or
machine-identity table is introduced.

### 15.2 Complete authorization matrix

| Caller | `claim` | `complete` | `fail` | `cancel` | staff report incl. job fields | BE-03 own-publisher config read |
|---|---|---|---|---|---|---|
| anonymous | DENY | DENY | DENY | DENY | DENY | DENY |
| authenticated, no applicable role | DENY | DENY | DENY | DENY | DENY | DENY |
| `PUBLISHER_USER` for the target publisher | DENY | DENY | DENY | DENY | DENY | ALLOW (unchanged, config only) |
| `PUBLISHER_USER` for another publisher | DENY | DENY | DENY | DENY | DENY | DENY |
| `PUBLISHER_ADMIN` without `PUBLISHER_USER` | DENY | DENY | DENY | DENY | DENY | DENY (unchanged) |
| `WORK_LIFECYCLE` without `PUBLISHER_USER` | DENY | DENY | DENY | DENY | DENY | DENY (unchanged) |
| `CDN_WRITE` without `PUBLISHER_USER` | DENY | DENY | DENY | DENY | DENY | DENY (unchanged) |
| `SUPERUSER` without `DISSEMINATION_WORKER` | **DENY** | **DENY** | **DENY** | **ALLOW** | ALLOW | ALLOW |
| `DISSEMINATION_WORKER` only | ALLOW | ALLOW | ALLOW | **DENY** | **DENY** | **DENY** |
| `SUPERUSER` + `DISSEMINATION_WORKER` | ALLOW | ALLOW | ALLOW | ALLOW | ALLOW | ALLOW |
| invalid, expired or unintrospectable token | DENY | DENY | DENY | DENY | DENY | DENY |

An introspection failure yields no `IntrospectedUser`, so
`require_authentication()` returns `Unauthorised` and every row above collapses
to the anonymous row. An authentication failure never broadens access.

Every authorization decision is taken **at resolver entry, before any database
access**, exactly as BE-03 does.

### 15.3 `SUPERUSER` does not receive worker powers

This is stated as a decision with reasons, because the instruction to justify it
is the point:

1. **The threat boundaries differ.** The worker role exists so a long-running
   automated process holding durable credentials can transition job state and do
   nothing else. A human superuser has no operational need to *claim* a job, and
   a claim taken by a human strands real work under a lease until it expires.
2. **The programme has already fixed "no role implies another"** (BE-03 section
   11.1). `require_role_for_publisher`'s superuser short-circuit exists because
   publisher scoping is an *ownership* question that a global administrator
   legitimately transcends. Claiming a job is not an ownership question, so that
   reasoning does not transfer and must not be copied by analogy.
3. **Least privilege is a repository requirement**, not a preference:
   `thoth-api/AGENTS.md` section 7 requires service roles to be least-privilege
   and distinct where read, ingest and synchronization have different powers.
4. **No operator capability is lost.** A superuser retains everything an operator
   actually needs: the complete job-aware staff report, and cancellation.
5. **The composition escape hatch already exists.** A superuser account that
   genuinely must act as a worker is granted `DISSEMINATION_WORKER` explicitly;
   roles compose additively in the merged model, so nothing is unreachable.

### 15.4 Rejected alternatives

| Alternative | Disposition |
|---|---|
| reuse `CDN_WRITE` | **Rejected.** It is publisher-scoped, so a cross-publisher worker would need a grant per publisher and would fail closed on the first missing one; and it authorizes file upload and modification, which a job-state worker must never hold. It would simultaneously over-grant and under-scope. Being "machine-adjacent" is not a reason. |
| reuse `SUPERUSER` | **Rejected.** It grants every operation in the API to a credential that lives in an automated process. See section 15.3. |
| a publisher-scoped worker role | **Rejected.** A back-catalogue worker claims across publishers; scoping it would require re-granting per publisher and would silently skip unenrolled publishers, which is a fail-*open* failure mode for coverage. |
| a generic `SERVICE`/`MACHINE` role shared by future workers | **Rejected**, and prohibited by non-goal 7. It is exactly the shared service-role convention section 6.2 forbids, and it would grant a future unrelated worker BE-04's powers by default. |
| a bespoke API-key or token table in Thoth | **Rejected.** It would add credential storage to a repository that has none, duplicating the identity provider, and is prohibited by non-goal 8. |

### 15.5 Provisioning and prerequisites

- BE-04 implementation **may** add `DISSEMINATION_WORKER` to the role list in
  `src/bin/commands/zitadel.rs` `setup`, so a newly bootstrapped project declares
  it. It **must not** run that command, must not grant the role to any account,
  and must not change any identity-provider configuration.
- The pre-existing absence of `WORK_LIFECYCLE` and `CDN_WRITE` from that same
  list (section 2.2 item 19) is **not** repaired here (non-goal 22). It is
  recorded as an observed gap for a separate task.
- Until the role is provisioned **and** granted, every worker operation denies.
  The API therefore merges inert: no worker exists until DIS-02, and no
  credential is created by this task.
- Worker credential issuance, rotation and revocation belong to deployment and
  runbook work, not to this specification (section 23).

## 16. Worker GraphQL API

### 16.1 Operations

Four additive mutations. Nothing else is added to `MutationRoot`, and **no new
top-level query is added**: durable job state is reachable only through the
existing staff report (section 17) and through these mutations' own payloads.

```graphql
"Claim a bounded batch of due distribution jobs. Requires the DISSEMINATION_WORKER role."
claimDistributionJobs(data: ClaimDistributionJobsInput!): [ClaimedDistributionJob!]!

"Record successful completion of a claimed distribution job. Requires the DISSEMINATION_WORKER role."
completeDistributionJob(data: CompleteDistributionJobInput!): DistributionJob!

"Record failure of a claimed distribution job, optionally scheduling a retry. Requires the DISSEMINATION_WORKER role."
failDistributionJob(data: FailDistributionJobInput!): DistributionJob!

"Cancel a pending or running distribution job. Superuser only. This does not undo any external delivery already performed."
cancelDistributionJob(data: CancelDistributionJobInput!): DistributionJob!
```

```graphql
input ClaimDistributionJobsInput {
  "Maximum jobs to claim. Values above 50 are clamped to 50; values at or below 0 claim nothing"
  limit: Int = 10
  "Requested lease duration in seconds, clamped to the range 60 to 3600"
  leaseSeconds: Int = 900
  "If set, only claims jobs of these kinds. An empty list claims any kind"
  kinds: [DistributionJobKind!] = []
}

input CompleteDistributionJobInput {
  distributionJobId: Uuid!
  claimToken: Uuid!
}

input FailDistributionJobInput {
  distributionJobId: Uuid!
  claimToken: Uuid!
  "Stable machine-readable classification, matching ^[A-Z][A-Z0-9_]*$, at most 64 characters"
  errorCode: String!
  "Bounded human-readable diagnostic, truncated to 2048 characters. Must contain no credential, token, signed URL, response body or personal data"
  errorDetail: String
  "Whether the failure may be retried. A retryable failure returns the job to PENDING until the attempt budget is exhausted"
  retryable: Boolean! = true
}

input CancelDistributionJobInput {
  distributionJobId: Uuid!
}
```

**No worker identity is an input.** `claimed_by` is derived from
`PolicyContext::user_id()` of the authenticated worker, exactly as BE-03 derives
its audit `actor`. Accepting a worker-supplied identity would make the audit
field spoofable and would introduce a second identifier format; deriving it
introduces neither. Per-process attribution within one machine account is
deliberately not provided and is a separate decision if it is ever needed.

`limit` uses the repository's `Option<Vec<T>>`/`Int = N` argument convention and
the `[DistributionJobKind!] = []` list shape matches BE-03's merged
`[DistributionPlatform!] = []` siblings; BE-04 must not introduce a stricter
non-null-list convention.

### 16.2 Types

```graphql
"A durable unit of distribution work."
type DistributionJob {
  distributionJobId: Uuid!
  kind: DistributionJobKind!
  publisherId: Uuid!
  "Reserved for future work-level jobs; always null for PUBLISHER_BACK_CATALOGUE"
  workId: Uuid
  status: DistributionJobStatus!
  "Number of execution attempts started so far"
  attemptCount: Int!
  "Earliest time at which this job may be claimed"
  availableAt: Timestamp!
  "Destinations this job delivers to, in canonical platform order. Always at least one"
  targets: [DistributionJobTarget!]!
  "Recorded execution attempts, most recent first. Bounded by the attempt budget"
  attempts: [DistributionJobAttempt!]!
  claimedAt: Timestamp
  leaseExpiresAt: Timestamp
  completedAt: Timestamp
  cancellationReason: DistributionJobCancellationReason
  "Stable classification of the most recent failure"
  lastErrorCode: String
  "Bounded sanitized diagnostic for the most recent failure"
  lastErrorDetail: String
  createdAt: Timestamp!
  updatedAt: Timestamp!
}

"One destination of a distribution job."
type DistributionJobTarget {
  platform: DistributionPlatform!
  createdAt: Timestamp!
}

"One recorded execution attempt of a distribution job."
type DistributionJobAttempt {
  attemptNumber: Int!
  "Identity that held the claim for this attempt"
  claimedBy: String!
  startedAt: Timestamp!
  finishedAt: Timestamp
  "Null while the attempt is open"
  result: DistributionJobAttemptResult
  errorCode: String
  errorDetail: String
}

"A distribution job together with the claim it was just granted."
type ClaimedDistributionJob {
  job: DistributionJob!
  "Present this token to complete or fail the job. It is returned only here"
  claimToken: Uuid!
  leaseExpiresAt: Timestamp!
  "Ordinal of the attempt this claim started"
  attemptNumber: Int!
}
```

**`claimToken` is a field of `ClaimedDistributionJob` only and must never appear
on `DistributionJob`.** Exposing it on the job type would let any caller who can
read a job steal the live claim, which would defeat the whole lease model. This is
a binding non-exposure requirement (non-goal 16) and section 25.10 requires an
SDL assertion that `DistributionJob` has no `claimToken` field.

`claimedBy` appears only on `DistributionJobAttempt`, never on `DistributionJob`.
It is reachable by a superuser through the staff report and by a worker through
its own payload. That exposure is accepted as a reviewed conclusion: worker
identities are non-secret account identifiers, all workers share one trusted
machine role, and attempt history is unusable for diagnosis without knowing who
held the attempt.

`attempts` takes **no `limit` argument** and returns every attempt, most recent
first. That is safe by construction, not by hope: `attempt_count` is hard-bounded
by `DISTRIBUTION_JOB_MAX_ATTEMPTS`, so a job can never accumulate more than five
attempt rows.

### 16.3 Errors

Exactly **two** new `ThothError` variants and exactly **two** new
`into_field_error` arms:

| Variant | GraphQL `type` | Raised when |
|---|---|---|
| `ThothError::StaleDistributionJobClaim` | `STALE_DISTRIBUTION_JOB_CLAIM` (**new arm**) | the presented claim token is not the job's current token, or the job is not `RUNNING` |
| `ThothError::DistributionJobAlreadyTerminal(String)` | `DISTRIBUTION_JOB_TERMINAL` (**new arm**) | the job is `SUCCEEDED`, `FAILED` or `CANCELLED`; the payload carries the current status code |

Existing families keep their merged mappings:

| Condition | Error | GraphQL `type` |
|---|---|---|
| anonymous or wrongly roled caller | `ThothError::Unauthorised` (existing) | `NO_ACCESS`, message `Unauthorized` |
| job not found | `ThothError::EntityNotFound` (existing) | `INTERNAL_ERROR` (unchanged) |
| backend/database failure | `ThothError::DatabaseError` (existing) | `INTERNAL_ERROR` (unchanged) |
| malformed request shape | rejected by Juniper before the resolver | n/a |

Rules:

1. the two new types exist because a worker must distinguish "someone else owns
   this now, stop" from "this job is finished, stop" — the two require different
   client behaviour, and a generic `INTERNAL_ERROR` would make an automated
   worker retry indefinitely against a terminal job;
2. `EntityNotFound`'s `INTERNAL_ERROR` mapping is **not** changed. BE-03 section
   13 rule 2 already records that as a known limitation whose correction would
   alter merged contracts and normalize unrelated error families; BE-04 inherits
   the limitation rather than silently widening scope;
3. no error message may include SQL, table names, column names, driver text, a
   claim token, an actor identity, a credential, an endpoint or a bucket. The
   terminal error discloses only the status code, which the caller is entitled to
   know;
4. `StaleDistributionJobClaim` must **not** disclose the current token, the
   current holder, or whether one exists.

### 16.4 API-surface justification

Every operation added is justified against an approved requirement, and nothing
is added to mirror a verb:

| Operation | Justification |
|---|---|
| `claimDistributionJobs` | named by the approved design; no other way for a worker to obtain work |
| `completeDistributionJob` | named by the approved design; the only success path |
| `failDistributionJob` | named by the approved design; carries both the terminal-failure and the retry transitions (section 13.4) |
| `cancelDistributionJob` | required by the approved rollout plan's stage 6 rollback ("cancel pending pilot jobs"); no other operator surface exists |

Deliberately **not** added: a retry mutation (section 13.4); a heartbeat or
lease-extension mutation (section 11.5); a top-level job query (the staff report
covers every reachable need); a job-creation mutation (creation is exclusively a
consequence of a configuration change); any operation that reopens a terminal
state.

**No uploader execution belongs in these resolvers.** They store and transition
durable work only. No resolver may open a network connection to a distribution
platform, read or write a publication file, generate a feed or deposit, or invoke
an adapter. `thoth-dissemination` remains the execution engine.

## 17. Additive staff-report contract

### 17.1 Additions

BE-04 adds job-aware data **additively to BE-03's existing superuser staff
report**, exactly as BE-03 section 12.1 requires. One new field on one existing
type:

```graphql
type PublisherServiceConfigurationSummary {
  configuration: PublisherServiceConfiguration!          # unchanged
  lastChange: PublisherServiceConfigurationChange        # unchanged
  "Most recent publisher back-catalogue distribution job, or null if none exists"
  latestBackCatalogueJob: DistributionJob                # BE-04
}
```

`latestBackCatalogueJob` is the `DISTINCT ON (publisher_id)` most recent
`kind = PUBLISHER_BACK_CATALOGUE` job for that publisher, ordered
`created_at DESC, distribution_job_id DESC` — a total order, so the selection is
deterministic even for two jobs sharing a `created_at`.

Through it the report represents everything section 16 of the authoring
instruction requires:

| Required representation | Provided by |
|---|---|
| latest relevant publisher back-catalogue job state | `latestBackCatalogueJob.status` |
| pending onboarding | `status = PENDING` (with `availableAt` showing when it becomes due) |
| failure | `status = FAILED`, plus `lastErrorCode`/`lastErrorDetail` |
| current or last attempt information | `attempts` (most recent first), with `attemptNumber`, `claimedBy`, `startedAt`, `finishedAt`, `result`, `errorCode`, `errorDetail` |
| target/platform state | `targets`, in canonical platform order |
| relevant timestamps | `availableAt`, `claimedAt`, `leaseExpiresAt`, `completedAt`, `createdAt`, `updatedAt` |

### 17.2 Filters

Two new arguments, added identically to **both** `publisherServiceConfigurations`
and `publisherServiceConfigurationCount`, and applied through BE-03's shared
`filtered_publishers` helper so the list and the count cannot diverge:

```graphql
"If set, only shows results whose latest publisher back-catalogue job has one of these statuses. Multiple values widen the results"
jobStatuses: [DistributionJobStatus!] = []

"If set to true, only shows publishers with no publisher back-catalogue job at all; if false, only publishers that have at least one"
withoutBackCatalogueJob: Boolean
```

Semantics, stated because the two adjacent list filters deliberately differ:

- `jobStatuses` is **OR** within the list — a publisher matches if its latest job
  is in any listed status. This is the opposite of `enabledPlatforms`, which is
  **AND**, and the difference is not an inconsistency: a status is single-valued
  per job, so AND over two statuses would match nothing. Both field descriptions
  must state their semantics explicitly.
- The two new filters and every existing filter are **conjunctive** with each
  other.
- `withoutBackCatalogueJob: true` combined with a non-empty `jobStatuses` is a
  contradiction that matches zero publishers. That is deterministic and
  documented; it is not an error.
- Empty `jobStatuses` and null `withoutBackCatalogueJob` both mean "no filter",
  per repository convention.
- All filters are applied **before** pagination, and the count query applies
  exactly the same predicates as the list query.

`jobStatuses` uses `Option<Vec<DistributionJobStatus>>` with
`#[graphql(default = vec![], ...)]`, rendering as
`jobStatuses: [DistributionJobStatus!] = []` — the merged convention BE-03
section 12 fixed. `withoutBackCatalogueJob` is `Option<bool>` with no default, so
absent and `null` both mean "no filter" and the three-valued semantics are
expressible.

### 17.3 The no-job distinction

**A publisher with no durable job is represented by `latestBackCatalogueJob:
null`, and by nothing else.** This is a binding requirement, not a stylistic
preference:

| Reality | Representation |
|---|---|
| no job exists | `latestBackCatalogueJob` is `null` |
| pending | non-null, `status: PENDING` |
| running | non-null, `status: RUNNING` |
| succeeded | non-null, `status: SUCCEEDED` |
| failed | non-null, `status: FAILED` |
| cancelled | non-null, `status: CANCELLED` |

BE-04 must **not**:

- add a `NONE`, `NOT_STARTED`, `UNKNOWN`, `NOT_APPLICABLE` or equivalent value to
  `distribution_job_status`;
- return a synthetic zero-valued or placeholder `DistributionJob`;
- collapse "no job" into `FAILED`, `PENDING`, `UNKNOWN` or a zero count;
- infer a job status from assignment state, package, descriptor behaviour or any
  other signal.

The null follows BE-03's own merged precedent for `lastChange`, which is `null`
for a publisher with no recorded change and is explicitly "not a fabricated
placeholder". Section 25.10 requires a test asserting the null for a publisher
with enabled `AutomaticPush` assignments and no job — which is precisely the
state every publisher is in while the switch is `OFF`.

### 17.4 Query efficiency

For a page of N publishers the report must issue a **bounded, constant** number
of statements with no per-publisher, per-job or per-attempt loop. The bound rises
from BE-03's two statements to five, and no further:

| # | Statement | Origin |
|---:|---|---|
| 1 | filtered, ordered, paginated publisher page | BE-03, filters extended |
| 2 | `DISTINCT ON (publisher_id)` latest configuration change for the page | BE-03, unchanged |
| 3 | BE-02's existing request-local assignment loader, one set-based statement per dispatch chunk | BE-02, unchanged |
| 4 | **new** latest-job loader — `DISTINCT ON (publisher_id) ... WHERE publisher_id = ANY($1) AND kind = 'PUBLISHER_BACK_CATALOGUE' ORDER BY publisher_id, created_at DESC, distribution_job_id DESC` | BE-04 |
| 5 | **new** target loader and **new** attempt loader — `... WHERE distribution_job_id = ANY($1) ORDER BY ...`, one set-based statement each | BE-04 |

Three new field-specific DataLoaders are added to the existing `RequestLoaders`
bundle under ADR-0007. This is the approved pattern, not a second batching
subsystem: BE-03's non-goal forbade a *second loader equivalent to BE-02's
assignment loader*, and these three have different keys, values and statements.
Each must:

- be built through `configured_loader` with the approved explicit `200`/`10`
  (ADR-0007 invariant 6);
- be request-local, non-cached and dropped with the request (invariants 1, 2, 12);
- use `try_load` only (invariant 3);
- have a **total** batch function over requested keys (invariant 4);
- register its key at resolver entry with no unrelated awaited work before
  `try_load` (invariant 5);
- issue **set-based** SQL with no per-parent loop, inside the approved blocking
  boundary with no connection across `.await` (invariants 7, 8);
- **fail closed** batch-wide, never becoming successful empty data and never
  falling back per key (invariant 9);
- preserve membership, ordering and authorization equivalence with the direct
  path (invariant 11).

The attempt loader loads **every** attempt for the requested job ids in one
statement and the resolver partitions them per parent, which is safe because
attempts are hard-bounded at five per job (section 16.2).

Loader availability is independent of mutation guard mode (invariant 13).

Section 25.12 requires measured statement counts at page sizes 1, 25 and 200,
proving the count does not grow with N, using the existing observed-loader test
harness that exercises the production batchers.

| Boundary | Requirement |
|---|---|
| BE-03 configuration-only surfaces | `PublisherServiceConfiguration` gains **no** job field. The `publisherServiceConfiguration` single-publisher query, readable by a `PUBLISHER_USER` for their own publisher, returns exactly what it returns today. Job state is reachable only from `PublisherServiceConfigurationSummary`, which is superuser-only. |
| APP-01 configuration scope | unchanged and still satisfiable from BE-03 alone. |

| existing SDL | additive only: one new field on one existing type, two new arguments with defaults on two existing queries. No existing field's type, nullability, arguments, defaults or description changes. |

## 18. Error storage and disclosure

### 18.1 Bounds

| Field | Type | Maximum | Enforcement |
|---|---|---:|---|
| `error_code` / `last_error_code` | `text` | 64 characters, matching `^[A-Z][A-Z0-9_]*$` | database `CHECK` **and** an application validation that returns a stable error rather than storing a malformed code |
| `error_detail` / `last_error_detail` | `text` | 2048 characters | database `CHECK` as backstop; the application **truncates** rather than rejecting |

Truncation is exact and specified, not implied: the API keeps the first 2048
**Unicode scalar values** (using character boundaries, never a byte slice, so no
partial UTF-8 sequence can be produced) and stores that. It is truncation, not
rejection, because a worker reporting a genuine failure must not have its report
refused over length — the diagnostic is best-effort, the state transition is not.

`error_code` is validated rather than truncated, because a truncated
classification code is worse than no code: clients switch on it.

### 18.2 Retained classification

The retained classification is the worker-supplied `error_code`. It is stable,
machine-readable, indexed by the report's filters through `status`, and is what
DIS-02 and operators use to distinguish transient transport failures from
permanent rejections. BE-04 defines no closed vocabulary of codes: the meaningful
values are adapter-specific and belong to DIS-02's own specification, so fixing a
list here would either be wrong or immediately stale. The **shape** is fixed
(pattern and length) and the vocabulary is not.

### 18.3 Sanitization

The server performs exactly this, on `error_detail`, before storage:

1. remove ASCII control characters other than newline (`\n`) and tab (`\t`);
2. trim leading and trailing whitespace;
3. truncate per section 18.1.

**The server does not attempt to detect or scrub secrets from free text, and this
specification does not claim that it does.** Pattern-matching for credentials
produces false negatives that create false assurance and false positives that
destroy diagnostics; either would be worse than an honest contract. The contract
is therefore stated as an obligation on the writer, enforced at review of DIS-02
rather than by a regex here.

### 18.4 Prohibited content

The worker contract — binding on DIS-02 and on any future writer — forbids
placing any of the following in `errorCode` or `errorDetail`:

- secrets, credentials, passwords, API keys, private keys;
- access tokens, refresh tokens, session identifiers, `Authorization` header
  values;
- signed or presigned URLs, or any URL carrying a query-string credential;
- raw or truncated external response bodies, request bodies or HTTP headers;
- publication file contents;
- personal data of contributors, staff or publisher users beyond an account
  identifier already stored as `claimed_by`;
- hostnames, bucket names, endpoints, container identifiers, task ARNs,
  deployment identifiers or environment names.

Attempt history must remain useful for diagnosis without becoming a secret log.
The intended shape of a stored detail is a bounded description of *what failed
and why*, for example `SFTP handshake rejected by remote host after 3 retries`,
never the transcript that produced it.

Existing repository logging rules apply unchanged: no resolver may log the
detail, the actor, a token or a credential (root `AGENTS.md` section 9).

## 19. Migration and schema contract

### 19.1 Procedure

The migration directory is created with the supported repository procedure and
never by hand:

```bash
make migration
```

which produces `thoth-api/migrations/<YYYYMMDD>_v<MAJOR>.<MINOR+1>.0/` containing
`up.sql` and `down.sql`.

**No migration directory is created, reserved or named by this specification
task.** The implementing task creates exactly one, and must **verify** that its
directory name sorts after every existing directory under the embedded runner's
lexicographic ordering — the highest at the authoring base is `20260813_v1.6.3`.
`make migration` derives the version from `Cargo.toml`, not from the existing
directories, so this ordering check is an explicit implementation obligation, not
an assumption (section 25.3).

Migrations are applied and reverted only with the embedded Rust runner:

```bash
cargo run migrate
cargo run migrate --revert
```

### 19.2 Atomic update set

Under ADR-0003 Architecture A the implementation must update, **atomically in the
same bounded pull request**:

1. migration `up.sql` — four `CREATE TYPE`, three `CREATE TABLE` with every named
   constraint of section 7, the three indexes of section 7.5, and
   `SELECT diesel_manage_updated_at('public.distribution_job')` (only
   `distribution_job` has `updated_at`; target and attempt rows are not
   `diesel`-managed);
2. migration `down.sql` — `DROP TABLE IF EXISTS` for
   `distribution_job_attempt`, then `distribution_job_target`, then
   `distribution_job` (child-first, so foreign keys do not block), then
   `DROP TYPE IF EXISTS` for the four enums;
3. `thoth-api/src/schema.rs`, **maintained directly** per section 7.6;
4. Rust SQL/custom types — the four `diesel_derive_enum::DbEnum` +
   `juniper::GraphQLEnum` enums with `ExistingTypePath`;
5. models — the `distribution_job` module of section 7.6;
6. GraphQL — sections 16 and 17;
7. focused database and model tests — section 25.

`diesel print-schema` must **not** be used as the canonical writer. External
introspection tools may be consulted diagnostically only, and their output must
never write to `schema.rs`. No Diesel CLI dependency, no root `diesel.toml` and
no schema-synchronization subsystem may be introduced.

### 19.3 Migration effect

Migration required: **YES**

- **Schema changes:** four new enum types, three new tables, three new indexes,
  one `diesel_manage_updated_at` trigger. **No existing table, column, constraint,
  index, trigger or enum is altered or dropped.**
- **Populated database behaviour:** zero rows are created by the migration
  itself. No publisher row, package value, assignment row or configuration audit
  row changes. No existing value is rewritten.
- **Data backfill:** none. There is nothing to backfill: a job exists only
  because a future activation created it.
- **Idempotency:** not applicable; this is one-shot DDL.
- **Locking/downtime assessment:** every object created is new, so the migration
  takes **no lock on any existing table** and performs no table rewrite. This is
  materially lighter than BE-03's `ALTER TABLE public.publisher ADD COLUMN`,
  which took a brief `ACCESS EXCLUSIVE` lock on a populated table. That
  expectation must still be **measured, not asserted**: section 25.3 requires the
  observed locks and duration on a representative populated database, and
  confirmation that `pg_class.relfilenode` is unchanged for `publisher`,
  `publisher_distribution_platform`, `publisher_service_configuration_history`
  and `work`.
- **Empty database test:** apply, revert, re-apply cleanly.
- **Populated database test:** forward migration against a representative
  populated database, proving existing publisher, package, assignment and
  configuration-audit rows are unchanged and zero job rows exist.
- **Rollback / forward repair:** section 23.

**No production migration is part of BE-04.** Production migration execution and
rollback remain governed by
[CG-13](../../repository-map/control-gaps.md) and separate release
authorization, and **merge of BE-04 implementation does not authorize production
migration execution**.

  are deployment and runbook work under OPS-01 and DIS-02.
- **One operational fact that must be recorded rather than discovered:**
  cancelling a `RUNNING` job does not undo external delivery already performed
  (section 14.1). Any runbook that offers cancellation as a rollback step must
  pair it with external reconciliation, as the rollout plan's stage 6 already
  requires.

## 22. Rollout

These seven lifecycle events are **separate** and none implies the next:

| # | Event | Authorized by BE-04 merge? |
|---:|---|---|
| 1 | repository merge of BE-04 implementation | yes — that is what the merge is |
| 2 | deployment of the additive schema and API | **no** — separate release authorization |
| 3 | production migration execution | **no** — CG-13 and separate release authorization |
| 4 | worker deployment and credential provisioning | **no** — DIS-02 and separate operational authorization |
| 5 | automatic-job-creation activation (`OFF -> ON`) | **no** — explicit CTO production activation approval |
| 6 | pilot | **no** — explicit CTO approval, per rollout-plan stage 6 |
| 7 | wider enablement | **no** — explicit CTO approval, per rollout-plan stage 7 |

Rollout properties:

- **initial state after merge: repository history changes only.** No deployment
  occurs, no migration is executed anywhere, no job exists, no worker exists, no
  credential exists and no API behaviour is available to any client;
- **BE-04 implementation merges inactive.** `DistributionJobCreation::Off` is the
  default and the merged state;
- **automatic job creation is OFF by default**, and section 9.4 guarantees that
  turning it on performs no sweep;
- **no merge and no deployment may itself enqueue the existing back catalogue.**
  The migration creates zero rows, and creation requires a *future* qualifying
  activation after the switch is on;
- **even after deployment and migration**, with the switch still `OFF`, the
  worker API exists but returns nothing to claim, and no configuration change
  creates a job;
- **even with the switch `ON`**, nothing is delivered until a worker is deployed
  with the `DISSEMINATION_WORKER` role granted — which is DIS-02's separately
  authorized work;
- **a future pilot requires explicit CTO production activation approval**, and
  must follow the rollout plan's stage 6 procedure: one publisher, one verified
  `AutomaticPush` platform, reviewed catalogue count, one activation, observed
  claim/attempt/completion, exercised retry or controlled failure, recorded
  decision. Do not pilot OAPEN/DOAB first unless linked multi-target behaviour is
  the explicit test objective;
- **legacy dissemination remains available** through the comparison and
  observation stages and is not removed, disabled or bypassed by BE-04
  (operational invariant 10).

## 23. Rollback

Rollback differs by lifecycle stage, and the difference is the point.

### 23.1 Before any deployment or migration

No job, attempt or lease exists anywhere. An ordinary code revert of the pull
request is possible under normal review, subject to the migration controls in
section 19.

### 23.2 After deployment and migration, before any production job exists

- set `THOTH_DISTRIBUTION_JOB_CREATION=OFF` (or leave it off) and redeploy: no
  new job can be created;
- the additive tables are empty and inert;
- code revert remains possible, subject to migration controls. The `down.sql`
  migration is reversibility **evidence**, not an automatic production rollback
  procedure.

### 23.3 After durable jobs exist

- **do not destroy job, target or attempt history merely to roll back
  application code.** That history is operational audit evidence of what was
  attempted against external platforms, and it is the only Thoth-side record of
  deposits that may exist remotely;
- **disable new creation** — switch to `OFF`;
- **disable new claiming** — stop the worker (DIS-02 operational control) and, if
  required, revoke the `DISSEMINATION_WORKER` grant. Both are outside this
  repository and belong to deployment/runbook work, not to this specification;
- **preserve the additive tables.** Dropping a populated `distribution_job`,
  `distribution_job_target` or `distribution_job_attempt` requires separate
  explicit authorization, exactly as dropping a populated
  `publisher_service_configuration_history` does;
- **use approved forward repair** where a destructive down migration would lose
  operational evidence. An incorrect job state is corrected by an explicit,
  recorded transition — cancellation — not by editing or deleting rows;
- **reconcile external delivery separately.** Rolling back Thoth-side state does
  not withdraw a deposit already made at a destination.

### 25.8 Concurrency, claim and retry tests

These must be **real database concurrency tests using multiple real connections
and real transactions**. Mocked sequential substitutes do not satisfy them.

- **concurrent claims by multiple workers**: with M due jobs and W concurrent
  workers, every job is claimed at most once, the union of claims is a partition,
  no worker blocks on another, and each claimed job has exactly one open attempt;
- **deterministic claim ordering**: with jobs of differing `available_at`, a
  single worker claims strictly in `(available_at, distribution_job_id)` order;
- **lease expiry**: a `RUNNING` job past its lease is recovered to `PENDING` by
  the next claim call, its open attempt is closed `ABANDONED`, and
  `attempt_count` is **not** decremented;
- **stale token complete rejection**: after recovery and re-claim, the original
  worker's `complete` returns `StaleDistributionJobClaim` and the newer attempt is
  untouched;
- **stale token fail rejection**: the same for `fail`, including
  `retryable = true`;
- **current-token complete** succeeds, closes the attempt `SUCCEEDED`, clears
  every claim field and clears `last_error_*`;
- **current-token fail** succeeds in both branches;
- **retry**: `fail(retryable = true)` at attempts 1–4 returns the job to
  `PENDING` with `available_at` equal to the computed backoff, adds exactly one
  closed `FAILED` attempt, and leaves `completed_at` null;
- **repeat retry**: the full 1→2→3→4→5 sequence terminalizes at `FAILED` on the
  fifth attempt with `attempt_count = 5` and five attempt rows;
- **repeat calls**: every row of the section 13.3 table;
- **claim bounds**: `limit` above 50 clamps; `limit <= 0` claims nothing;
  `leaseSeconds` outside `60..=3600` clamps; the kinds filter selects correctly;
- **eligibility**: a job whose target is disabled is not claimed; a job whose
  target is enabled under a *different* activation is not claimed.

### 25.9 Cancellation and assignment-interaction tests

- cancellation from **every** state of the section 14.2 table, asserting the job
  effect, the attempt effect and the error where rejected;
- cancelling a `RUNNING` job invalidates the live token, so the holder's
  subsequent `complete` and `fail` both return `StaleDistributionJobClaim`;
- cancelling an already-`CANCELLED` job returns `DistributionJobAlreadyTerminal`
  and changes nothing;
- a cancelled job cannot be reopened, retried or re-claimed;
- target rows and attempt history are unchanged by cancellation;
- **assignment disabled with a `PENDING` job**: the job becomes `CANCELLED` with
  `ASSIGNMENT_DISABLED` in the same transaction as the disable; another
  publisher's jobs are untouched; a `PENDING` job for a *different* group of the
  same publisher is untouched;
- **assignment disabled with a `RUNNING` job**: the job is untouched; the
  claiming worker can still complete or fail it; after lease expiry and recovery
  to `PENDING` it is **not** claimable, and remains visible for explicit
  cancellation;
- **terminal job mutation rejection**: complete, fail and cancel are each
  rejected against `SUCCEEDED`, `FAILED` and `CANCELLED`;
- **attempt history** survives every path and is readable in order.
