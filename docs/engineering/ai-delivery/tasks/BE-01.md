## 1. Objective

Add the inactive backend foundation for publisher packages by storing exactly
one non-null package for every publisher, defaulting existing and new
publishers to `OASIS`, defining stable Rust and GraphQL package and capability
codes, and implementing one exhaustive code-owned package-to-capability
mapping. BE-01 creates no distribution-platform behaviour, exposes no new
public or protected package query or mutation, and activates no OAI-PMH or
Metrics feature.

The implementation branch must be created from the latest verified `develop`
after the BE-01 specification PR has been independently approved and merged.
The implementing agent must record that exact then-current base before changing
anything. This specification does not pin implementation to the historical
BE-01-SPEC base.

### 2.3 Current implementation findings

The implementation agent must refresh these findings against its exact base:

- `Publisher`, `NewPublisher`, and `PatchPublisher` are defined in
  `thoth-api/src/model/publisher/mod.rs`.
- `Publisher` is a Diesel `Queryable` and serde-serializable persisted model.
  `NewPublisher` is a Diesel `Insertable` and GraphQL input.
  `PatchPublisher` is a Diesel `AsChangeset` and GraphQL input.
- The public GraphQL `Publisher` object is implemented explicitly in
  `thoth-api/src/graphql/model.rs`; its currently exposed fields contain no
  package or capability data.
- Ordinary publisher create and update mutations accept `NewPublisher` and
  `PatchPublisher` respectively. Neither currently contains a package field.
- Publisher history stores a JSONB value containing the serialized persisted
  publisher snapshot. No parser in the inspected current publisher-history path
  deserializes every historical snapshot into the current `Publisher` struct.
- `thoth-api/src/schema.rs` is generated/derived, while root `diesel.toml`
  currently declares `src/schema.rs`; CG-12 therefore remains an explicit
  precondition.
- `thoth-client/build.rs` generates its GraphQL schema from the reachable
  Juniper schema. An otherwise unused GraphQL enum may therefore be absent from
  generated schema output until BE-03 references it.
- Root migration commands use the embedded migration runner:
  `cargo run migrate` and `cargo run migrate --revert`.

## 5. Invariants

The implementation must preserve:

1. package and distribution-platform independence;
2. `DistributionPlatform` and `MetricPlatform` as separate domains;
3. PostgreSQL as canonical storage for the publisher package;
4. one code-owned and compile-time-exhaustive capability mapping;
5. stable screaming-snake-case package and capability codes;
6. no anonymous package or capability exposure;
7. no package field in ordinary publisher create or patch inputs;
8. no capability acting as operational configuration or activation;
9. no inference of entitlement from locations, distribution assignments, or
   platform configuration;
10. no distribution, job, OAI, or Metrics side effect from BE-01;
11. existing publisher-history rows remain readable;
12. canonical Metrics history is retained across future package changes;
13. future feature code calls `has_capability` instead of duplicating package
    name combinations;
14. authorization remains enforced in the backend, never only in a UI.

## 6. Required behaviour

### 6.1 Settled package and capability codes

PostgreSQL, Rust, and future GraphQL package codes must be exactly:

```text
OASIS
OBELISK
SPHINX
PYRAMID
```

Capability codes must be exactly:

```text
OAI_PMH
METRICS_COLLECT
METRICS_IMPORT
METRICS_DASHBOARD
METRICS_WIDGET
METRICS_OPERAS_EXPORT
```

The names and meanings are stable API and domain identifiers. The
implementation must not introduce aliases, lowercase database values,
`OTHER`, custom publisher capability sets, or fallback values.

### 6.2 Normative capability mapping

The one canonical mapping must implement exactly:

| Package | OAI_PMH | METRICS_COLLECT | METRICS_IMPORT | METRICS_DASHBOARD | METRICS_WIDGET | METRICS_OPERAS_EXPORT |
|---|---:|---:|---:|---:|---:|---:|
| OASIS | No | No | No | No | No | No |
| OBELISK | Yes | Yes | No | No | No | No |
| SPHINX | Yes | Yes | Yes | Yes | Yes | Yes |
| PYRAMID | Yes | Yes | Yes | Yes | Yes | Yes |

The implementation must be equivalent to:

```rust
impl ThothPackage {
    pub fn capabilities(self) -> &'static [PublisherCapability];
    pub fn has_capability(self, capability: PublisherCapability) -> bool;
}
```

The exact signature may follow repository conventions, but it must:

- use a closed `ThothPackage` enum;
- use a closed `PublisherCapability` enum;
- handle every package exhaustively at compile time;
- avoid runtime database configuration;
- avoid allocation where practical;
- expose one canonical mapping implementation;
- contain no wildcard or fallback arm that could grant access to a future
  package or capability.

### 6.3 Database behaviour

Migration required: YES.

The migration must create:

```text
PostgreSQL enum: public.thoth_package
Values: OASIS, OBELISK, SPHINX, PYRAMID
Column: publisher.subscription_package
Column type: thoth_package
Nullability: NOT NULL
Database default: OASIS
```

Required outcomes:

- all existing publisher rows become `OASIS`;
- no publisher row contains null;
- a new publisher insert that omits the field receives `OASIS` from the
  database default;
- `NewPublisher` does not require or expose a package field;
- `PatchPublisher` does not contain or expose a package field;
- no commercial package backfill occurs in BE-01;
- no capability, platform, job, audit, or external record is created.

MIG-01 will later update publishers from an approved production mapping.

### 6.5 Rust model behaviour

The implementation must:

- add `ThothPackage`;
- add `PublisherCapability`;
- add `subscription_package: ThothPackage` to persisted `Publisher`;
- follow existing Diesel/PostgreSQL enum conventions;
- preserve serde and GraphQL naming as stable screaming-snake-case codes;
- update the generated Diesel schema through the verified procedure;
- preserve ordinary publisher CRUD.

`NewPublisher` must not require a package field. `PatchPublisher` must not
contain one. The database default supplies `OASIS`.

### 6.6 GraphQL boundary

BE-01 may define GraphQL enum representations for:

```text
ThothPackage
PublisherCapability
```

BE-01 must not add:

- `Publisher.subscriptionPackage`;
- `Publisher.capabilities`;
- a package or capability query;
- a package filter or report;
- a package mutation;
- a protected service-configuration query;
- a dedicated superuser configuration mutation.

The implementation must not add a public field solely to force an otherwise
unused enum into generated schema output. If Juniper omits an unreferenced enum
until BE-03 uses it, that is acceptable and must be recorded in the
implementation report.

Package values must not become anonymously readable through existing publisher
queries, exports, serialization surfaces, or generated clients.

### 6.7 Authorization

BE-01 introduces no new query or mutation authorization surface.

Tests must nevertheless prove:

- anonymous callers gain no package data;
- authenticated callers gain no new package field through public queries;
- ordinary publisher mutations cannot alter the package;
- superusers also cannot alter the package through ordinary publisher
  mutations;
- a GraphQL request supplying `subscriptionPackage` to ordinary create or
  patch input fails schema validation;
- no UI-only restriction is relied upon.

The dedicated protected read and superuser mutation belong to BE-03.

### 6.8 Publisher-history compatibility

The implementation must assess and test the current history serialization.

Required behaviour:

- existing history rows that predate the package field remain readable;
- BE-01 performs no history-row backfill;
- new publisher history snapshots may contain the package where existing
  serialization naturally serializes the persisted `Publisher`;
- package changes are not introduced through the ordinary history-producing
  patch mutation;
- no parser assumes every historical JSON value contains
  `subscriptionPackage`.

If the existing history implementation would become unreadable without an
unrelated history migration, stop before implementation.

### 6.9 Package and platform independence

Tests and review evidence must show that BE-01:

- creates no distribution-platform assignment;
- changes no platform assignment;
- creates no distribution job;
- changes no dissemination eligibility;
- changes no publisher-ID environment configuration;
- does not infer package from existing locations or platform configuration;
- does not infer Metrics entitlement from locations or platforms.

`OASIS` receiving no Metrics capability must not be interpreted as a
distribution prohibition.

### 6.10 Capability semantics

The following approved invariants apply to future consumers:

- capabilities permit a feature but do not configure or activate it;
- source accounts, credentials, feature flags, approvals, and schedules remain
  additional requirements;
- OBELISK collection is private, configured, and non-blocking;
- unavailable Metrics data is not represented as zero;
- package downgrade retains canonical Metrics history;
- package changes leave distribution assignments unchanged;
- historical OPERAS export requires a separately authorized backfill;
- in-flight feature work rechecks capability at its final boundary;
- BE-01 itself consumes no capability in OAI or Metrics operations.

### 6.11 Failure behaviour

The migration and model must fail closed:

- unknown package values are rejected by the PostgreSQL and Rust enum
  boundaries;
- null packages are rejected by the database;
- ordinary GraphQL inputs reject the unknown `subscriptionPackage` field;
- a schema-generation uncertainty blocks work before migration edits;
- no fallback package or capability grants access.

### 6.12 Concurrency and idempotency

The migration must be safe to apply once through the repository migration
runner, safe to revert under the pre-dependency rollback condition, and safe to
reapply in the required disposable-database test. BE-01 adds no concurrent
package mutation or job path.

The implementation report must assess retry behaviour after partial migration
failure and explain how the embedded migration harness records successful
migrations.

### 6.13 Compatibility

The implementation report must inspect:

- generated GraphQL schema;
- internal Rust client;
- `thoth-app` generated-client impact;
- dissemination consumers;
- exports;
- the OAI branch;
- Metrics branches.

Expected result:

- no downstream repository change is required for BE-01;
- no existing GraphQL field or input is removed or changed;
- no public package field is introduced;
- ordinary publisher input remains backwards compatible;
- BE-03 later exposes the protected package/capability contract;

Any unexpected generated-client or public contract change requires review

## 12. Rollback

### 12.1 Before BE-03 or MIG-01 writes a non-OASIS package

An immediate BE-01 rollback may:

- revert the code;
- run the tested down migration;
- remove `publisher.subscription_package`;
- drop `thoth_package`.

This is allowed only when every package value remains `OASIS` and no later
merged task depends on the field.

### 12.2 After a non-OASIS package exists or a later task depends on BE-01

Do not run the destructive down migration.

Use a separately reviewed coordinated rollback or forward-repair task that
preserves package data and dependent contracts.

The BE-01 implementation report must state which rollback condition applies at
review time.

Feature disable/kill switch: no BE-01 feature path exists to disable.

External side effects: none; stop and investigate if any are observed.
