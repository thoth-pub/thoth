#### 3.2 Objects added by R-8

Migration 2 creates one generic function and two statement-level guards, placed immediately after the `work_upsert_admission` guard, in the generic part of the migration:

```sql
CREATE FUNCTION public.work_upsert_refuse_truncate() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN RAISE EXCEPTION '%', TG_ARGV[0]; END $$;
CREATE TRIGGER work_upsert_control_no_truncate BEFORE TRUNCATE ON public.work_upsert_control
    FOR EACH STATEMENT EXECUTE FUNCTION public.work_upsert_refuse_truncate('WORK_UPSERT_CONTROL_ROW_IS_PERMANENT');
CREATE TRIGGER work_upsert_admission_no_truncate BEFORE TRUNCATE ON public.work_upsert_admission
    FOR EACH STATEMENT EXECUTE FUNCTION public.work_upsert_refuse_truncate('WORK_UPSERT_ADMISSION_DELETE_ONLY_BY_PUBLISHER_CASCADE');
```

The function is generic, not `crossref_refuse_truncate`, because frozen rule 12 keeps Crossref state out of the generic substrate. Both guards reuse existing codes, because their semantics are exact: a `TRUNCATE` of the control table deletes the permanent control row, and a `TRUNCATE` of the admission table deletes admission rows by a path other than the publisher cascade. A statement-level `BEFORE TRUNCATE` trigger never fires for the row-level referential `DELETE` cascade a publisher deletion performs, so the admission guard's publisher-cascade exception (R52B §18.5) is untouched. Executed (§17, E2): `TRUNCATE work_upsert_control`, with and without `CASCADE`, and `TRUNCATE work_upsert_admission` are refused with exactly those messages; `TRUNCATE publisher CASCADE` is refused by the admission guard; `DELETE FROM publisher` still cascades the publisher's admission rows and sets its permits' links `NULL`; a direct `DELETE` of an admission row while its publisher exists is still refused; and the test reset's transaction-local `replica` mode still truncates both tables, as §5 requires.

### 5. Test-harness reset contract

#### 5.1 Guarantees

1. **Never production.** Both helpers compile only for tests: `#[cfg(test)] pub(crate) mod tests` in `model/mod.rs`, and the integration-test crate under `thoth-api/tests/`. No production module or migration contains the bypass.
2. **Only through the helpers.** Tests reset only by `setup_test_db()` or `reset_db()`.
3. **Manifest first.** Before any bypass the statement positively verifies, on its own connection, that the mode is `origin` and that the **15** permanence triggers of §5.2 are present and enabled, and fails closed otherwise.
4. **Complete.** Every per-test row is removed, BE-06's permanent tables included.
5. **Seeds exact.** `work_upsert_control` holds exactly `('CROSSREF', false, false)` and `work_crossref_version_floor` exactly `(true, 0)`; `updated_at` takes its column default.
6. **No residue.** Every other public table is empty and identities are restarted; `__diesel_schema_migrations` is untouched.
7. **Protections active before the next test body.** The bypass is transaction-local and ends with the statement; after reseeding the statement verifies that the mode is `origin` and that no public user trigger is disabled.
8. **Fail closed.** Any error rolls back the truncation, the reseed and the mode change; `setup_test_db` panics `Failed to reset DB`; no error path can leave `replica` on a pooled connection.
9. **Ordinary SQL still refused** (H3).

#### 5.3 Rules

- **One statement**, run through `diesel::sql_query(…).execute`, as released, on a pooled connection with no open transaction.
- **Transaction-local only.** The bypass is `set_config('session_replication_role', …, true)`; a session-level `SET`, or `set_config(…, false)`, is prohibited in the reset.
- **Privilege precondition.** The test role is a superuser or holds `SET` on `session_replication_role`; the released `work_relation` audit tests already need this; in CI the `postgres:17` `POSTGRES_USER` is a superuser. Without it the reset fails closed with `permission denied to set parameter`.
- **No leaked mode.** A test that sets `session_replication_role` does so only inside a transaction it rolls back.
- **No committed DDL.** A negative control that alters a trigger, function or constraint runs inside a rolled-back transaction or on a throwaway database (the released `TempMigrationDb` pattern).
- **Production unchanged.**

#### 5.4 Containment boundary, stated for review

The primary boundary is compilation: the statement exists only in a `#[cfg(test)]` module of the library and in the integration-test crate, neither of which is part of a release binary. The secondary boundary is textual: H7 scans `thoth-api/src` and `thoth-api/migrations` for `session_replication_role` and permits it only in `tests.rs` and `*_tests.rs`. The textual scan is file-name based and would not catch a production helper deliberately named `*_tests.rs`; the compile boundary would, because such a helper would still have to be reachable from a non-test module, which review of the four authorized paths excludes. No stronger boundary exists inside the authorized paths, and none is claimed.

### 6. The binding: internal exact binding and public projection

**Investigation.** R52B §0 defines a binding as the exact `(publisher_id, activation_id, execution_profile)` triple, and §19.4 says the four reservation mutations return "the binding the reservation checked". The released API boundary at `b23ba05c` never exposes activation identity: `PublisherDistributionPlatformAssignment` is documented as the public projection that "carries only the destination and the timestamp at which the current activation began", with `activation_id` "deliberately absent", and its SDL test forbids `activationId` in that type; the BE-04 leakage test forbids `activationId` inside `type DistributionJob`. Neither test is whole-SDL, so a new type could carry the field without failing a released test; the released rule is nonetheless explicit. The downstream consumer's needs after a reservation, from R52B §28.2 and §15.5, are: the permit id and token; `crossrefTimestamp` and the root Work identity, to request the prepared artifact; the canonical `dois`, batch id and timestamp, as cross-checks; the publisher identity, to select the credential and DOI prefix it POSTs under and to perform the pre-POST recheck against the `AUTHORIZED` permit's `publisherIdentity`; and `payloadDigest` from the permit. No worker step reads an activation, because activation enablement is verified server-side at reservation (fence clause 6) and again at finalisation (group B3) under the held publisher.

**Decision.** This amendment distinguishes two things and amends R52B §19.4's phrase:

- the **internal exact binding** is R52B's triple, verified by the API under the locks R52B prescribes, and never exposed;
- the **public binding projection** returned by every reservation is exactly `publisherIdentity` (the permit's immutable `publisher_identity`, the binding publisher the reservation checked) and `rootWorkIdentity` (the permit's `root_work_identity`, which on the `WORK_UPSERT` route the API derived from the job). "The binding the reservation checked" in R52B §19.4 means, on the public surface, this projection. The execution profile is not a field, because every permit type is Crossref-only and the value is implied by the type; `DistributionJob.executionProfile` carries it where it varies.

### 7. Input validation, code-owned

#### 7.1 The non-blank rule (R-7)

A `String` argument that must be non-blank is **blank** iff it is empty or every Unicode scalar value in it satisfies Rust `char::is_whitespace()` or `char::is_control()`; it is non-blank iff at least one scalar value satisfies neither. Enumerated with the workspace toolchain (rustc 1.97.0; §17, E7): `is_whitespace` is exactly the 25 code points of the Unicode `White_Space` property — `U+0009`–`U+000D`, `U+0020`, `U+0085`, `U+00A0`, `U+1680`, `U+2000`–`U+200A`, `U+2028`, `U+2029`, `U+202F`, `U+205F`, `U+3000`; `is_control` is exactly the 65 `Cc` code points `U+0000`–`U+001F` and `U+007F`–`U+009F`; the union has 84. Format characters such as `U+200B`, `U+FEFF` and `U+180E` are content, so a string made only of them is non-blank; that boundary is deliberate and tested (N4). The rule is evaluated in `thoth-api` on the decoded string, never trims or normalises, and stores the accepted value verbatim. It does not depend on the database's collation provider: executed (E7), the CHECK regex `~ '[^[:space:]]'` treats `U+00A0` as blank under ICU but as content under the C and libc providers, and treats `U+001C` as blank under ICU but as content under C, whereas the code rule refuses every string that any of the three providers refuses, so a database CHECK can never refuse a value the code accepted and never decides API validity.

The rule applies to exactly these inputs, with these codes:

| Input | Mutation | Code |
|---|---|---|
| `operatorAuthorizationReference` | 6 | `CROSSREF_MANUAL_RECOVERY_REQUIRES_REFERENCE` |
| `detail` | 9, 10 | `CROSSREF_PERMIT_VOID_REQUIRES_DETAIL` |
| `authorizationReference` | 10 | `CROSSREF_VOID_REQUIRES_AUTHORIZATION_REFERENCE` |
| `authorizationReference` | 11 | `CROSSREF_RECONCILIATION_REQUIRES_REFERENCE` |
| `evidenceReference` | 15 | `WORK_UPSERT_ADMISSION_REQUIRES_EVIDENCE_REFERENCE` (new) |
| `authorizationReference` | 16 | `CROSSREF_VERSION_FLOOR_REQUIRES_AUTHORIZATION_REFERENCE` |

No other BE-06 textual input carries a non-blank requirement: `observedDoiBatchId` and each `observedDois` member are cross-checks whose mismatch is a finalisation result (R52B §16.6 A3, A4), and `authorizationRegisterDigest` and `payloadDigest` have shape rules of their own. The rule is evaluated only after request authorization (C1): for the fixed-role operations after the role check, and for the route-owner void of mutation 9 after the coarse role, the permit's route read and the route-derived role (§10.1), so an unauthorized caller receives `NO_ACCESS` and never a non-blank refusal. The database CHECKs `~ '[^[:space:]]'` remain as defence in depth; only the admission CHECK maps to its code, as §10.3 states.

#### 7.2 Digest shapes (R-6)

`FinaliseCrossrefWriteInput.payloadDigest` is valid iff it is exactly 64 bytes long and every byte is one of `0`–`9` or `a`–`f`: the lower-case hexadecimal SHA-256 of the exact artifact bytes (R52B §15.4). Anything else — upper-case digits, 63 or 65 characters, a non-hex character, a space, a full-width digit, a non-ASCII character, the empty string — is refused `CROSSREF_PAYLOAD_DIGEST_INVALID` at §9.7 step 4: after request authorization (the coarse role, the permit's route read and the route-derived role) and before any lock, token comparison, state read or mutation. A caller without the route's role receives `NO_ACCESS` for the same request and learns nothing, not even that its digest was malformed (C1). The CHECK `crossref_write_permit_payload_digest_check` (`^[0-9a-f]{64}$`) remains as defence in depth. A replay (§9.7 C2) is reached only by a valid digest, so it must present the original one exactly. `authorizationRegisterDigest` keeps the same shape rule under `CROSSREF_VERSION_FLOOR_REGISTER_DIGEST_INVALID` (§9.9). Executed (E8): the validator accepts the two valid vectors and refuses the eight invalid ones.

#### 7.3 Scalars, sizes and lists

`Uuid` and `Generation` are coerced by GraphQL before any resolver runs; a failure is the released input error, and every accepted UUID spelling denotes one value. `Int` limits follow the released clamp convention: `limit <= 0` runs no unit, values above the clamp are clamped, and no `Int` argument is ever refused. `executionProfiles` empty → `WORK_UPSERT_EXECUTION_PROFILES_REQUIRED`; a member that is not a registered profile → `WORK_UPSERT_PROFILE_NOT_IMPLEMENTED`; both before any database access. A count that cannot be represented as `Int` is `INTERNAL_ERROR` with an empty message; no BE-06 count can reach that bound in practice.

#### 9.2 The seed — R-2 closed

**Signature.** `seedCrossrefWorkUpsert(data: SeedCrossrefWorkUpsertInput!): SeedCrossrefWorkUpsertResult!`, `SUPERUSER`. `limit: Int = 100`: nullable, default `100`; an absent or null `limit` means `100`; effective minimum `1` (`limit <= 0` runs no unit and is not refused); effective maximum `500` (larger values are clamped, not refused); no value of `limit` is ever refused (R52B §19.2's convention for the drain).

**Precedence.** 1 `require_superuser()`. 2 no argument refusal exists. 3 `SELECT 1 FROM public.publisher WHERE publisher_id = $1`, by MVCC; absent → released `EntityNotFound`. 4 `work_upsert_control` for `CROSSREF`, by MVCC: `capture_enabled` false → `WORK_UPSERT_CAPTURE_NOT_ENABLED` (R52B §21.2 makes capture the seed's precondition). 5 coverage, by MVCC: no enabled `CROSSREF` assignment for the publisher → `CROSSREF_PUBLISHER_NOT_COVERED`. Steps 3–5 take no lock and are evaluated once per call; the seed writes generation state only, which is activation-independent, so it binds no activation and does not re-check coverage per unit — admission does that under `P FOR SHARE` (§9.3). 6 the batch.

**Selection, exactly (C4).** The selector is **one `READ COMMITTED` statement per call**, run outside any unit transaction; its own statement snapshot is the only snapshot it has. There is no call-wide snapshot, no cursor and no keyset continuation. It returns at most `limit` rows: the Works `w` of the publisher such that, on current ownership, `w`'s imprint belongs to the publisher, `w` is **uncovered** (no `work_upsert_generation` row for `(w, 'CROSSREF')`, or a row with `source_generation = 0`) and `w` satisfies the **SQL-evaluable eligibility clauses** of R52B §14.2 — E4, E5 and every row-level clause of E6 — ascending by `work_id`. E1–E3 are the publisher-level coverage of step 5. The one clause the selector cannot evaluate, abstract normalisation under `normalise_crossref_abstract_jats`, is **not applied by the selector and not re-evaluated by the unit**: a selected Work that fails it is seeded like any other, which is harmless — the seed writes generation state only, the Work is not eligible so the census does not count it, and materialization ends `INELIGIBLE` for it until its abstract is corrected, which is a captured edit. Every selected Work runs exactly one unit, so `limit` bounds both the rows the selector returns and the units the call runs, and `examined` equals the number of rows returned. Changes committed between the selector statement and a unit are handled by the unit, never by the selector: a deleted Work ends `NO_WORK`; a Work moved out ends `BINDING_MOVED_RETRY_LATER` and has left this publisher's set; a Work covered meanwhile by a capture flush ends `OBSERVED`; a Work moved in, or an assignment or eligibility change, is seen by the next call's selector, which evaluates current data afresh. A Work created after Migration 2 is covered by its own capture and is never a selector candidate. Convergence: every unit either covers its Work, observes it covered, or ends on a Work that has left the publisher's set, so the selector's set loses every examined member — a Work that later moves back in is covered by that move's own capture, because `work.imprint_id` and `imprint.publisher_id` are captured columns, and is never a candidate again — and repeated bounded calls reach every uncovered Work of the publisher; no uncovered Work is starved, because covered Works are not candidates and every returned candidate is examined. The traversal is restartable: no position is persisted; every call starts from the lowest uncovered `work_id` on current data, so a call interrupted after `k` committed units leaves exactly those `k` Works covered and the next call continues under the same predicate. Executed (E15): seven SQL-eligible Works, one already covered and one failing the non-SQL clause, pages of three — the calls returned 3, 3, 1 and 0 rows, seeded 7 including the non-SQL-clause Work, and the census excluded that Work throughout; a Work moved in after a selector statement was absent from that page and selected by the next call; a Work deleted, a Work covered by a concurrent flush and a Work moved out after selection ended `NO_WORK`, `OBSERVED` and `BINDING_MOVED_RETRY_LATER` in one call, and the moved Work was absent from the next page; every call returned at most `limit` rows. #### 9.3 Admission — R-3 resolved

**Signature.** `admitCrossrefWorkUpsert(data: {publisherId: Uuid!, evidenceReference: String!}): WorkUpsertAdmission!`, `SUPERUSER`.

**Precedence.** 1 `require_superuser()`. 2 `evidenceReference` blank under §7.1 → `WORK_UPSERT_ADMISSION_REQUIRES_EVIDENCE_REFERENCE`, with no database access. 3 one `work_upsert_transaction` (§10.3 EB1): a pool acquisition failure is `WorkUpsertDatabaseFailure`; the transaction runs at `READ COMMITTED`, PostgreSQL's default, which the wrapper never changes and steps 7 and 8 require. Its first statement is `SELECT 1 FROM public.publisher WHERE publisher_id = $1 FOR SHARE` — the binding publisher's lock, first (LO-5); absent → rollback, released `EntityNotFound`. 4 in a later statement, read `A`, the `activation_id` of the publisher's enabled `CROSSREF` assignment, under the held `P`; none → rollback, `CROSSREF_PUBLISHER_NOT_COVERED`. 5 in a later statement, `SELECT execution_profile, publisher_id, activation_id, evidence_reference, actor, admitted_at FROM public.work_upsert_admission WHERE execution_profile = 'CROSSREF' AND publisher_id = $1 AND activation_id = A`; a row → commit and return it unchanged, writing nothing: repeated exact admission is idempotent, the presented reference is not compared because the row is immutable, and the census is not re-run. 6 compute the eligible population of `(P, A)` with the seed's eligibility code and evaluate R52B §21.3's census statement, unchanged; `uncovered > 0` → rollback, `WORK_UPSERT_ADMISSION_CENSUS_NOT_EMPTY`. 7 the insert, exactly:

```sql
INSERT INTO public.work_upsert_admission (execution_profile, publisher_id, activation_id, evidence_reference, actor)
VALUES ('CROSSREF', $1, $2, $3, $4)
ON CONFLICT (execution_profile, publisher_id, activation_id) DO NOTHING
RETURNING execution_profile, publisher_id, activation_id, evidence_reference, actor, admitted_at
```

with `$2 = A`, `$3` the presented reference and `$4` `PolicyContext::user_id()`, never a caller value, executed inside the closure as `get_result(…).optional()?`; a returned row → commit and return it. 8 no row returned → re-run step 5's `SELECT` as a later statement of the same transaction, which under `READ COMMITTED` takes a fresh snapshot; it returns the row a concurrent admission committed → commit and return that row unchanged: its `evidence_reference`, `actor` and `admitted_at` are the first inserter's, and the presented reference is discarded. If that `SELECT` returns no row — impossible while `P` is held, as below — rollback, `WorkUpsertDatabaseFailure`. Nothing else is computed or persisted: the census is the complete correctness proof, and `evidence_reference` is the opaque pointer to the durable bootstrap and census proof.

**Repeated calls and expected conditions, exactly.** (a) The exact `('CROSSREF', P, A)` row exists: step 5 returns it unchanged, nothing is written and no census runs. (b) A row exists for another activation of the same publisher, admitted historically: it is neither a match nor a bar, because the primary key is per activation; steps 6–8 run for the current activation and, on a passing census, a second row is inserted; both rows persist until the publisher cascade, and `workUpsertAdmissions` lists only the current one (§4.4). (c) The activation changes while an admission is attempted: activation drift, below. (d) The publisher has no enabled `CROSSREF` assignment: step 4, `CROSSREF_PUBLISHER_NOT_COVERED`, nothing written. (e) The publisher does not exist: step 3, the released `EntityNotFound`, nothing written. No raw primary-key or foreign-key error reaches the caller for any of these, and none is part of any expected path: step 7 names the primary key's exact columns in `ON CONFLICT … DO NOTHING`, so it never raises a unique violation, and the publisher foreign key cannot fail because the publisher row is share-locked from step 3 to commit.

**Activation drift.** The released coordinator takes `P FOR UPDATE`, so under `P FOR SHARE` the activation read in step 4 cannot change before commit; a change that commits before step 3 is read as the new activation; a change after commit leaves the admission row naming the superseded activation, which the claim predicate (clause 4) and the fence (clause 7) then reject, so the new activation needs its own admission after its own census. A stale activation can never be persisted (T292).

**Concurrent exact admissions, exactly (C8).** Two admissions of one publisher whose `P FOR SHARE` locks overlap — the locks are compatible — read the same `A`, because the released coordinator cannot commit an activation change while either holds `P`, and both pass step 5. The first to execute step 7 inserts the row. The second's step 7 meets that uncommitted row in the primary key and waits for the first transaction to end — on the first transaction's lock, not on `P` — and then:

- if the first commits, the second's `INSERT` completes without inserting, raises nothing and returns no row; its transaction is not aborted; step 8's later statement sees the committed row and returns it unchanged;
- if the first rolls back, the second's `INSERT` inserts its own row and returns it at step 7.

Both transactions hold `P FOR SHARE` until they end, so the released coordinator's `P FOR UPDATE` waits until both have ended and `A` cannot change inside either: both callers return a row naming that one activation. #### 9.4 The drain and `remainingCandidates` — R-4 closed, selector made executable (C4), timestamp rotation withdrawn (C10)

**The sets.** Let `C(p)` be R52B §9.2's candidate set for profile `p`: `RESIDUE` rows and `STALE_PENDING` jobs. The **drainable set** `D(p)` is empty when `work_upsert_control.capture_enabled` is false for `p`; otherwise it is every `STALE_PENDING` candidate, whatever its eligibility or admission, plus every `RESIDUE` candidate whose Work satisfies R52B §14.2's whole eligibility predicate — E1–E6, the abstract-normalisation clause included — and whose current binding (`work → imprint → publisher`, and the activation of that publisher's enabled `p` assignment) has a `work_upsert_admission` row. `D(p)` is exactly the set of candidates on which R52B §9.3's unit, run with no intervening commit, creates a job or retires a stale row: a `RESIDUE` member ends `CREATED`; a `STALE_PENDING` member has its row retired at step 7 and ends `CREATED`, `INELIGIBLE` or `RESIDUE_NOT_ADMITTED`. On every candidate outside `D(p)` the unit would end `CAPTURE_DISABLED`, `INELIGIBLE` or `RESIDUE_NOT_ADMITTED`, creating no job and retiring no row; its only possible write there is step 8's one-time raise of a reservation's `0` generation row to `1`. Because no call examines a candidate outside `D`, such a `0` row stays `0` until the seed raises it (§9.2) or a captured edit does — the paths R52B §9.2 and §21.2 already give it — and the census counts it only when its Work is eligible, so nothing R52B relies on waits for the drain to raise it. Every predicate in `C` and `D` is a pure function of committed rows with no timestamp, interval or cadence; the classes are the ones R52B §20 entry 3, `workUpsertResidue`, already reports (`MATERIALIZABLE` is `D`'s residue; `NOT_ADMITTED` and `INELIGIBLE` are outside it). `work_upsert_generation.updated_at` is informational only, as R52B §9.2 states: no selector, unit, count or convergence argument of this amendment reads it.

**The selector, exactly.** `materializeWorkUpsertJobs` evaluates `D` over the requested profiles in two parts:

1. **one `READ COMMITTED` statement**, in its own `work_upsert_transaction` (§10.3 EB1), run outside any unit transaction and taking no row lock, returning every member of `C` over the requested profiles — with no `LIMIT` — and, for each: `work_id`, `execution_profile`, its class, the profile's `capture_enabled`, whether its current binding has an admission row, the value of the SQL-evaluable eligibility clauses (E1–E5 and every clause of E6 other than abstract normalisation), and the stored content of every abstract the abstract-normalisation clause evaluates for the root Work and for every emitted chapter;
2. **one pure Rust filter** over exactly those rows, with no further database read, keeping a row iff `capture_enabled` holds and either its class is `STALE_PENDING`, or its binding is admitted, its SQL-evaluable clauses hold and every returned abstract normalises under `thoth_api::markup::normalise_crossref_abstract_jats`.

The rows kept are `D`, ordered ascending by `(work_id, execution_profile)` — R52B §9.5's order. The call then runs R52B §9.3's unit, unchanged, for the first `limit` members of `D` in that order, one `work_upsert_transaction` each. **One definition, used twice:** the SQL-evaluable clauses are one SQL expression and the abstract clause is one Rust function, and the selector and the unit's step 10 each use that expression and that function, so the selector's decision and the unit's decision are the same predicate over the same committed rows (M15). There is no call-wide snapshot, no cursor, no keyset continuation, no second page, and no write made for scheduling: the unit adds nothing to R52B §9.3, and no row is mutated to change the order in which it is examined.

**Cost, stated honestly.** A call reads every candidate of `C` over the requested profiles and the abstract content of those candidates — undrainable residue included, which no call examines — so its read is linear in the number of candidates plus the total size of their abstracts. `remainingCandidates` repeats that read after the call's last unit commits, so a call that runs at least one unit reads `C` twice. `limit` bounds the number of unit transactions, and so the rows a call locks and writes; it does not bound the rows a call reads. The selector holds no lock across units and its snapshot ends with its statement. Executed (§17, E22 R5): with 50 residue Works failing the abstract clause and 3 drainable Works, `limit` 2, the two calls read 53 and 51 candidate rows and ran 2 and 1 units.

**Convergence, independent of scheduling.** Write `S` for a call's selector statement, `D_S` for `D` on `S`'s snapshot, and `E` for the first `min(limit, cardinality of D_S)` members of `D_S`.

1. **No unit is spent on an undrainable candidate.** A call runs units only on `E`, a subset of `D_S`, so undrainable residue, however large and however it sorts, never occupies a unit. The starvation that `ab09b119…`'s evidence E16 showed without rotation — undrainable rows sorting ahead of drainable ones — cannot occur.
2. **An examined member leaves `D`.** For `w` in `E`, if no transaction commits a change to `w`'s membership inputs between `S` and `w`'s unit — `w`'s generation row, its `WORK_UPSERT` jobs and their attempts, its ownership, its publisher's assignment and admission rows, the control row, and its captured eligibility inputs — the unit ends as the definition of `D` says, and `w` is no longer in `D`.
3. **Nothing enters `D` except through an external act.** A unit only creates a job for its own Work, which removes that Work from `C`, or retires its own stale row, after which its Work either receives its job in the same unit or is residue outside `D`. A Work outside `D` enters it only through a commit, by another path, that changes its membership inputs: a captured edit, an ownership move, an assignment or activation change, an admission, capture enable, or the resolution or withdrawal of its actionable job.
4. **Quiescent bound.** If no external act commits after some call's selector statement, each later call removes every member it examines and adds none, so `D` is empty after at most ⌈cardinality of `D_S` ÷ `limit`⌉ further calls, counting calls whose selector statement starts after the previous call's last unit committed. Overlapping calls lose nothing and create nothing twice: a member examined by two of them is created by one unit, and the other unit ends `PENDING_CURRENT` (E23 N3). The bound depends on no clock, cadence or call timing.
5. **Bounded wait below saturation.** A member `x` of `D` is examined by the first call in whose `D_S` fewer than `limit` members precede `x`. If, between consecutive calls, fewer than `limit` external acts make lower-ordered Works drainable, the number of members ahead of `x` falls by at least one per call, so `x` is examined within a number of calls bounded by the members ahead of it when it entered `D`.
6. **Saturation.** When at least `limit` lower-ordered Works become drainable again between every pair of consecutive calls — a worker resolving their jobs and editors changing those Works again, for example — every call drains `limit` Works and `x` may wait without bound (E23 N2a). This is a capacity condition, not a loss: every outstanding generation remains durable residue under R52B's INV-RESIDUE and is reported. Removing it would need durable arrival-order state — a clock or sequence value written for scheduling — or a new priority policy; the first is what this correction removes and the second would be a new latency semantic, and this amendment adds neither. O1 below observes it.
7. **Safety, unchanged.** The drain holds no authority (R52B §9.5): not running it, running it more or less often, or saturating it changes latency only.

**The withdrawn design, falsified.** `ab09b119…` ordered the selector by `(work_upsert_generation.updated_at, work_id)` and made an `INELIGIBLE` unit end write `updated_at = current_timestamp` so that an examined undrainable row would sort behind every unexamined one. That claim depended on the wall clock and failed (§17, E22): with a drainable Work's generation written one hour ahead of the rotation's clock, as after a backward clock step, ten calls rotated ineligible rows and never examined it; with the rows' timestamps equal to the rotation's value, as under a coarse or repeated clock reading, ties fell back to `work_id` and the same two rows were examined eight times; with the real clock, a drainable Work edited after every call was re-timestamped behind that call's rotations and never examined in ten calls; 50 ineligible rows ahead of 3 drainable Works cost 27 calls and 54 units; and a drainable Work committed after call 1's selector was first examined in call 4. One flush of a publisher-name edit wrote six generation rows with a single `updated_at` value. The corrected selector created the three drainable Works of the baseline in two calls, examined the single drainable Work of the clock, equal-timestamp and repeated-edit schedules in call 1, and examined the Work committed after call 1's selector in call 2; its selection was identical when `updated_at` was rewritten to future, past and equal values (E23 N1). The rotation write is withdrawn, and R52B §9.3's unit is unchanged.

**Result fields.** `examined` = units run, which is `min(limit, cardinality of D_S)` for `limit > 0`. `created`, `skippedResolved`, `skippedIneligible`, `skippedNotAdmitted` = units ending `CREATED`, `RESOLVED`, `INELIGIBLE`, `RESIDUE_NOT_ADMITTED`. `rebound` = units in which step 7 retired a stale `PENDING` row, whatever the unit's end; it overlaps the other counts. `examined − created − skippedResolved − skippedIneligible − skippedNotAdmitted` = units ending `NO_WORK`, `BINDING_MOVED_RETRY_LATER`, `CAPTURE_DISABLED`, `PENDING_CURRENT` or `RUNNING_IN_FLIGHT`, none of which is a separate field (R52B §19.2 fixes the seven). Every such end, and every `RESOLVED`, `INELIGIBLE` or `RESIDUE_NOT_ADMITTED` end of a `RESIDUE` member, records a commit between the selector and the unit. **`remainingCandidates`** = the cardinality of `D` over the requested profiles, evaluated by the same statement and the same filter after the call's last unit has committed, or taken from the call's single evaluation when no unit ran; no lock is taken. It counts every `STALE_PENDING` row; counts residue only when capture is enabled, the current binding is admitted and the Work satisfies the whole eligibility predicate; excludes residue failing the abstract-normalisation clause, which `workUpsertResidue` names `INELIGIBLE` with the failing clause; excludes a generation row that has an actionable `PENDING` or `RUNNING` job; excludes unadmitted and capture-disabled residue; and is reproducible from `D`'s predicate by any reader. A `BINDING_MOVED_RETRY_LATER` end leaves its candidate in `D` when the new owner is admitted, so a later call re-examines it. `limit <= 0` runs no unit and still evaluates `remainingCandidates`. Precedence: 1 `require_dissemination_worker()`; 2 `executionProfiles` empty → `WORK_UPSERT_EXECUTION_PROFILES_REQUIRED`; a member not registered → `WORK_UPSERT_PROFILE_NOT_IMPLEMENTED`; 3 the call. Tests: M1–M15.

**Operational observation and stop criteria** — predicates over results and reports, never clocks, as R52B §20 requires of alarms:

- **O1, saturation.** At `limit` 500, three consecutive calls each return `remainingCandidates` of at least 500 and `created + rebound` of at least 1: the drain is saturated (item 6). Stop increasing its cadence and escalate to the operator who owns the worker schedule; the wait bound of item 5 does not apply while O1 holds.
- **O2, no progress.** Three consecutive calls each return `remainingCandidates > 0` and `created + rebound = 0`: every examined unit met a concurrent change, or the selector and the unit disagree, which M15 forbids. Stop the drain schedule and investigate.
- **O3, undrainable growth.** `workUpsertResidue`'s `INELIGIBLE` or `NOT_ADMITTED` classes grow across consecutive drains: R52B §20's alarm, retained; such residue enlarges every call's read without ever occupying a unit.
- **O4, read cost.** Three consecutive calls fail with `INTERNAL_ERROR`, for example because the full read exceeds a server or proxy limit: stop scheduling drains and escalate. A bounded read would be a separately approved change to this selector, outside this amendment.

#### 9.6.1 After `CROSSREF_PERMIT_ATTEMPT_ALREADY_RESERVED`: recovery by the existing permit's state (C3, C9)

The refusal means exactly one thing: *this attempt already owns its one permit for all time, and reservation must not be repeated for it*. It is reached only by a caller that repeats a reservation for an attempt whose first reservation committed — after a lost reservation response, after an `INTERNAL_ERROR` that left the caller unable to know whether the reservation committed, or through a defect. It discloses nothing about the permit, and no report is available to the worker's role, because every report is `SUPERUSER`-only (R52B §20), so a worker cannot learn the permit's state from the API. R52B fixes the rest: a lost reservation response leaves no API or query from which the token can be recovered (§16.4); the superuser void is the fallback for a lost `RESERVED` token (§16.7); provider truth and reconciliation own every state in which an external write may have begun (§16.8, §11.7); `failDistributionJob` is refused while the attempt's permit is `RESERVED` or `AUTHORIZED` (`ATTEMPT_HAS_OPEN_RESERVATION`, `ATTEMPT_HAS_AUTHORIZED_PERMIT`; §10.8 row 5); released lease recovery closes a lapsed attempt `ABANDONED` and returns the job to `PENDING`, or to `FAILED` at the attempt budget, touching no permit (§10.8 rows 6–9, §11.7); and the Crossref claim guard and the fenced-abandonment clause keep the job unclaimable while its permit blocks or its fenced attempt is uncleared (§10.7 clauses 6 and 7, §14.4).

Two concepts are therefore kept apart.

1. **The protocol-stop.** `CROSSREF_PERMIT_ATTEMPT_ALREADY_RESERVED` is a reservation refusal only. It is never retryable, is never the `errorCode` of `failDistributionJob` or of any other job call, and never causes one (§9.6.2).
2. **Lifecycle recovery after the permit is resolved.** No new job-failure classification is needed and none is added. Every state is recovered by acts R52B already approves — released lease recovery, the superuser void, reconciliation with its internal clearance, and the next claim — and, for a worker that still holds its own `(permitId, reservationToken)`, by the job call R52B §28.3 already assigns to the protocol position that worker recorded, carrying that position's own code.

Diesel exposes no SQLSTATE: it maps PostgreSQL's unique, check, foreign-key, not-null, restrict, exclusion, serialization, read-only and connection conditions to named kinds and everything else, a PL/pgSQL `RAISE` included, to a kind Diesel documents as matchable only by `_`. The conversion, exactly:

1. `Error::DatabaseError(DatabaseErrorKind::CheckViolation, info)` with `info.constraint_name()` equal to one of the four exact CHECKs below → that CHECK's code.
2. `Error::DatabaseError(DatabaseErrorKind::UniqueViolation, info)` with `info.constraint_name()` equal to one of the two exact unique indexes below → that index's code.
3. `Error::DatabaseError(_, info)` with `info.constraint_name()` equal to `None` and `info.message()` either byte-equal to a member of `WORK_UPSERT_TRIGGER_CODES`, or split at its first `": "` into a prefix that is a member of `WORK_UPSERT_SUFFIXED_TRIGGER_CODES` and any remainder → the `ThothError` variant of that code, whose fixed message never contains the remainder.
4. Everything else — every other `DatabaseError`, whatever its kind, `constraint_name()` or `message()`; `Error::NotFound`; and every non-database Diesel error — → `ThothError::WorkUpsertDatabaseFailure`.

**The fixed internal failure.** `WorkUpsertDatabaseFailure` is a new variant whose `Display` text is exactly `A work-level distribution database operation failed.` and which has **no** `IntoFieldError` arm of its own: it falls to the released `_ =>` arm and reaches GraphQL as `"type": "INTERNAL_ERROR"` with that fixed message. Nothing about the SQL, the relation, the constraint, the trigger, the driver, the pool or PostgreSQL's text reaches the caller; the released assertion that `"INTERNAL_ERROR"` occurs exactly once in the `IntoFieldError` impl keeps passing, and no released error changes. It is not a code of §25.1 (§10.4). BE-06 statements that may legitimately find no row use `.optional()`, so a Diesel `NotFound` on a BE-06 statement is a protocol failure and maps here, never to `EntityNotFound`; where this amendment names the released `EntityNotFound` (§9), the operation raises it explicitly.

### 15. Independent-review attack surface

1. **The drainable set (C10).** `D` is R52B §14.2's whole eligibility predicate plus admission, evaluated on one statement's rows by one SQL expression and one Rust function that the unit's step 10 also uses. Attack the claim that every candidate outside `D` is one the unit would end without creating a job or retiring a row, that leaving a reservation's `0` row unraised until the seed or an edit is harmless, that the selector and the unit cannot disagree (M15), and that `D` contains no timestamp; the negative controls are the falsifications of the withdrawn rotation and its latency cost (E22).
2. **The drain's cost and saturation (C10).** Each call reads every candidate, twice when it runs a unit, and `limit` bounds only units. Under saturation a drainable Work can wait without bound (§9.4 item 6; E23 N2a). Attack whether R52B §9.5's "latency only" framing stays truthful there, whether O1–O4 are sufficient stop criteria, and whether any read of `C` could be bounded without new durable state.
3. **The seed's non-SQL clause.** The seed selector does not apply abstract normalisation, and a Work failing only that clause is seeded (§9.2). Attack whether covering it could mislead: `remainingUncovered` counts only eligible Works, so such a Work is never in it, and once seeded it appears in `workUpsertResidue` as `INELIGIBLE` with its failing clause and stays outside the drain's `D` until a captured edit makes it eligible.
4. **Non-disclosure on the worker routes.** A nonexistent job and a stale claim share `CROSSREF_PERMIT_CLAIM_STALE`, while the released `completeDistributionJob` returns `EntityNotFound` for a nonexistent job. The divergence is deliberate and stated.
5. **`CROSSREF_BINDING_MOVED_RETRY` for a permanent condition.** A disabled assignment is reported with a "retry" code because the worker's correct action is the same retryable failure and the drain retires the row; attack whether a worker could loop.
6. **Admission idempotence without a reference comparison.** A repeat with a different `evidenceReference` returns the original row, and a concurrent second caller's reference is discarded in the same way. Attack whether that hides operator error; the returned reference shows it.
7. **Concurrent admission (C8).** Attack `INSERT … ON CONFLICT … DO NOTHING`'s wait-then-skip under `READ COMMITTED`, the step-8 re-read's exactness — only the publisher cascade deletes an admission row, and `P FOR SHARE` excludes it — the dependency on the default isolation level, and the claim that two overlapping censuses cannot disagree.
8. **The defence mappings.** A shape-CHECK mapped to an argument code is exact only while tier 3's argument rules are enforced; a regression would be mislabelled rather than surfaced.
9. **The value-suffixed trigger codes.** Rule 3 of §10.3 accepts a remainder after the first `": "` for exactly two codes and never echoes it. Attack the split, whether any other code is raised with a suffix, and `WORK_UPSERT_TARGET_SET_MISMATCH`'s treatment as an invariant rather than a code.
10. **The blank rule's boundary.** Format characters are content. Attack whether a reference of only `U+200B` is acceptable; the rule is exact and tested, and stricter alternatives would need a hand-maintained table.
11. **Reset containment.** `cfg(test)` is the boundary; the textual scan is file-name based; the "no leaked session mode" rule is procedural; a session-level `replica` on a pooled connection the reset never samples is caught only on the reset's own connection.
12. **Authorization order.** Every mutation checks the role, then the route-derived role, before any own-input error; R52B §19.4 rule 3's numbered list said otherwise for three operations and is amended (§12). Attack any resolver that validates an argument before the route is read, or that lets a not-found answer precede the coarse role check.
13. **SDL rendering.** `force: Boolean! = false` and `limit: Int = 100` are pinned to juniper 0.16.2's rendering; the 115 and 104 counts are pinned to `b23ba05c`.
14. **Evidence provenance.** Everything in §17 is specification-harness or prototype evidence on disposable instances; nothing is implementation acceptance evidence. The drain prototype modelled the SQL-evaluable clauses by DOI, landing page, publication date and status and the abstract clause by a marker in abstract text; the admission and error-boundary probe ran the specified Diesel calls through a scratch copy of `thoth-errors`; and the `DIS-04` rules were checked as a decision model against the released worker module, not as `DIS-04` source, which does not exist.
15. **The typed error boundary (C11).** Compile-time exclusion of the released conversions holds inside `work_upsert_transaction`; EB1's exception passes four entry points' released helper errors through; EB2's `.work_upsert()` rule is enforced by static scan (X4) and review, not by the type system; EB3 leaves pool errors, released statements and `COMMIT`-time BE-06 trigger errors inside released transactions on the released conversions; and EB1 and EB2 record the withheld text server-side. Attack a future BE-06 statement written outside EB1 and EB2, a helper added to the exception without X11 failing, and whether any EB3 message can carry more than a BE-06 code or PostgreSQL text.
16. **Recovery by state and the `DIS-04` contract (C9).** A protocol-stop after a lost reservation response costs a lease period and an operator act. Attack whether any of the six states lacks a token-free exit, whether §9.6.2 rule 2's continuation could ever derive a job call from the refusal, whether "persistence optional" leaves any R52B conformance item unsatisfiable, and whether any rule of §9.6.2 decides something #106 reserves to `DIS-04`.
